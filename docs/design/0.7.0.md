# Design of spec-dna 0.7.0

Status: accepted, 2026-11-16. The owner accepted this design with the answers in section 14. This page is a design only. It adds no code. The work in section 13 starts after it.

0.7.0 turns spec-dna from a gate and a corpus control into one tool for the whole change. It has a deterministic core and a pack of skills on top. The pack covers the stages that Spec Kit, OpenSpec and Superpowers cover. The core keeps what none of them has: the layer graph, the ids and hashes, the gate against the base and the locked decisions.

Each decision has a number (D1 to D41). A question that only the owner could answer is one of Q1 to Q8. Section 14 gives each question, its recommendation and the answer. [ADR 0010](../adr/0010-workflow-pack.md) to [ADR 0017](../adr/0017-profiles.md) give the reasons and the rejected options of each group of decisions.

## 1. Evidence and sources

### Evidence from earlier versions

The data of the experiments stays outside this repository, in the lab report of the owner. This page names the corpus as "corpus A: mature product, about 2.3k documents" and gives no number of corpus A.

| Fact | Result | Use in 0.7.0 |
| --- | --- | --- |
| The gate against the base held the accepted decisions | Corpus A: edits of the locked `Decision` text of accepted ADRs stopped when the gate ran. Synthetic project: 15 of 15 correct runs with the gate, 6 of 15 without it | The core keeps the gate. A skill must bind to a check where it can (D2) |
| Agents search the repository and seldom follow a tree of links | A reorganization of large documents gave no gain | Skill text is short and on demand. No skill depends on an agent that follows a link tree |

| Fewer tokens is not the gain | On the synthetic project the input with the tool was 1.4 to 2.0 times higher. The gain was the cost of a correct result | The eval plan measures cost per correct outcome (D32) |
| One process step costs one pull request | 0.6.1: the intent, the plan with the design, the code with `finish` and the pin were 4 pull requests (#34, #35, #37, #40) | Section 4 and D11 to D17 cut the count |

## 3. The workflow pack

### D1. Own skills, bound to the artifacts of spec-dna

spec-dna ships its own skills. It does not wrap the skills of an installed plugin. [ADR 0010](../adr/0010-workflow-pack.md) gives the reasons:

- A plugin skill writes its own files, such as `docs/superpowers/specs/<date>-<topic>-design.md`. These files are not an `intent.md`, so the gate and `next` do not see them.
- A wrapper cannot pin the text. The project pins the binary (ADR 0003), so the skill text must come from the binary. A plugin updates on its own.
- A check cannot bind to a skill that spec-dna does not own. A check binds to a file and a section.
- A hook of Superpowers injects its entry skill in each session. Its text tells the agent to invoke a skill at a chance of 1%. This hook competes with `spec-dna next`, and 2 entry points give 2 answers.
- The skills must work for an agent that is not Claude Code (D4).

Superpowers (MIT) gives 4 ideas to the pack:

- A fresh subagent for each task, with a review after it.
- A test that fails before the code.
- The cause before the fix.
- The proof before the word "done".

spec-dna writes its own text for them. If a later build copies text, it adds the MIT notice of the copyright holder to `docs/research/matrix.md` in the same pull request.

### D2. The 11 skills

A stage skill binds to a step that `next` names. An event skill binds to an event. The column "Floor" names a check that fails when the artifact of the skill is wrong. It does not check what the skill adds, such as the order of a test and its code. The column "Default" gives the state before the first eval result, and its reason (D33).

| Skill | Kind | Trigger (the start of the description) | Artifact | Floor | Default |
| --- | --- | --- | --- | --- | --- |
| `brainstorm` | Stage `plan` | A request starts a change | `intent.md`: intent, why now, out of scope, class | SD306 (a placeholder stays) | On (carried from 0.6) |
| `specify` | Stage `design` | The intent is `accepted` and the class is `higher-risk` | `spec.md`: `Delta` with hashes, `Interfaces`, `Decisions` | SD914, SD920 | On (a gate checks the artifact) |
| `clarify` | Stage `design` | The spec has an open concern or question | The sections `Concerns` and `Open questions` of `spec.md`, answered | SD919, SD922 | On (a gate checks the artifact) |
| `write-plan` | Stage `build` | Before the code | `plan.md`: `Files` and small tasks in `Order` | SD913, SD923, SD924 | On (a gate checks the artifact) |
| `execute` | Stage `build` | The plan is `approved` and a task is open | The code, the tests and the checked task | SD913 (the scope only), the hook `protect-tests` | Off (no check of what the skill adds) |
| `tdd` | Stage `test` | A requirement has no evidence | A test with a `covers:` tag, run red before the code | SD608, SD916 (the tag, not the order) | Off (no check of what the skill adds) |
| `review` | Stage `deploy` | Before a merge | The review of the diff in the 3 passes of `REVIEW.md` (Bugs, Security, Compliance), and the answer to review comments | None: the text is the same as `REVIEW.md`, which is a prompt | On (carried from 0.6) |
| `verify` | Stage `deploy` | Before the word "done" | The output of the `Proof` commands and of `check` | `finish` stops on SD915, SD916 (the result, not the proof run before it) | Off (no check of what the skill adds) |
| `finish` | Stage `closed` | The change is ready to apply | The result of `spec-dna finish` | `finish` itself | On (a gate checks the artifact) |
| `debug` | Event | A test or a command fails, and the cause is not known | A reproduction, then a regression test, then one fix | None | Off (no check) |
| `post-mortem` | Event | An `incident` has an open follow-up | A new `intent.md` with `from:`, and an eval file | SD918 | On (a gate checks the artifact) |

The 7 skills "On" are 2 that replace `spec-dna-intent` and `spec-dna-review` of 0.6 (an upgrade keeps them on), and 5 whose artifact a gate checks. The 4 skills "Off" have no check of what they add. `init` generates them only when the project lists them, and it proposes them at the level `full`. A skill that is off is still available: `spec-dna skill show <name>` prints its text (D4). D33 gives the rule that turns a skill on. The 7 skills that are on have no eval result yet. D33 and Q3 give the plan to measure them.

Each skill has 5 parts, in this order:

1. When to use the skill.
2. The commands to run.
3. The artifact to write.
4. The check that must pass.
5. What to do when the check fails.

A skill never sets `accepted` or `approved`. The change guide names the approver.

`write-plan` and `execute` use the task form of 0.6.0: `- [ ] <id>: <text>. Files: <paths>. Verify: <check>.` The 2 passes of `execute` are:

1. Compliance: the diff of the task against the task, `spec.md` and the rules of the project.
2. Quality: the diff against the style of the code, the tests and the simplicity.

`execute` starts one fresh subagent for each task. It uses the roles of 0.6. At the level `full`, `implementer` builds, `verifier` runs pass 1 and `code-simplifier` runs pass 2. At the level `lean`, a fresh general subagent builds and `verifier` runs both passes. It needs no new role.

### D3. The disciplines

5 rules apply to each task. Each rule is one line of 140 bytes or fewer. The detail of each rule is in one skill, and the rule names that skill.

The adapter skill `spec-dna` holds the 5 lines in a block of 700 bytes or fewer. Its description makes Claude Code load it for each task of a spec-dna project, but a skill body loads on demand. Thus the block is not in the request of an agent that does not load the skill. One line of 400 bytes or fewer in `AGENTS.md` names the 5 rules for each other agent. This line is the line of ADR 0003 made longer.

| Discipline | The line (the idea) | Detail in |
| --- | --- | --- |
| Test first | Write a test that fails before the code | `tdd` |
| Cause first | Find the cause of a failure before the fix. After 3 failed fixes, stop and ask | `debug` |
| Proof before done | Run the proof and read its output before you say "done" | `verify` |
| Review is data | Check each review comment against the code before you act on it | `review` |
| Isolated work | Do each change in its own git worktree or branch | `execute` |

The block is small, because the measured gain of a short core is firm only for the first request (section 1). A discipline works when its skill is off: the line is the rule, and `spec-dna skill show <name>` prints the detail on request (D4).

### D4. Delivery and names

- The skill folder is `.claude/skills/spec-dna-<name>/SKILL.md`, with the harness marker of 0.5. `next` prints the bare name (`write-plan`), as in 0.6.
- The text of each skill is a constant in the binary. `spec-dna skill list` prints the 11 names, their kind and their state. `spec-dna skill show <name>` prints the body of one skill, with no front matter and no marker. It works for a skill that is off. An unknown name gives exit code 2. Both take `--json`.
- An agent without a skill folder runs `spec-dna skill show <name>` for the step that `next` names. `AGENTS.md` carries this one line.
- `[harness] skills` lists the names. The 0.6 names `intent`, `spec` and `plan` end, and `review` stays. `upgrade` and `init` map them: `intent` to `brainstorm`, `spec` to `specify` and `clarify`, and `plan` to `write-plan`. A key with an old name is an error (exit code 3), and `upgrade` rewrites it.
- `init` removes an unedited file of an old skill folder, and it keeps an edited file. `check` reports SD501 for a kept file, as for a role in 0.6.

### D5. Another workflow plugin in the same project

If the project also has Superpowers, 2 skills of the same stage compete. The rules are:

- The description of each spec-dna skill starts with "In a spec-dna project". This states the scope. It helps the match, but nothing proves that Claude Code selects it. No eval of D32 has Superpowers installed, so this is an open limit (ADR 0010).
- The adapter skill states: "A spec-dna skill replaces a general skill of the same stage. For `write-plan` it replaces `writing-plans`." The 2 sets then give one answer.
- `init` reads `.claude/settings.json` of the project. If `enabledPlugins` names a plugin with the word `superpowers`, `init` prints a note with these rules. It never reads a file of the home folder.
- A file that a plugin writes into a root, such as `docs/superpowers/specs/`, is outside the intent layer. `init` does not move it. The note tells the person to exclude that folder from the roots.

### D6. Budgets

The 0.6 limits stay: a description has 160 characters or fewer, and a body has 2,500 bytes or fewer. The new limits are:

- All descriptions together, as the skill listing of Claude Code shows them (`- spec-dna-<name>: <description>` and a line feed for each skill): 1,900 bytes for the 11 skills, and 1,250 bytes for the 7 skills that are on. The prefix "In a spec-dna project" is in these counts.
- The block of disciplines in the adapter skill: 700 bytes. The line of `AGENTS.md`: 400 bytes.
- A test fixes each limit. The test of 0.6 fixes the size of the listing of the 4 skills, 588 bytes (the 4 descriptions alone have 512 bytes). The limit of one description stays 160 characters.

## 4. The count of pull requests

### Measurement

The lab script `before.sh` builds a scratch repository with a bare origin, `gate = "block"` and the binary 0.6.1. It squash-merges each branch, as GitHub does. It tries the change in one branch, and then in the fewest branches that give exit code 0 of `check --base origin/main`.

| Change | Pull requests before | Result of 1 branch |
| --- | --- | --- |
| Routine: intent, plan, code with `finish` | 3 | Exit code 1 with 3 SD910 errors (one for the plan and one for each code file). With `finish` in the same branch: 1 SD910 error |
| Higher-risk: intent, spec, plan, code with `finish` | 4 | Exit code 1 with 4 SD910 errors. With `finish` in the same branch: 1 SD910 error |

The real history gives the same result. The change of 0.6.1 had the class `routine` and a design page. It took 4 pull requests in 7 hours, from the first merge to the last merge. They were the intent (#34), the plan with the design (#35), the code with `finish` (#37) and the pin (#40).

The lab scripts `after.sh` and `model.py` apply the rule of D11 to a real branch with 7 commits. `model.py` reads the SD910 findings of the 0.6.1 binary and clears a finding when the commits hold an approval that D11 accepts. It is a model, not the code of the product. It covers the higher-risk change. The routine count follows from the same rule with one artifact less.

| Branch variant | SD910 findings | Left after D11 | Statuses set outside an approval commit |
| --- | --- | --- | --- |
| `ok`: the approvers approve each artifact before its successor | 4 | 0 | 0 |
| `late`: the approval of the plan comes after the code | 4 | 2 (the code files) | 0 |
| `stranger`: the approval commits come from an author that is not an approver | 4 | 4 | 3 |
| `mixed`: the approval commit of the intent also edits the text | 4 | 1 (the spec) | 1 (the intent) |
| `backdoor`: a later commit adds a path to `Files` and creates the file | 5 | 1 (the new file, reason 8 of D17) | 0 |

### Result, per profile

The rules of D11 to D17 and D18 to D20 give the "after" column. Nobody measured it on the product, because the product does not exist yet.

| Change | Before | After, `lite` and `standard` | After, `strict` |
| --- | --- | --- | --- |
| Routine | 3 | 2: the intent and the plan (approved in the branch), then the code with `finish`. Under `gate = "warn"`, `check` does not enforce this floor | 3 |
| Higher-risk | 4 | 2: the intent, the spec and the plan (approved in the branch by the owner), then the code with `finish` | 4 |
| The pin after a release (the checkout of spec-dna itself) | 1 | 0 (D18, D19) | 0 |

The floor is 2, not 1, because of `log`. A squash merge writes only the net diff. A change that starts and ends in one pull request then leaves no record (D16). The first pull request holds the approvals, and the owner reads the design before the work starts. The owner answered Q2 with no: no key turns the record off, and the floor stays 2 pull requests.

The floor of 2 does not force a design pull request. The change guide advises this order for a higher-risk change: the pull request of the intent, the spec and the plan first, then the code with `finish`. The rule also allows a first pull request with the approvals and the code, and `finish` alone in a second one. ADR 0006 rejected `finish` after the code. Thus this order stays a convention, and `check` does not enforce it.

## 5. The entry points

### D7. `next` stays the entry of an agent

`spec-dna next <slug>` stays the one entry of an agent. The 9 names of 0.6.0 and the step of each name do not change. Each line has `[skill: <name>]`. With `--json`, each item has the field `skill`. A test fixes the list. In branch mode, the line of `next` for an approval says that an approver commits the `status` line alone, so an agent does not make a mixed commit.

### D8. `status` stays the entry of a person

`spec-dna status` also names the skill `post-mortem` for an incident with an open follow-up. It shows, for each change, the source of each approval: `base` or `branch <short sha>`.

### D9. `debug` has no stage

`debug` is an event skill. `next` does not name it, because a failure has no stage. If the project lists it, its description starts it. If it is off, the discipline "Cause first" (D3) still gives the rule, and `spec-dna skill show debug` gives the detail. The eval of `debug` (D32) measures the start.

### D10. `spec-dna skill` is the one command of the pack

It reads no document and never writes (D4). The eval commands are in D35.

## 6. The approval in the branch

[ADR 0012](../adr/0012-approval-in-the-branch.md) amends ADR 0006 and ADR 0001 ("Layers": a gate reads 2 trees, and a fetch of depth 1 is enough). The branch rule also reads the commits of the range, so it needs a full history. These decisions apply when `[change] approval = "branch"`.

### D11. The rule

`check` walks the commits of `base..HEAD` from the oldest. A commit that touches an artifact or a path of `Files` needs the approval of the earlier artifact. The approval is in the base tree, as in 0.6, or in an approval commit that comes before this commit in the walk.

An approval commit must meet all these conditions:

1. It is not a merge commit.
2. The e-mail of its author is in `[change] approvers`. The compare ignores case and needs an exact match.
3. It changes one file only: `intent.md`, `spec.md` or `plan.md`. It changes the `status` line only, to `accepted` for an intent and `approved` for a spec or a plan.
4. The file is an artifact of a change that the branch started or continued.

The class decides the artifact that needs the approval: the spec needs an `accepted` intent. A plan needs an `accepted` intent for a routine change, and an `approved` spec for a higher-risk change. Code under `Files` needs an `approved` plan. This is the rule of 0.6. It uses the base tree plus the approval commits before the commit, not the base tree alone.

The scope of a plan is its `Files` at the approval commit. A path that a later commit adds to `Files` has no approved plan, and `check` gives SD910 (reason 8 of D17). SD913 is only a warning, so it cannot hold this case.

The rule also covers the last approval. Take each artifact whose status is `accepted` or `approved` and differs from the base tree. An approval commit that meets the 4 conditions must have set that status. A merge commit does not count. Else `check` gives SD910, also when no later commit depends on the status. Else nothing checks the last approval: after the squash, the next pull request reads it from the base tree with no author.

### D12. The identity of the approver

An author e-mail is not a proof. A person can set any e-mail, and an agent often commits with the e-mail of its owner. The condition keeps its hard form: an approval commit of an author outside the list does not count. The limits are in [ADR 0012](../adr/0012-approval-in-the-branch.md):

- The check proves the order of the commits and a match of the e-mail for each status that the branch sets. It does not prove that a person read the text.
- The real control is the code host: `CODEOWNERS` for `docs/intent/`, a protected default branch, and required signed commits.
- For a higher-risk change, the owner should list only the e-mail of a human, and the agent must not commit with it. Then the owner makes the approval commits in the web editor of the host. The owner answer to Q5 changes this advice for this repository: see section 14.
- A person who hides an e-mail on the host commits in the web editor with a `users.noreply.github.com` address. `approvers` can list more than one e-mail for one person. The owner lists that address too.
- The one list serves 2 classes. ADR 0006 lets the agent approve a routine plan, so the e-mail of the agent must be in the list for a routine change. A project that wants a human approval of each higher-risk plan does not list the agent. For a routine change, it then has 2 options. It accepts 3 pull requests, or a human makes the approval commit of the routine plan.

### D13. The history must be complete

The rule fails closed. The branch counts no approval in each of the first 3 cases below, and SD910 reports as in 0.6:

- The clone is shallow, and the merge base is not reachable. The message says "shallow clone". `init` writes `fetch-depth: 0` in each workflow that it generates and that runs `check`. The guide says the same for a workflow that a person writes.
- A merge commit in the range merges another branch into this one. It stops the rule, except in 2 neutral cases:
  - Its second parent is an ancestor of the base tip: the branch took the base.
  - Its first parent is the base tip: the test merge of a host.
- A merge queue makes a commit whose first parent is not the base tip. The rule stops there. The check on the pull request event holds the rule. A required check must also report on the event `merge_group`, and there it gives the result of 0.6.

In a fourth case, a commit has an approval and another change in the same file. Only this commit gives no approval.

If the base is unknown, no change check runs, as in 0.6.1. The note says so.

### D14. `strict` keeps the base

`approval = "branch"` in a configuration with `profile = "strict"` is an error (exit code 3). `strict` reads the approvals of the base tree only, as 0.6.

### D15. Keys

| Key | Values | Default | Meaning |
| --- | --- | --- | --- |
| `[change] approval` | `base`, `branch` | `base` | `branch` turns on D11 |
| `[change] approvers` | list of e-mails | none | Required and not empty when `approval = "branch"`. Else an error (exit code 3) |

`init` writes `approval = "branch"` and `approvers = ["<git user.email>"]` for `lite` and `standard`, and `approval = "base"` for `strict`. An upgraded project keeps `base`. A change of these keys edits `spec-dna.toml`, so SD503 applies.

### D16. A change that starts and ends in one branch

A branch that adds an intent and deletes it with `finish` gives SD910, also when approval commits exist. This is the case "added and finished in this branch". `log` reads the deletion of `intent.md` on the default branch, and a squash merge leaves no such deletion. This keeps the record of ADR 0006 and the 2-pull-request floor of section 4. The owner answered Q2 with no, so no key turns the record off.

### D17. The message

The message of SD910 names one reason of 8:

1. No approval in the base.
2. No approval commit before the work.
3. An author that is not an approver.
4. A commit that changes more than the status.
5. A shallow clone.
6. A merge commit that stops the rule.
7. The change was added and finished in this branch (D16).
8. A path that is not in the `Files` of the plan at the approval commit.

The `fix` text says which. The change adds no diagnostic code.

## 7. The checkout of spec-dna itself

[ADR 0013](../adr/0013-self-hosting.md) gives the reasons.

### D18. The tree binary

A 0.6.1 binary exits with code 3 on an unknown top-level table (the lab test: `unknown key dev`). A key cannot start a mode in the release that introduces it. Thus the mode needs no key. The binary reads a fact of the checkout instead:

- The file `Cargo.toml` at the top level of the git repository that holds `spec-dna.toml` has `name = "spec-dna"`.
- Its `version` is equal to the version of the binary that runs.

If both are true, the binary is a tree binary. A tree binary changes one rule only (D19). The pin stays exact for each other rule: a pin that differs from the version of the binary stops `check`, `finish` and `eval run` with exit code 3, as in 0.6.1. A release binary in another repository never finds this file with this name, so it keeps the exact pin of ADR 0003.

### D19. The pin line and SD503

In a tree binary, SD503 does not count a change of the line `spec-dna = "..."` of `spec-dna.toml`. A change of any other line counts as before. SD503 reads paths only today, so this needs a read of the diff of that one file. The build changes SD503 and its section in `docs/diagnostics.md`.

Thus the release pull request sets the version in `Cargo.toml` and the pin in one commit, and the tree binary equals the pin. The pull request of the pin after the release ends. Between a commit of the version and a commit of the pin, a local run stops with exit code 3, so a person makes them one commit.

A release pull request cannot hold the sums of a release that does not exist yet. This repository has no `[spec-dna-sha256]` table, so this limit does not apply to it.

### D20. The self-check in CI

CI gets a job that builds the tree binary and runs `check --base origin/master` on this repository, with `fetch-depth: 0`. 0.6.1 has no such job, so no pull request checks the documents of this repository. The job is the first slice of the build (section 13), because each later pull request then uses the new rules.

## 8. The import

[ADR 0014](../adr/0014-import.md) gives the reasons. The sources are Spec Kit 1.4.1 and OpenSpec 2.0.0.

### D21. The command

```text
spec-dna import speckit|openspec [--dry-run] [--skip-open] [--areas <file>] [--keep none|research] [--json]
```

- `import` needs a project that `init` made. Else it stops with exit code 3 and says "run `spec-dna init` first".
- It refuses a tree that is not clean, also with `--dry-run`, as `upgrade` does. It moves a document with `git mv`, so git keeps the history. It never deletes a file and never commits.
- It builds the whole plan in memory, proves it (D22), and then writes.
- If the plan needs a change of `spec-dna.toml`, the first run writes only that file. Such a change is a legacy key pattern for `FR-nnn`, an area or a type. SD503 rejects it together with other files. The person commits it in a pull request of its own and runs `import` again. The second run writes the documents.
- An open Spec Kit feature or an open OpenSpec change becomes an intent folder with a draft `intent.md`, `spec.md` and `plan.md` in one diff. The base has no approval of them, so `check` gives SD910 for each such folder, and `gate = "block"` fails the pull request. `--skip-open` leaves the open changes in place and imports only the rules and the current truth. The report lists the SD910 findings that the import causes.
- `--keep research` needs the layer `research`. If the graph has none, the command stops with exit code 2 and says "run `spec-dna layer add research`".
- The exit codes are these:
  - 0: a write, or nothing to change.
  - 1: a tree that is not clean, a stop or a failed proof.
  - 2: a usage error.
  - 3: an unknown layout, no project or a bad file.
  - 4: a git or write error. The message gives the commands that restore the tree.
- `--areas` has the form of `upgrade --layout --areas`: a TOML table `[areas]` that maps a source name to an area folder. `--keep research` is D26.

### D22. The proof

The proof of `import` states what it proves. It does not claim byte equality, because OpenSpec moves a requirement from a heading to a list item.

1. Each requirement of a source spec has one target requirement, or one target delta line for a change. Their normalized sentences are equal. The normal form removes the markup of the heading or the bold key, and it joins the white space. The report lists each pair: the old place and the new id.
2. Each source file has exactly one state in the report: moved (`git mv`), written, left in place, or skipped. A written file is a new file that holds the text of the source. The source stays, and the report prints the `git rm` command for it. A skipped file names its reason.
3. No id of the project before the import disappears.
4. `check --all` on the new tree gives no new error of the codes SD101 to SD106, SD201 to SD204, SD301 to SD306 and SD401 to SD405. These are the codes of references, ids, front matter and statuses. The proof ignores the codes of evidence, budgets and changes (SD608, SD7xx, SD9xx), because the imported text has no `covers:` tag and no intent yet. The report lists them (D21).
5. A second run writes no file and moves no file. The files that the report lists as left in place stay as they are.

The proof covers sentences. A scenario of OpenSpec moves with its requirement, but the hash of a requirement covers its sentence only, so no hash covers a scenario. The proof counts the scenario headings of the source and of the target, and they must be equal. The proof stops the write (exit code 1) if one of the 5 steps fails.

### D23. Spec Kit (1.4.1)

| Source | Target | Rule |
| --- | --- | --- |
| `.specify/memory/constitution.md` | `rules/constitution.md`, type `rule` | Each principle heading becomes a requirement key. The text stays. The import skips a file that still has the template placeholders (`[PROJECT_NAME]`), and the report says so |
| `specs/NNN-<name>/` with a `tasks.md` that has no open task | `requirements/<name>.md` | The feature is done. Its `FR-nnn` lines become requirements through a legacy key pattern. The id `NNN-<name>` is an alias |

Each `FR-nnn` line becomes a delta line `ADD requirements/<name>#fr-nnn: sentence`. Each task `T001 [P] [US1] text in path` becomes `- [ ] t001: text. Files: path.` The task has no `Verify:` label, because the source gives none, so SD923 reports it. The mark `[x]` stays |

Spec Kit has no merged view of the truth. A later feature can change a requirement of an earlier one, and the import cannot see it. Each done feature becomes one `requirements` document, in the order of `NNN`. The report says that these documents can contradict each other, and a person reviews them.

### D25. An unknown layout stops the import

`import` stops with exit code 3 and writes nothing in each of these cases:

- `.specify/` or `openspec/` is absent, or the folder `specs/` is absent for the named source.
- A spec file has no `### Requirement:` heading and no `FR-` line, so the import finds no requirement.
- The source layout belongs to another major version. For OpenSpec, a folder `openspec/specs/` with no domain folder is such a case.

The message names the file and the rule that failed, and the supported versions.

### D26. The archive and the other files

ADR 0006 rejected a status that keeps finished changes, because an old plan is a search hit next to the current truth. The import honors this. The default is `--keep none`: no archived change and no extra document of a feature becomes a document of spec-dna. They stay where they are, and the report counts them.

`--keep research` is not the default. It moves each archived change or extra document to `research/imported/`, as one `research` document. The layer `research` has `context = "on-request"`, so `context` never serves it. The report states that the files remain search hits.

### D27. What the import does not read

The delta of spec-dna has no rename verb. `RENAMED` of OpenSpec would need a `REMOVE` and an `ADD`, which change a key with no proof of the references to it. So the import keeps a change with `RENAMED` in place and reports it. The import does not read `.openspec.yaml`, `openspec/schemas/` or the extensions of Spec Kit.

## 9. The limits of 0.6.1

[ADR 0015](../adr/0015-limits-of-0-6-1.md) gives the reasons.

### D28. A paragraph under `Files`

The parser keeps the first paragraph of the section `Files`. A paragraph with the first word `none` (any case), followed by `:`, `.` or the end of the paragraph, means the same as `- none`. A paragraph such as "None of the old files stay" is another paragraph. Another paragraph gives the line "the section `Files` has a paragraph and no list item; write the paths as a list, or write `- none`" in `next`, `status` and the messages of SD913 and SD915. `PARSER_VERSION` is 14, so spec-dna rebuilds the cache once. If the cache holds the new field, the build also changes the cache `FORMAT`.

### D29. `index` on a layer with a status

`index` never writes a document that `check` rejects. Assume that the types of the layer need a status, and the index document has none. Then `index` writes the first status of the type that the place gives. If it cannot name one, it stops with exit code 2 and names the layer. A `failure-analyst` proves the cause of the empty target of SD304 first (section 13, slice 7).

### D30. Area names that differ only in case

The configuration reader compares the names of `areas` in lowercase ASCII. A pair of names that differ only in case is an error (exit code 3). `new`, `mv`, `import --areas` and `upgrade --layout --areas` use the same compare. A project that has such a pair gets the error at the first run and renames one area.

### D31. `git mv` of an intent with no alias

`log` and `stats --sdlc` treat a rename of `intent.md` out of the intent folder as a move when 3 conditions are true:

1. Git rename detection (`-M`, similarity of 50% or more) finds the rename.
2. The new file is identical to the old file, or it has the old id as an alias.
3. The same commit deletes no other file of the change folder.

A plain `git mv` has no alias, and it gives an identical file, so it is a move. A `finish` commit that adds a near copy of the intent, with no alias, is not a move (condition 2). With the alias, it is not a move when `finish` deletes the other files of the folder (condition 3). The alias also keeps the old id valid for links (SD101).

One case of 0.6.1 stays: a folder that holds only `intent.md`, and a near copy with the alias in the commit of `finish`. A move that changes more than half of the text still ends the change, as in 0.6.1. Of the 6 limits of 0.6.1, D28 to D31 close 5. The sixth is `layer add` with a `types` list on many lines. The TOML editor cannot grow such a list, and the message already tells the person to add the types by hand.

## 10. The evals of the pack

[ADR 0016](../adr/0016-skill-evals.md) gives the reasons.

### D32. What the set measures

The shipped set has 5 evals for each of the 11 skills (55 evals). Each eval has the key `skill`. The runner runs each eval in 2 arms, with the same runs in pairs:

- `with`: the temporary copy of the tree has the skill folder, also when the skill is off in the configuration. The runner writes it with the text of `skill show`.
- `without`: the temporary copy has no skill folder and no discipline line. It has no name of the skill in the adapter skill and in the line of `AGENTS.md`. The arm denies `Bash(spec-dna skill*)`, so the agent cannot read the text. `next` still prints `[skill: <name>]`, so the arm measures the absence of the text, not of the name.

The working tree never changes. The unit of data is one run. The pass rate of a skill is the share of its runs that pass. The 4 runs of one eval are not independent, so the interval resamples the 5 evals first, and then the runs of each eval. A pair is the same eval and the same run number in both arms.

The result for each skill has these fields:

- The runs, the passes, the pass rate, the cost and the cost per correct outcome of each arm.
- The difference of the pass rates, with a 90% interval from the bootstrap (2,000 resamples, seed 24).
- The ratio of the costs per correct outcome, with a 90% interval. If a resample has no pass in an arm, the ratio is undefined, and rule 2 of D33 is not met.
- A verdict.

The runner uses no model grader. Each check is a command of the pack, as ADR 0008 requires.

### D33. When a skill is on by default

A skill is `on` when the committed result shows one of these:

1. The pass rate with the skill is at least 0.20 above the pass rate without it. The lower end of the interval is above 0.
2. The pass rate with the skill is not more than 0.05 below the pass rate without it. The cost per correct outcome with the skill is at most 0.90 of the cost without it. The upper end of the interval of the ratio is below 1.

The verdict is `off` when the upper end of the interval of the difference is below 0. Else it is `inconclusive`. A skill that is off in D2 and has the verdict `off` or `inconclusive` stays off. A skill that is on in D2 stays on unless its verdict is `off`. A verdict `inconclusive` does not turn it off. `eval verdict` prints it, and the release notes name each skill that has no verdict `on`.

The rule is strict by design. A simulation with 20 runs for each arm and a true pass rate of 0.8 against 0.6 (a gain of 0.20) gave the verdict `on` in about 36% of the trials. That simulation resampled single runs. The bootstrap of D32 resamples evals, so it gives fewer. Thus rule 1 finds only a large gain. A small gain is `inconclusive`, and the skill stays off. A test of the earlier sessions gave an interval that includes 0 for a small gain. The build runs the same simulation on the bootstrap of D32 before the pack ships (slice 5).

### D34. The cost

The estimate for the full run is 55 evals x 2 arms x 4 runs, which is 440 runs, and about 440 US dollars at about 1 US dollar for a run (lab sessions 8 and 16). The pilot runs the 20 evals of the 4 skills that are off: `execute`, `tdd`, `verify` and `debug`. It has 160 runs and costs about 160 US dollars. These 4 verdicts decide the most.

The line of `AGENTS.md` (D3) is in each run, and no eval measures it alone. The pilot adds one pair of arms for it: 5 evals with the line and without it, 40 runs, about 40 US dollars. The pilot then has 200 runs, and the full run has 480.

The default of `max-total-usd` is 20, so each run needs `--max-total-usd` above its estimate. The numbers are estimates. The owner answered Q3: the pilot runs after slice 5, the full run runs before the tag, and the 2 steps cost about 520 US dollars in total. The owner allows a higher `--max-total-usd`. The work stops at 600 US dollars and reports.

### D35. Commands and the check

- `spec-dna eval pack` writes the shipped evals and their small fixtures to `<[evals] dir>/pack/`. It writes each file once. `eval run` without `--ab` does not read this folder, because a JSON file in a subfolder is not an eval ([docs/evals.md](../evals.md)).
- `spec-dna eval run --ab [<skill>|all]` reads `<[evals] dir>/pack/`, checks each file with the rules of SD506 (an invalid file gives exit code 3), runs the 2 arms and writes `<[evals] dir>/results/skills-<date>.json`.
- `spec-dna eval verdict` prints the verdict of each skill, or `unmeasured`. It reads the newest project result file, and for a skill with no result there it uses the table of the release, which the binary holds. It never starts an agent.
- SD507 `skill-unproven` reports a skill that `[harness] skills` enables when the project result and the table of the release give it no verdict `on`. It is off in `lite` and `standard`, and a warning in `strict`. A skill that is on in D2 is exempt.

### D36. The limits of the plan

One model family runs the agents, as in the earlier sessions. A result is valid for the model and the Claude Code version that the file records. A new model needs a new run. No result is a proof for another project. The `without` arm cannot remove what the model learned in training. The pack has no arm with another plugin installed (D5).
