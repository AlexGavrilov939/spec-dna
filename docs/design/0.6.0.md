# Design of spec-dna 0.6.0

Status: accepted, 2026-11-14. The owner answered the open points ([Owner answers](#owner-answers)). This page is a design only. It adds no code. The decisions are in [ADR 0005](../adr/0005-layout-and-layers.md), [ADR 0006](../adr/0006-change-lifecycle.md), [ADR 0007](../adr/0007-templates-and-document-mapping.md), [ADR 0008](../adr/0008-harness-and-evals.md) and [ADR 0009](../adr/0009-upgrade-from-0-5.md). Each ADR has its own status. Each ADR states its rejected options. This page holds the tables.

## Goal

0.6.0 gives a project one small layout of documents and one lifecycle for a change. A person or an agent can find the current truth in one place. A change leaves no extra documents after it ends.

The evidence of earlier versions is outside this repository. It gives these facts:

- The gate against the base gave the measured gain. Retrieval and a split of big documents did not.
- Agents search the repository. They seldom navigate a link tree.
- Big files and process documents in the text that every task loads cost tokens and give no gain.

Thus 0.6.0 keeps the gate. It makes the text that every task loads small. It moves the documents of a change into one folder that `finish` deletes.

## Terminology

Each term has one meaning. A source is a section of the [playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook), a page of the Claude Code documentation, or "plain STE word". The playbook has no definition of a change class, a requirement, a rule or a layer. For these, the term is a plain word.

The author checked each source against the text of its page on 2026-11-14. Where the playbook or the documentation names nothing, this table says so.

## Document model

### Types

0.6.0 has 15 document types. The type of a document comes from the front matter, or from its place (see [Place gives the type](#place-gives-the-type)).

| Type | Layer | Place | Statuses | Required sections | Budget (soft, hard) |
| --- | --- | --- | --- | --- | --- |
| `product` | foundation | `docs/product.md` | none | none | 8,000, 16,000 |
| `system` | foundation | `docs/system.md` | none | none | 8,000, 16,000 |
| `terms` | foundation | `docs/terms.md` | none | none | 10,000, 20,000 |
| `roadmap` | pending | `docs/roadmap.md` | none | none | 8,000, 16,000 |
| `questions` | pending | `docs/questions.md` | none | none | 8,000, 16,000 |
| `rule` | rules | `docs/rules/` | draft, active, deprecated, superseded, retired | `Rules` | 3,000, 6,000 |
| `requirements` | requirements | `docs/requirements/<area>/` | as `rule` | none | 10,000, 20,000 |
| `interface` | interfaces | `docs/interfaces/` | as `rule` | none | 10,000, 20,000 |
| `decision` | decisions | `docs/decisions/` | proposed, accepted, superseded, rejected | `Decision Outcome` or `Decision` | 7,000, 14,000 |
| `procedure` | procedures | `docs/procedures/` | as `rule` | none | 14,000, 28,000 |
| `incident` | incidents | `docs/incidents/` | none | `Summary` and `Root cause` | 6,000, 12,000 |
| `research` | research | `docs/research/` | none | none | none |
| `intent` | intent | `docs/intent/<slug>/intent.md` | draft, accepted, closed | `Intent`, `Problem` or `Summary` | 6,000, 12,000 |
| `spec` | intent | `docs/intent/<slug>/spec.md` | draft, approved | `Delta` | 10,000, 20,000 |
| `plan` | intent | `docs/intent/<slug>/plan.md` | draft, approved | `Files` | 6,000, 12,000 |

Notes:

- `requirements` is a plural by design. A `requirements` document holds a set of requirements for one capability. A requirement is one list item with a key. The name `spec` is not available, because `spec.md` means the spec of one change. The name `requirement` would name both the document and the list item.
- `terms` has a table of terms, with the columns term, meaning and forbidden synonyms. [SD904](#checks) reads it.
- The type `procedure` replaces `guide` and `runbook`. The runbook form is a template, not a type ([Templates](#templates)).
- The types `change` and `note` end. `intent` replaces `change`. `research` replaces `note` and `reference`.
- A requirement keeps its form: a list item with a bold slug key. Requirements are in the types `requirements`, `interface` and `rule`. A `spec` document has delta lines, not requirements.

### Place gives the type

In a root, a document under a layer folder takes the type of that layer, if the layer has one type. In the `intent` layer, the file name gives the type: `intent.md`, `spec.md` or `plan.md`. A top file gives its type by its name (`terms.md` has the type `terms`). Front matter `type` overrides the place only in a root with `type = "mixed"`.

This rule extends `default-type` of [config.md](../config.md). It makes `type:` optional in a new corpus. The types `intent`, `spec` and `plan` are valid only in the `intent` layer. A document of the type `spec` anywhere else gives SD303. The message says that the 0.5 name of its type was `requirements`.

A mixed root has no default for `default-type` in a new corpus. In such a root, a document outside every layer place and with no `type` gives SD303. `upgrade` writes `default-type = "research"` for a root that had the 0.5 default `note`.

### Names and aliases

0.6.0 renames all names in one release and keeps no runtime alias. The table says which names get an alias and which do not.

| Name | Alias in 0.6.0 | How an old name ends |
| --- | --- | --- |
| A document id that a move changed | Yes: `upgrade` or `mv` writes `aliases` in the front matter | The old id resolves. SD202 stays silent |
| A decision id of the form `ADR-NNN` | Yes: `legacy-ids` of the root | The pattern gives the alias, as in 0.5 |
| A requirement key | Not renamed | Keys do not change |
| A status word | No | `upgrade` rewrites it. A file with an old status gives SD304 |
| A document type in a front matter | No | `upgrade` rewrites it. A file with an old type gives SD303, and the message names the new type |
| A configuration key or a type name in `spec-dna.toml` | No | An old key is an error (exit code 3) that names the new key |
| A folder name | No | `upgrade` moves each change into an intent folder. `upgrade --layout` moves the other folders. Both use `git mv` and write document aliases |
| A command | No | An old command is an error that names the new command, for example `new change` gives "use `new intent`" |
| A harness role or an agent file | No | `upgrade` removes an unedited generated file and writes the new one |
| A code number | Never changes | A code name can change (SD405 is now `decision-locked`, SD611 is now `decision-links-intent`). The `--json` field `name` changes with it. `--json` consumers must read `code` |

Thus "no runtime alias" means that the binary accepts no old name as input. It uses an old name in 3 cases only. These cases are the hint of an error, the run of `upgrade`, and the SD202 exemption of a document that `upgrade` marked.

A document alias is data in a file, which the id model already reads. `upgrade` never renames the file stem of a decision, so `legacy-ids` patterns such as `ADR-{n}` still resolve. A change gets the stem `intent` when it moves into its folder. When a move changes an id, `upgrade` writes the old id and each old legacy alias into `aliases`.

### Areas and groups

An area is a folder under `requirements/`. `init` proposes the areas ([Init questions](#init-questions)). The configuration lists them in `areas`. A group is a named set of areas:

```toml
areas = ["valves", "sensors", "reports"]

[groups]
operations = ["valves", "sensors"]
reporting = ["reports"]
```

A project has no group by default. A group is a view: `status --group <name>`, `context --group <name>` and `stats --group <name>` read it. A group never makes a folder, an id or a requirement key.

## Layer graph

### Definition

A layer is a named set of documents. A layer chooses its documents by type, by top file or by path. The configuration gives each layer these keys.

| Key | Meaning | Default |
| --- | --- | --- |
| `types` | The document types of the layer. A type is in at most one layer. A document of a type that no layer has gives SD303 with a hint to run `layer add` | `[]` |
| `dir` | The folder of the layer, relative to the root. `spec-dna new` writes here | `<layer name>` |
| `files` | Top files of the layer, relative to the root, for example `["terms.md"]`. A layer with `files` has no `dir` | `[]` |
| `paths` | Globs, relative to the root. A document that matches belongs to this layer, also when its type is in another layer. The first layer in the file that matches wins. This is how a project adds a custom layer | `[]` |
| `moves-to` | The layers that the text of this layer matures into | `[]` |
| `linked-from` | Layers that can link to this layer, although they are more stable than it | `[]` |
| `keep` | `forever` or `until-finished` | `forever` |
| `context` | `always` or `on-request` | `always` |
| `max-docs` | The most documents in the layer | none |
| `max-chars` | The most body characters in the layer | none |
| `max-started` | `intent` layer: the most started changes | none |
| `stale-days` | `intent` layer: days without a commit before a change is stale | none |

- `keep = "forever"`: a document stays. SD202 reports a deleted document that keeps no alias. A status can end a document (`superseded`, `retired`). An author can edit it, unless its type locks text (a decision).
- `keep = "until-finished"`: a deleted document gives no SD202. In the `intent` layer, `finish` deletes the folder of the change. The limits `max-started` and `stale-days` apply. Another layer with this value gets the SD202 exemption and the limits `max-docs` and `max-chars`. It has no `finish` command and no SD911 or SD912. These 2 codes are for changes.
- `context = "always"`: the layer can fill the plan of `context` without a named target. The type behavior of 0.5 stays (for example a decision as a summary of a linked decision). The order of the layers replaces the type order.
- `context = "on-request"`: `context` serves the documents of the layer only when the target names them, or when `show` reads them. The plan counts them in one line and lists no file.

### Levels

The graph must have no cycle. A cycle is a configuration error (exit code 3). The level of a layer is the number of edges on its longest `moves-to` path to a layer with no edge out.

A layer with no edge in or out has level 0, so it is a stable layer. Level 0 is the most stable. The levels follow from the graph. The file has no level key.

- Context order from the top: `context` lists the layers by level, from 0 up. Layers of one level keep the order of the configuration. This replaces the type order of 0.5, in which a rule came first. In the default graph, `foundation` comes before `rules`. This is a change of behavior. The CHANGELOG records it.
- A layer X is more stable than a layer Y if X is reachable from Y by `moves-to` edges.

### Default graph

`init` writes this graph for a project of the size `default`. The graph gives the row "level". It is not a key.

| Layer | Types | `moves-to` | `linked-from` | `keep` | `context` | Limits | Level |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `foundation` | `product`, `system`, `terms` (`files`) | none | none | `forever` | `always` | `max-chars = 30000` | 0 |
| `rules` | `rule` | none | none | `forever` | `always` | `max-docs = 30` | 0 |
| `requirements` | `requirements` | none | none | `forever` | `always` | none | 0 |
| `interfaces` | `interface` | none | none | `forever` | `always` | none | 0 |
| `decisions` | `decision` | none | none | `forever` | `always` | none | 0 |
| `procedures` | `procedure` | none | none | `forever` | `always` | none | 0 |
| `research` | `research` | `decisions`, `requirements` | `decisions`, `requirements` | `forever` | `on-request` | none | 1 |
| `intent` | `intent`, `spec`, `plan` | `requirements`, `interfaces`, `rules`, `decisions`, `procedures` | none | `until-finished` | `on-request` | `max-docs = 30`, `max-started = 3`, `stale-days = 14` | 1 |
| `incidents` | `incident` | `intent` | `rules`, `procedures`, `decisions`, `requirements`, `interfaces`, `intent` | `forever` | `on-request` | none | 2 |
| `pending` | `roadmap`, `questions` (`files`) | `intent`, `decisions` | `intent` | `forever` | `on-request` | `max-docs = 2` | 2 |

A layer at level 0 needs no `linked-from`, because no layer is more stable than it. `research` and `incidents` keep `linked-from` entries, because a decision, a rule or a procedure names its source.

`init` proposes a graph by project size:

| Size | Test | Layers |
| --- | --- | --- |
| small | fewer than 30 documents, also in a new project | `foundation`, `pending`, `rules`, `requirements`, `decisions`, `intent`, `incidents`. `intent` moves to `rules`, `requirements` and `decisions`. `pending` and `incidents` move to `intent` |
| default | 30 documents or more | the default graph: the small graph and `interfaces`, `procedures` and `research` |

A `moves-to` entry names only a layer that the graph has. `spec-dna layer add` adds a layer later.

`init` proposes areas at every size, when it detects 2 or more. `init` never proposes a group. A project adds it on request. The size only decides which layers `init` writes. `layer add` adds the others later.

### Derived checks

These checks come from the graph:

- SD901 (link direction).
- SD902 (limits).
- SD911 and SD912 (staleness and started changes, from the `keep` and limit keys).
- The target rule of SD914 (the `moves-to` edges of the `intent` layer).
- SD915 (finishing: the delta of a deleted intent folder is in the tree).
- The order of `context`.

[Checks](#checks) gives the table.

SD901 reports an explicit reference from a document of a layer X to a document of a layer Y. It reports it when X is more stable than Y, unless Y lists X in `linked-from`. An explicit reference is a Markdown link, a `[[id]]` or a front matter id field, such as `depends-on`, `supersedes` or `from`. A locked decision that links an intent gives SD611, not SD901.

| `roots.required-sections` | Keys are the 0.6 types. The default of `rule` is `Rules`. The default of `incident` is `Summary` and `Root cause`. The default of `intent` is `Intent`, `Problem` or `Summary`. The default of `spec` is `Delta`. The default of `plan` is `Files` |
| `roots.live-sections` | The default is `{ decision = ["Status"] }` |
| `[budgets.<type>]` | Keys are the 0.6 types. The defaults are in the type table |
| `[layers.<name>]`, `areas`, `[groups]`, `[change]`, `[templates]`, `[evals]` | New |
| `language` | New. The default is `en`. A value other than `en` disables SD801 to SD805 and SD904 for the root, because the word lists are English |
| `[harness]` | New keys `skills`, `review-md` and `protect-tests`. The key `skills` decides which skills spec-dna writes. `init` proposes its value from `[change] policy` |
| `[lint] history-terms` | New. The phrases that SD903 reports |
| `[harness.roles]` | The role `reviewer` is now `verifier`. The role `spec-writer` ends. The role `code-simplifier` is new (level `full`). The role `implementer` stays |
| `[conventions]` | Keys are the 0.6 types |

A project with no `[layers]` table gets the default graph for its types. `init` writes a layer of `high-risk-layers` only if the graph has it. A project with no `[change]` table gets `policy = "none"`, so an upgrade adds no new gate. `init` writes `[change]` for a new project. A project with no `[evals]` table has no evals, and `upgrade` writes none. `init` writes `[evals]` for a new project, unless the harness level or the answer to question 14 is `none`.

## Change lifecycle

### Artifacts

A change is a folder `docs/intent/<slug>/`. The slug is the name of the change.

| File | Type | Status | Content |
| --- | --- | --- | --- |
| `intent.md` | `intent` | `draft`, `accepted`, `closed` | What the originator wants and why. Front matter: `class: routine` or `class: higher-risk`. Optional `areas` and `from` (an incident id) |
| `spec.md` | `spec` | `draft`, `approved` | The `Delta`, `Interfaces`, `Decisions` and `Concerns` sections |
| `plan.md` | `plan` | `draft`, `approved` | `Files`, `Order`, `Risks` and `Proof` |

The id of the 3 files is `intent/<slug>/intent`, `intent/<slug>/spec` and `intent/<slug>/plan`. The commands `next`, `status` and `finish` take the slug. `closed` means that the change does not proceed: the owner did not accept it, or the team ended it. A status only moves forward: `draft` to `accepted` or `closed`, `accepted` to `closed`, and `draft` to `approved`. SD401 checks this. A started change is a change with the status `accepted`.

The author can edit the text of an approved spec or plan. When the work differs from the plan, the author updates `plan.md` in the same commit as the work, as the playbook says. The author can do this in the code commits before `finish`. The pull request of `finish` reads the plan from the base tree, so it needs no plan edit. The status stays `approved`.

### The spec

`spec.md` has these sections:

- `Delta`: a list. Each item starts with a verb and is not a requirement, because it has no bold key.

  ```md
  - ADD requirements/valves/closing#sensor-timeout: When a moisture sensor times out, the controller SHALL close the valve of its bed.
  - CHANGE requirements/valves/closing#flush-time@3f2a9c1b7e0d4a11: The controller SHALL flush a valve line for 30 seconds before it closes the valve.
  - REMOVE requirements/valves/closing#manual-override@91c0aa5d2e7b4f08
  ```

  `ADD` names a document and a new key. `finish` appends the list item at the end of the last list of requirements in that document. If the document does not exist, `finish` writes it from the template.

  `CHANGE` and `REMOVE` name a requirement that exists and its hash, which is the hash of ADR 0001 (first 16 hexadecimal digits). The hash identifies the text that the author read. The target must be a document of a type that holds requirements (`requirements`, `interface` or `rule`). Its layer must be in the `moves-to` list of the `intent` layer. A change to a decision or a procedure uses the `Decisions` section or the plan.
- `Interfaces`: a list of `CHANGE <interface id>: <text>`. The pull request that runs `finish` must change the interface document, or one file that it cites.
- `Decisions`: a list of links `[[decisions/<slug>]]`. Each decision must exist when the spec is approved. Each must be `accepted` when `finish` runs.
- `Concerns`: a task list. `- [ ]` is an open concern. `- [x]` is a resolved concern and ends with its resolution. A spec with an open concern cannot be `approved` (SD919).

A `covers:` tag in a test can name an `ADD` requirement before `finish` writes it. SD105 does not report a tag whose target is an `ADD` line of an `accepted` change in the tree.

### The plan

`plan.md` has these sections:

- `Files`: a list. Each item has a path or a glob, in a code span or as a plain path (a token with no white space that has a `/`, a `.` or a `*`). The `Files:` paths of the tasks of `Order` are patterns of the plan too, so each reader of the plan sees both lists. This list is the scope of the change (SD913).
- `Order`: the steps, in order.
- `Risks`: what can go wrong, and what limits it.
- `Proof`: the tests, with the `covers:` ids, and the commands that show the result.

### Stage derivation

A change has no stage field. The stage comes from the files, their statuses and git. `status` and `next` read the head tree, the base tree and git. The stage is the first row of this table that matches, from the top.

| Stage | The change is in this stage when |
| --- | --- |
| Closed | `intent.md` is `closed`. The next step is `finish`, which deletes the folder |
| Plan | `intent.md` is `draft` |
| Design | The class is `higher-risk`, and `spec.md` is absent or `draft` |
| Build | `plan.md` is absent or `draft`, or no file of `Files` has changed against the base |
| Test | At least one requirement that the diff adds or changes has no evidence. For a `higher-risk` change, these are the `ADD` and `CHANGE` lines of the delta. For a `routine` change, these are the requirements whose hash differs from the base |
| Deploy | Each such requirement has evidence, and the intent folder still exists |
| Maintain | An `incident` has an open item (`- [ ]`) in its `Follow-ups` section. `status` lists it as an open follow-up. The incident gets its own intent with `from:`. The author checks the item (`- [x]`) when the follow-up is complete |

A change that the default branch has finished is no longer in the tree. `log` lists it ([Log and history](#log-and-history)). A `small-fix` has no folder, so it has no stage. The playbook rule is that a stage ends with a commit of an artifact. Thus each approval of a stage is a commit.

A `routine` change has no delta. Its author edits the requirements in the same pull request as the code. `finish` then checks the evidence of each requirement whose hash differs from the base.

### Change classes

| Class | Artifacts | Plan approved by |
| --- | --- | --- |
| `small-fix` | none: a pull request only | not applicable |
| `routine` | `intent.md`, `plan.md` | the agent |
| `higher-risk` | `intent.md`, `spec.md`, `plan.md` | the owner |

`[change] policy` sets the classes that a project uses.

| Policy | Classes | Default |
| --- | --- | --- |
| `three-class` | `small-fix`, `routine`, `higher-risk` | yes, for a new project |
| `two-class` | `routine`, `higher-risk`: each change has an intent. This is a team rule. SD921 reports one kind of break of it: a changed requirement with no intent folder. The skills and `CLAUDE.md` do not mention `small-fix` | |
| `none` | no change process: layers and checks of the graph only. SD905 and SD910 to SD921 are off. SD911 and SD912 are off too | for an upgraded project |

The minimum class comes from the delta and the diff. A change is `higher-risk` at least in these cases:

- A delta line targets a document of a layer in `[change] high-risk-layers` (default `interfaces`, `rules`). A `routine` change has no delta. For it, the test is that the diff changes the hash of a requirement in such a layer.
- The plan or the diff has a path that matches a glob of `[change] high-risk-paths` (globs from the repository root, default none).

An intent with a lower `class` gives SD917. A `small-fix` has no intent. SD917 applies to it only when its diff matches `high-risk-paths`, or changes the hash of a requirement in a layer of `high-risk-layers`.

spec-dna does not know who approves. It records each status change in git. The branch protection of the repository enforces who may merge. The agent approves a routine plan with its own commit. The merge records the approval.

The owner approves a higher-risk plan by a review of the pull request that merges the approval. `init` can print a `CODEOWNERS` line for `docs/intent/*/spec.md`, because only a higher-risk change has a spec. A path rule cannot select a higher-risk plan, so the repository process must require the owner for it. Open point 2 settles this: the repository uses branch protection, and `init` prints the `CODEOWNERS` line but does not write the file.

### Approval and merge

- To approve is to change a `status` in a commit. A pull request merges the commit.
- "Merged" means: the base tree has the status. The base tree is the merge base of the pull request with the default branch. An approval in the pull request itself does not count. spec-dna uses no network and no API of a code host.
- A gate reads the base tree. The pull request that adds `spec.md` needs `intent.md` to be `accepted` in the base tree.
- The review findings of a pull request are outside the repository. spec-dna does not check them. The generated `REVIEW.md` and the review skill give them a policy. The approval of a pull request is branch protection.

### Gates

`[change] gate` sets the strictness. If `[change]` is absent, `policy` is `none` and no gate runs. If `[change]` is present and `gate` is absent, SD910 takes the severity of the profile column (`lite`: warning, `standard` and `strict`: error). `init` always writes `gate`.

| Value | Effect |
| --- | --- |
| `block` | SD910 is an error. A change that adds or edits an artifact of a stage needs the base tree to show approval of the artifact before it |
| `warn` | SD910 is a warning |
| `off` | SD910 is off |

The order of artifacts is `intent.md`, then `spec.md` (for `higher-risk`), then `plan.md`, then code. Code is a changed file that no layer owns. A change is an intent folder that the diff touches. A diff that touches 2 intent folders is 2 changes.

SD910 also reports a diff that touches a path of `Files` in the plan of an in-tree change. It reports it if that plan is not `approved` in the base tree. A diff that touches no intent folder and no `Files` path is a `small-fix`, so SD910 does not apply to it.

SD921 reports a diff that changes the truth without a change. Its severity comes from the profile. A `small-fix` that matches `high-risk-paths` gives SD917. `[rules]` can override SD910 and SD921, as it overrides each code.

Each check reads the artifacts of a change from the head tree. If the diff deletes the folder, the check reads them from the base tree. Thus an edit of a spec or a plan in the pull request of `finish` has no effect on its checks. A correction of a delta or of `Files` goes in its own pull request before `finish`. The status stays `approved`.

The scope of SD913 always has the intent folder and the documents that the delta names. For a `routine` change, a requirement document is in scope only if `Files` lists it. The plan is the only approved text that names the truth that the change edits.

Without `--base`, the lifecycle checks and the commands `status`, `next` and `finish` use the merge base with the default branch that `origin/HEAD` names. If git cannot name it, they print a note that they cannot decide SD910 locally.

### Finish

`spec-dna finish <slug>` works in the working tree. It does these steps and stops at the first failure:

0. Check that no document outside the intent folder links into it. Such a link would break when `finish` deletes the folder (SD101 for an id, SD102 for a Markdown link). `finish` lists each link in unlocked text. Then it stops. A reference in the locked text of a decision does not stop `finish`. SD101 does not report it, because that text cannot change (SD611 already warned).
1. Check that the intent is `accepted`, the plan is `approved`, and (for `higher-risk`) the spec is `approved`.
2. Check each concern (SD919) and each needed decision (SD920).
3. Check each `CHANGE` and `REMOVE` hash against the requirement text of the head tree (SD914). Check that each interface document of `Interfaces`, or a file that it cites, changed in the diff (SD914).
4. Apply the delta: `ADD` appends a list item, `CHANGE` replaces the sentence, `REMOVE` deletes the list item. If the document does not exist, `finish` writes a minimal new document. It has the front matter with the status `active`, the H1, a `Requirements` section and the `ADD` items. It has no placeholder.

    The new document has a `type: requirements` line when the place of the file does not give the type. If a root requires more sections of `requirements`, the new document gets SD305. The author adds them.
5. Check the evidence of each requirement that the delta adds or changes (SD916). For a `routine` change, check each requirement whose hash differs from the base.
6. Delete the intent folder.

`--dry-run` prints the diff and writes nothing. `finish` does not commit. The author commits the result in the same pull request as the code. For an intent with the status `closed`, `finish` checks only that status (step 1) and deletes the folder.

To drop a started change, a pull request first sets `closed`. A later pull request runs `finish`. A pull request that deletes a folder with an unapplied delta and a base status other than `closed` gives SD915.

`finish` is the one command that deletes documents. This amends the sentence in ADR 0001 that spec-dna never deletes a document. The deletion covers only the intent folder, and only after the checks. Git is the archive.

`check` verifies the result in the pull request of `finish` and after the merge. SD915 reports a deleted intent folder whose delta is not in the head tree. It reads the delta from the base tree.

A pull request that holds the intent, the approval and the code together is possible. With `gate = "warn"` or `"off"`, it passes. With a squash merge, the default branch then never holds the intent folder. Thus `log` has no entry for that change. If the intent was `draft` in the parent tree, `log` reports the change as closed.

### Log and history

The intent folder is on the default branch from its Plan or Design pull request. The pull request of the code deletes it. Thus the default branch has the folder in its history, even with squash merges, if the folder came in an earlier pull request.

`spec-dna log` reads each commit that deleted an `intent.md`. It counts a change as finished when the parent tree has the status `accepted`. A change with any other status in the parent tree is closed. It prints the slug, the class, the title, the counts of the delta, the commit and its date.

### Incidents

A new `incident` document needs an eval. SD918 reads the diff: it warns if the change that adds the incident adds or edits no file in `[evals] dir`. It applies only when `[evals]` is in the configuration and `[change] policy` is not `none`. It is off in the profile `lite`. A new project with the default answers meets these conditions, so SD918 warns about each new incident that comes with no eval. An upgraded project has no `[evals]`. A lesson moves into `procedures/` or `rules/` by an intent with `from:` that names the incident. An incident never links the folder of a finished change, because `finish` deletes it. It links the requirement, the decision or the procedure that came from the change.

## Checks

A new check has a code in a free range: SD9xx for layers and changes, SD506 for evals. A code keeps its meaning, and spec-dna never reuses a retired code. [diagnostics.md](../diagnostics.md) gives the 0.5 codes. A profile column gives the default severity. `rules` can change it.

ADR 0003 says that a new rule starts as a warning in a minor release. The codes SD901 to SD904 apply to every project, so they are warnings at most. The codes SD506, SD905 and SD910 to SD921 apply only to a project that has `[evals]`, or `[change]` with a policy other than `none`. They follow the precedent of ADR 0004. They can be errors from the start, as the table shows, because no older configuration has these tables. `upgrade` writes no `[evals]` and writes `policy = "none"`, so no current corpus gets these codes. SD911 and SD912 also need a policy, so the same precedent covers them. `init` writes `[evals]` and a policy for a new project (questions 4 and 14), as ADR 0004 writes `[harness]` for a new project. Thus a new project gets these codes from the start.

| Code | Name | Meaning | lite | standard | strict |
| --- | --- | --- | --- | --- | --- |
| SD506 | evals-invalid | A `*.json` file directly in `[evals] dir` is not a valid eval, or an eval names no check, or its fixture is absent, or `<dir>/check.sh` is absent. SD506 does not read the text of `check.sh` or of a fixture, or a file in a subfolder | error | error | error |
| SD901 | link-direction | A document links a document of a less stable layer, and the layer does not list it in `linked-from` | off | warning | warning |
| SD902 | layer-limit | A layer has more documents than `max-docs`, or more body characters than `max-chars` | off | warning | warning |
| SD903 | history-in-requirements | A requirement sentence has a calendar date, `round <n>` or `iteration <n>`, or a phrase of `[lint] history-terms` (default: "previously", "formerly", "no longer", "used to", "was changed", "before this change", "after this change"). A duration such as "30 days" is not a date | off | warning | warning |
| SD904 | term-forbidden | A normative sentence uses a forbidden synonym of `terms.md` | off | warning | warning |
| SD905 | fan-out | One change touches more requirement documents than `[change] max-fanout`: the documents of its delta, or for a `routine` change the documents of the diff. Split the change | off | warning | warning |
| SD910 | gate-approval-missing | An artifact of a stage changes while the base tree has no approval of the artifact of the stage before. Code under the `Files` of an unapproved plan counts as an artifact | warning | error | error |
| SD911 | change-stale | A started change has had no commit for `stale-days` days. The check compares the committer dates of the base commit and of the newest commit that touched the folder or a `Files` path. The result needs no clock. It depends on the commits that the checkout has. A shallow clone can hide a stale change, but it never reports a false stale change | off | warning | warning |
| SD912 | started-limit | More changes than `max-started` have an `accepted` intent | off | warning | error |
| SD913 | outside-plan | The diff of a change touches a file that no item of `Files` matches. The intent folder and the documents of the delta are always in scope | off | warning | warning |
| SD914 | delta-invalid | A delta line has an invalid form, names an absent target, targets a layer that `moves-to` does not allow, or has a hash that does not match the requirement. SD914 also reports an interface that `Interfaces` names and that did not change. `check` reports SD914 as an error for a spec that the diff touches, and as a warning for another spec. `finish` always stops on it | warning | error | error |
| SD915 | finish-incomplete | The diff deletes an intent folder whose base status is not `closed`, and one of these holds. The head hash of a delta target is not the hash of the delta sentence of the base (a `REMOVE` target must be absent). Or, for a `routine` change, which has no delta, the diff changes no `Files` path and no requirement hash | warning | error | error |
| SD916 | delta-evidence-missing | An `ADD` or `CHANGE` requirement has no `covers:` tag and no `verified-by` when `finish` runs, or when the diff deletes the intent folder | warning | error | error |
| SD917 | class-too-low | The `class` of an intent is lower than the minimum that the diff gives | off | warning | error |
| SD918 | incident-eval-missing | A change adds an incident and no file in `[evals] dir` | off | warning | warning |
| SD919 | concern-open | A spec is `approved` with an open concern | warning | error | error |
| SD920 | decision-needed-unaccepted | A decision that the spec needs is absent, or is not `accepted` when `finish` runs | warning | error | error |
| SD921 | truth-changed-without-change | The diff touches no intent folder, and a requirement hash of `rules`, `requirements` or `interfaces` differs between the base and the head, or the diff adds or removes a key. The check applies aliases. A move keeps the hash. | off | warning | error |

Notes:

- SD910 follows `[change] gate`. The columns are the defaults when `[change]` is present and `gate` is absent. `init` writes `gate`. With `policy = "none"`, SD905 and SD910 to SD921 are off.
- SD911 never reads the clock. It compares the committer dates of the base commit and of the newest commit that touched the folder or a `Files` path. A repository with no new commit has no stale change.
- SD921 compares requirement hashes directly. A move or a split with `spec-dna mv` keeps the hashes, so it gives no SD921. A split by hand with no alias gives 2 SD921 (an added key and a removed key).
- The new codes have 2 new rule groups for `[rules]` and the profiles: `layers` (SD901 to SD904) and `changes` (SD905 and SD910 to SD921). The word `rules` still names the severity table of the file. A layer named `rules` is not the severity table. The key path shows which one: `[rules]` or `[layers.rules]`.
- This design renames SD405 to `decision-locked`. It renames SD611 to `decision-links-intent`. SD202 gives no error for a deleted document of a layer with `keep = "until-finished"`.
- SD303 names the new type when a file has a 0.5 type. SD305 applies to the new required sections.
- SD501, SD502 and SD504 apply to the new generated files: `REVIEW.md`, the stage skills and the renamed agent files ([ADR 0008](../adr/0008-harness-and-evals.md)).
- SD503 does not apply when the pin of the base is before 0.6.0 ([ADR 0009](../adr/0009-upgrade-from-0-5.md)). A later pin change keeps SD503.
- SD609 links: an incident links a requirement, a rule, a decision or a procedure.
- The starter files of `skeleton` pass SD506. `check` on the result of `init --non-interactive` in an empty repository exits with code 0 and gives no SD506.

## Templates

`spec-dna new` writes a template. spec-dna embeds the templates below. A project can add its own in `[templates] dir`. A file there with the name of an embedded template replaces it. `new <type> <id> --template <name>` selects a template.

The `Status` section of a decision is a live section: its text can change after the outcome is locked. It comes before `Amendments`, because an amendment goes at the end of the file and must not be inside the live section. `new` sets the first status of the type. It writes the H1 from the id. It removes `was-type` from the copy.

The template `madr` is the default template of `decision`. A file `madr.md` in `[templates] dir` replaces it. A template of a project names its `type` in its front matter. `new` stops with exit code 2 for an unknown template name or a template of another type.

`[templates] dir` is outside every root, or the root excludes it. `init` writes that `exclude` for a root `.`. A violation gives exit code 3. The `prd` and `rfc` templates satisfy the required section of an `intent` because each has a `Problem` or `Summary` heading.

### Stage skills

Each skill is a folder `.claude/skills/<name>/SKILL.md`. spec-dna generates all of it, with the harness marker. Skills: <https://code.claude.com/docs/en/skills.md>.

| Skill | Stage | What it does |
| --- | --- | --- |
| `spec-dna-intent` | Plan | Writes `intent.md` from a request, then runs `spec-dna next` |
| `spec-dna-spec` | Design | Writes `spec.md`: the delta with hashes from `spec-dna show`, the interfaces, the decisions and the concerns |
| `spec-dna-plan` | Build | Writes `plan.md` in plan mode: the files, the order, the risks and the proof |
| `spec-dna-review` | Deploy | Reviews the diff against `spec.md` and `plan.md`, with the passes and severities of `REVIEW.md` |

A description costs tokens in each request, so each has a short `description`. The key `[harness] skills` decides which skills spec-dna writes. `init` proposes its value from `[change] policy`. The test plan measures the cost.

### `REVIEW.md`

spec-dna generates `REVIEW.md` at the root with the harness marker as its last line. Its text follows the playbook:

- 3 passes: Bugs, Security and Compliance. Compliance compares the change with `spec.md`, `plan.md` and the documents of `rules/`, because project policy is in `rules/`.
- Severities: Important and Nit. Important is for a finding that breaks behavior, leaks data or breaches a policy.
- At most 5 Nits per review.
- A `Do not report` list that names the findings of `spec-dna check` and the generated files.

The Code Review service reads `REVIEW.md` from the base branch or the default branch, and the repository must protect that branch. The local `/code-review` command does not read it: <https://code.claude.com/docs/en/code-review-customize.md>. Thus the review skill has the same passes for local use. The `finish` pull request deletes `spec.md` and `plan.md`. The deleted text is in its diff, so the Compliance pass can read it.

### Protect tests during a fix

`spec-dna hook protect-tests` runs on `PreToolUse` for `Edit|Write` (<https://code.claude.com/docs/en/hooks.md>). It reads the event from stdin and never fails. It asks the person before an edit of a test file that git tracks, when the branch starts with `fix/`. It returns `permissionDecision: "ask"` with a reason. A new test file does not trigger it.

In a headless run, Claude Code denies a call that needs approval. The Claude Code documentation does not say whether an allow rule for `Edit` has priority over a hook `ask`. A probe on a scratch repository must decide this before the build. The check `tests_unchanged` of an eval proves the result in both cases.

The generated command contains the test globs of `[evidence] tests`. The hook runs `git` only for a path that matches a test glob. The hook reads no configuration, as the 0.5 hooks do. `protect-tests = "always"` removes the branch test. `"off"` writes no hook. An empty `[evidence] tests` list writes no hook.

## Evals

[ADR 0008](../adr/0008-harness-and-evals.md) records the decisions. This section gives the form.

### An eval file

```json
{
  "id": "fix-keeps-tests",
  "task": "Fix the failing renew test by changing the code, not the test.",
  "fixture": "evals/fixtures/renew",
  "branch": "fix/renew",
  "allowed-tools": ["Read", "Edit", "Bash(cargo test*)"],
  "max-turns": 20,
  "max-budget-usd": 2,
  "runs": 3,
  "pass-at": 2,
  "checks": [
    { "name": "tests-unchanged", "run": "tests_unchanged" },
    { "name": "tests-pass", "run": "cargo test --quiet" }
  ]
}
```

`<dir>/check.sh` (`[evals] dir`, default `evals`) is a file of the project. It defines the shell functions that the checks call, such as `tests_unchanged` and `spec_dna_clean`. The runner sources the copy of the project, never the copy in the temporary directory, so the agent cannot change its own checks. `init` writes a starter once and never again. `branch` is optional: the runner starts the work on that branch, so a `fix/` branch can trigger `protect-tests`. `max-budget-usd` is required.

The form above is for a Rust project. The starter of `skeleton` needs no build tool, so it works in any stack. Its example eval has a fixture of one text file in `<dir>/fixtures/example/`, a task that edits that file, and one check that calls a function of `check.sh`. It has `"runs": 1`, `"pass-at": 1` and `"max-budget-usd": 1`. Git keeps no empty folder, so the fixture holds the file. No starter file is Markdown. For a root `.`, `init` writes an `exclude` for `[evals] dir`, as it does for `[templates] dir`, because a later fixture can hold Markdown files.

### The runner

`spec-dna eval run` does these steps for each eval and each run:

1. Copy the fixture and the harness files of the project into a new temporary directory. The harness files are `CLAUDE.md`, `AGENTS.md`, `REVIEW.md` and `.claude/`, but not `.claude/settings.local.json`. Start a git repository in it. Commit this state as the base with a fixed author and no signature. Switch to `branch` if the eval has one.
2. Start `claude -p "<task>" --allowedTools "<tools>" --output-format json --max-turns <n> --max-budget-usd <usd> --permission-mode dontAsk`. The runner does not pass `--bare`, because an eval must load `CLAUDE.md`, the skills and the hooks. `--bare` skips them (<https://code.claude.com/docs/en/headless.md>).
3. Read the exit status of the process. Read `total_cost_usd` from the JSON result. The cost is an estimate of the client.
4. Source `check.sh` of the project. Then run each check with `sh -c` in the directory. A check passes on exit code 0. A run passes only when `claude` exits with code 0 and each check passes.
5. Delete the directory.

An eval passes when at least `pass-at` of its `runs` pass. The suite passes when the share of evals that pass is at least `min-pass-rate`. The command prints a table. It exits with code 1 when the suite fails. Exit code 3 means a configuration error or a refusal by the cost cap. An absent `claude` binary also gives exit code 3, with a message that names it.

`--out <dir>` writes a result file with the counts, the costs and the check names only. The pass-rate indicator of `stats --sdlc` reads result files that the project keeps. The result file stores no prompt text and no output text, because they can hold secrets.

spec-dna itself makes no network call. `eval run` starts `claude`, which uses the network. The command refuses to start when `runs × max-budget-usd` of all evals is more than `max-total-usd`.

Claude Code checks `--max-budget-usd` against a client-side estimate, and spend can exceed it. Thus the runner adds the `total_cost_usd` of each run. It starts no more runs when the sum exceeds `max-total-usd`. This stop is exit code 3.

The Claude Code documentation says that `--bare` will become the default of `-p`. When that happens, the runner must pass the flag that disables it. A probe at build time finds the flag.

### The workflow

`init` writes `.github/workflows/agent-evals.yml` when the answer to question 14 is `skeleton`. The table `[evals]` is the only switch for evals. The workflow follows the rules of `AGENTS.md`: each `uses:` is a full commit SHA, and `permissions: {}` is at the workflow level.

- Triggers: `pull_request` and `push` with `paths` for `CLAUDE.md`, `AGENTS.md`, `.claude/skills/**`, `.claude/agents/**`, `.claude/settings.json` and the `[evals] dir` folder; a weekly `schedule`; `workflow_dispatch`. The playbook asks for a run "on a schedule and on any change to `CLAUDE.md`, skills or hooks".
- A pull request from a fork has no secrets. The job runs only if the head repository is this repository. The workflow never uses `pull_request_target`.
- `init` writes the workflow once. The workflow has no marker, so a Dependabot update of a pin gives no SD501. The job has `contents: read`. It installs Claude Code and spec-dna. It runs `spec-dna eval run`. The key is the secret `ANTHROPIC_API_KEY`.
- The step fails the job when the pass rate is below `min-pass-rate`.

## Upgrade

[ADR 0009](../adr/0009-upgrade-from-0-5.md) records the decisions. `upgrade` is also the command that [ADR 0003](../adr/0003-distribution.md) names for a change of the pin. It moves the pin to the version of the binary that runs.

`spec-dna upgrade [--dry-run] [--layout] [--pin-file <file>]` takes a project that pins 0.4.0 or later. The reason is the "pin first" rule of ADR 0003. From 0.4.0, a teammate with an older binary gets the install command and not a parse error. A project with an older pin must first move to 0.4.2 and then run `upgrade`. `--pin-file` gives the file `spec-dna-pin.toml` of the release, which has the checksums. The binary cannot know its own checksum.

| Step | What it does |
| --- | --- |
| 1. Check | Refuses on a dirty working tree. Reads the old configuration. Builds the whole plan in memory |
| 2. Configuration | Writes the new keys and renames the old ones (types, `reviewer`, `spec-writer`). It writes `[change] policy = "none"` and the layers that the types in use need, with no limits. It sets the pin to the new version |
| 3. Front matter | Rewrites each `type:`, each `status:`, `roots.status` and each `status-map` target that changed. A `change` that is `proposed` or `accepted` becomes an `intent` that is `draft` or `accepted`, and a `rejected` change becomes a `closed` intent. A `done` change becomes `research`. A former `note` becomes `research`. `upgrade` writes `was-type` (`change` or `note`) on each such document, and removes the `status` line of a `done` change. For a migrated `intent`, it writes `required-sections = { intent = [] }`, and the field `class` is optional. If a migrated change is over the new hard budget of 12,000, it writes a `[budgets.intent]` of 10,000 and 20,000. For each root that has no `live-sections`, it writes `live-sections = {}`, so that no 0.5 decision gains a live section by default |
| 4. Harness | If `[harness]` exists, renames the role keys, and writes the new parts (`skills`, `review-md`, `protect-tests`) as off. A 0.5 project at level `full` gets `code-simplifier = "none"`, so it gets no new agent. It deletes an unedited generated file under its old name. It keeps an edited one, and `check` reports it (SD501). It never replaces a file that has no marker: it disables that role. [ADR 0008](../adr/0008-harness-and-evals.md) gives the cases |
| 5. Changes and layout | Always: moves each `proposed`, `accepted` or `rejected` change to `intent/<slug>/intent.md` with `git mv`, and writes its old id into `aliases`. The reason is that the type `intent` is valid only in the `intent` layer. Only with `--layout`: moves the folders of the other 0.5 namespaces (`contracts`, `invariants`, `guides`, `runbooks`, `reference`, `notes`) to the 0.6 folders. It writes the old ids into `aliases`. It stops if 2 moves have the same target. A 0.5 spec has no namespace, so it stays where it is. New specs go to `requirements/<area>/` |
| 6. Proof | Checks that each old id resolves in the new tree, and that the hash of each requirement and each section is the same. If the proof fails, `upgrade` writes nothing and exits with code 1 |
| 7. Report | Lists each `done` or `rejected` change that no document cites as a proposal to delete, each decision with no `Status` section, and the changes of behavior below |

`upgrade` never renames the file stem of a decision, so `legacy-ids` patterns still resolve. The one change of a stem is the move of a change into `intent/<slug>/intent.md`. A root of 0.5 type `note` becomes a mixed root with `default-type = "research"`, so no id changes. For a project with the profile `strict`, `upgrade` writes no limit. A second `upgrade` changes nothing.

Changes of behavior that `upgrade` reports and the CHANGELOG records:

- A former `note` is now `research`, with `keep = "forever"`. SD202 allows the deletion of a document that has `was-type: note` or `was-type: change`, as 0.5 did. This is the only exemption in a `forever` layer.
- `context` listed incidents and notes. It now counts them in one line.
- The context order follows the levels of the graph. `foundation` comes before `rules`.
- The `--json` field `name` of SD405 and SD611 changed.
- 0.6.0 renames types, keys and commands, so it is a minor release that breaks compatibility. Semantic Versioning allows this before 1.0.

`--dry-run` prints the diff of every file and writes nothing. `upgrade` never commits and never deletes a document.

The first pull request after the upgrade has a base tree with a pin before 0.6.0. The documents of the base use 0.5 types and statuses, which 0.6 rejects. In that case `check` runs the plan of `upgrade` on the base tree in memory, and then makes the normal comparison. The gate stays active. No second code path decides what is new.

SD503 does not apply when the pin of the base is before 0.6.0, so a single pull request can hold the configuration and the documents. A later change of the pin, such as 0.6.0 to 0.6.1, keeps SD503.

A brownfield project keeps its folders. The `[[roots]]` table maps them to the new types. `--layout` is optional, and `spec-dna mv` can move one document at a time.

To undo the upgrade, revert it. After the merge this needs 2 pull requests, because SD503 of the old binary rejects a configuration and documents together. The second pull request also gives SD202 for each migrated change, and with `--layout` for each moved id. Revert before the merge when possible.

### Detail of ADR 0006: playbook quotes

ADR 0006 gives these rules of the [playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) in short form. This is the text of the playbook:

- Section "Plays": "A stage ends by committing an artifact with the commit initiating the next stage."
- Section "Plays": "An accepted `intent.md` triggers the requirements and design pass, an approved `spec.md` triggers plan mode, a merged PR triggers the pipeline, and a breached control band in production writes the next `intent.md` and so the loop continues."
- Stage 1: "The product owner approves, and the accept or reject decision that sends the intent into Stage 2: Design is recorded as the merge or the closing review." spec-dna uses only the merge.
- Stage 3: "When implementation departs from the plan, update `plan.md` in the same commit."
- Stage 3: "Routine changes are approved by the engineer, and anything the organization classes as higher risk goes to a tech lead or architect."
- Stage 4: "Each production incident gets an eval, written by the team that owned the incident, and stays in the suite as a regression test."
- Stage 5, "AI in the PR review loop": "Approval comes from a human through branch protection, informed by the findings."
- Stage 5: "Findings do not approve or block a PR on their own, and branch protection still requires approval from a code owner."
- Stage 6: "A small, well-bounded fix arrives as a PR through the review gate, and anything larger is written up as `intent.md` for Stage 1: Plan, at which point the loop starts feeding itself." A `small-fix` is such a pull request.

### Detail of ADR 0006: the approver and the review findings

- spec-dna reads no git author, no e-mail and no signature for an approval.
- The code host enforces who may merge: branch protection, required reviews and code-owner rules. A repository without them has no enforcement of the approver.
- The merge of a plan stays under the branch protection of the repository.
- Review findings are the comments of a review on a pull request. They are data of the code host, and spec-dna reads none of them.

### Detail of ADR 0006: the base of a gate

The gate trusts the base that CI gives with `--base`. A stacked pull request, or a base other than the default branch, can hold an approval that the default branch does not have.

### Detail of ADR 0006: SD911 and the history

- In a shallow clone, git gives the boundary commit as the newest commit that touched the folder. Its date is the same or later. Thus a shallow clone can hide a stale change, but it never reports a false one.
- A project that makes SD911 an error with `rules` accepts a gate that reads the history.

### Detail of ADR 0007: how `new` uses a template

- `new <type> <id> --template <name>` reads `<dir>/<name>.md` first, and then the embedded template of that name. `<dir>` is `[templates] dir`.
- Without `--template`, `new` uses the default template of the type.
- `new` copies the template. The `type` line stays in the copy.

### Detail of ADR 0008: Claude Code facts

These facts support the decisions of ADR 0008:

- The built-in subagents are `Explore`, `Plan` and `general-purpose`. None has the name `verifier` or `code-simplifier`. A project agent has priority over a user or plugin agent of the same name: <https://code.claude.com/docs/en/sub-agents.md>.
- The Code Review service and the local `/code-review` command both read `CLAUDE.md`. `REVIEW.md` can include a skill file, but Code Review ignores a Nit cap or an exclusion in a skill: <https://code.claude.com/docs/en/code-review-customize.md>.
- A `PreToolUse` hook can block a call, or answer `allow`, `deny` or `ask`. In a `-p` run where nobody can answer, Claude Code denies the call, and Claude reads the reason: <https://code.claude.com/docs/en/hooks.md>.
- A hook decision does not bypass a deny rule or an ask rule: <https://code.claude.com/docs/en/permissions.md>.
- In `dontAsk` mode, Claude Code denies each call that would prompt. Without `--bare`, a `-p` run also loads `~/.claude`, and runs the project hooks with no trust prompt: <https://code.claude.com/docs/en/headless.md>.

### Detail of ADR 0008: roles

- `model-team.md` and `docs/harness.md` give the source URL of each role.
- `code-simplifier` removes needless complexity from the diff, and keeps the behavior.

### Detail of ADR 0008: harness files after the upgrade

- After `upgrade` deletes an unedited `checker.md` or `spec-writer.md`, `check` reports nothing.
- `init --reconfigure` offers the new parts, as ADR 0004 does for an upgrade.
- To clear SD501 for an edited marked file that the configuration does not generate, delete the file. To keep it as an agent file of the project, delete its marker line. The names `checker` and `spec-writer` belong to no 0.6 role.

### Detail of ADR 0008: `protect-tests`

- `git` also resolves a worktree. A path that matches no glob starts no process.
- An error gives no output and exit code 0, so the edit continues. The generated command ends with `2>/dev/null || true`.

### Detail of ADR 0008: the runner and its result

- `<dir>/check.sh` has no marker, and `check` does not compare its text.
- The runner never copies `.claude/settings.local.json`, because it is the local state of one person.
- `--runs` overrides the `runs` of an eval, which overrides `[evals] runs`.
- Exit code 0 means that the pass rate is at least `min-pass-rate`. Exit code 1 means that it is lower.
- `--json` prints the result, and `--out <dir>` writes it to a file. The result has the eval ids, the check names, the counts, the sum of `total_cost_usd` and the versions. It has no prompt text and no output text. The task text is in the eval file, which the project commits.
- Claude Code can keep its own session files on the machine. spec-dna does not read or copy them. To see a session, a person runs one eval again.
- The workflow commits nothing, so `stats --sdlc` does not read its results.

The playbook says that the eval suite runs non-interactively in CI. The workflow follows this with `claude -p`.

### Detail of ADR 0009: source versions

- `upgrade` reads the pin with the line scan of ADR 0003, amendment "phase 2", item "Pin first". The reason is that the 0.6 schema rejects the keys and type names of a 0.5 file.
- A 0.4 configuration is a 0.5 configuration with no `[harness]` table. Thus one reader serves both.

### Detail of ADR 0009: phases of a run

`upgrade` does these phases. It stops at the first failure, and it writes nothing before phase 4.

1. Read. Refuse a staged change, an unstaged change and an untracked file that git does not ignore. `--dry-run` has the same rule, so its diff is the diff of a write.
2. Plan. Compute the new configuration, front matter, adapters and harness files in memory. Also compute the moves of the changes, and with `--layout` the other moves.
3. Proof. Run the proof of ADR 0009 on the plan.
4. Write. Write the files, and move with `git mv`. `--dry-run` prints the diff of each file and stops before this phase.
5. Report. Print the report and the `git add` command. Never commit.

A run with the pin of the binary rewrites only the 0.5 names that remain. Thus a branch that merges the default branch after the upgrade runs `upgrade` again for its own new documents.

### Detail of ADR 0009: exit codes, `--json` and the report

`upgrade` uses the exit codes of [commands.md](../commands.md#exit-codes):

- 0 after a write, or when nothing changes.
- 1 when it refuses a tree that is not clean, or when the proof fails.
- 2 for a usage error, and 4 for a git error.
- 3 for a configuration error: no `spec-dna.toml`, a pin before 0.4.0 or after the binary, or a file that neither schema reads. `[spec-dna-sha256]` with no valid `--pin-file` also gives 3.

`--json` has `from`, `to`, `files`, `proof` and `report`. Each entry of `files` has `path`, `action` (`write`, `move`, `remove` or `keep`) and `diff`, as in `init --json`.

The report lists these items:

- The deletion proposals, and each decision with no `Status` section.
- Each locked decision that cites a migrated change, because `finish` does not stop on a reference in locked text.
- Each kept harness file, and each ended role with its model.
- The changes of behavior of [Upgrade](#upgrade).
- The count of each error code of `check --all` on the new tree.

### Detail of ADR 0009: configuration

- `upgrade` renames each 0.5 type in `types`, `roots.type`, `roots.default-type` and the keys of each table by type. It renames each `change` status in `roots.status` and `roots.status-map`.
- When 2 old types with explicit keys merge into one, `upgrade` keeps the weaker value. That is the larger budget, the required sections that both share, and the union of other section names.
- If `spec-dna.toml` has `[spec-dna-sha256]`, `--pin-file` must name the `spec-dna-pin.toml` of the new version. The person verifies that file with `gh attestation verify`. `upgrade` copies its sums.

### Detail of ADR 0009: documents and layout

- `upgrade` changes a body only for the link destinations of a move. It changes the relative links, as `mv` does.
- The move of a change writes the old id and each old legacy alias into `aliases`, because the file stem `intent` matches no `legacy-ids` pattern.
- `upgrade` also writes the 0.6 adapters, as `init` does: the line of each instruction file, and the skill with the new types.
- `type: spec` outside the `intent` layer is a 0.5 spec, so `upgrade` writes `requirements`. `upgrade` also writes `type:` where the place now gives another type.
- A 0.5 spec that a branch brings after the upgrade gives SD303, and the message names `requirements`.
- With `--layout`, a `done` change stays, because it is a deletion proposal. A 0.5 spec stays, because only a person can choose its area.

### Detail of ADR 0009: first pull request after the upgrade

- The plan on the base tree runs without `--layout`. It takes the pin and the sums of the head.
- `check` reads the base pin with the line scan of "Pin first".
- A pin change inside 0.6, such as 0.6.0 to 0.6.1, keeps the usual comparison.

### Detail of ADR 0009: deletion and rollback

- The owner confirms the second condition of ADR 0001 for each proposal: the decisions of the change exist as decision documents.
- The owner approves each batch, and a later pull request deletes it.
- On a 0.5 project, `init` and `init --reconfigure` do not run when the pin differs. The message names `spec-dna upgrade`.
- Before the commit, `git reset --hard` and `git clean -fd` restore the tree, because `upgrade` starts from a clean tree.

### Owner additions for step 3

The owner added 3 items to step 3, to prepare the workflow pack of 0.7.0. They are additions, not deviations.

- Tasks in `plan.md`. The `Order` section is a task list. A task is a checkbox line with a stable id:

  ````md
  - [ ] <id>: <text>. Files: `path`, `glob`. Verify: <text or `command`>.
  ````

  The id matches `[A-Za-z0-9][A-Za-z0-9_-]*` and is followed by a colon and a space. `- [x]` is a done task. A line of `Order` with no id is not a task. A duplicate id marks the later task, and `next` ignores it. `status` and `next` read the checkboxes, and `next` names the next open task. `PARSER_VERSION` is 13.
- Skill names in `next`. Each item of the `next` checklist has a `skill`, in the text as `[skill: <name>]` and in `--json` as the field `skill`. The 9 names are fixed constants: `brainstorm`, `specify`, `clarify`, `write-plan`, `execute`, `tdd`, `review`, `verify`, `finish`. The mapping is:

  - Plan stage: `brainstorm`.
  - Design with no spec or a draft spec: `specify`.
  - An open concern or open question: `clarify`.
  - Build with no plan or a draft plan: `write-plan`.
  - Build with an open task: `execute`.
  - Test: `tdd`.

#### `protect-tests` (S4)

The settings entry is a `Want::Hook` with `event: "PreToolUse"`, `matcher: "Edit|Write"` and `name: "protect-tests"`. Its command:

```text
spec-dna hook protect-tests --mode fix-branches --test '**/tests/**' --test '**/*_test.*' 2>/dev/null || true
```

- One `--test '<glob>'` for each glob of `[evidence] tests`, in the order of the list. The glob is in single quotes, and a `'` in it becomes `'\''`. `--mode` is `fix-branches` or `always`. An absent or unknown `--mode` value acts as `fix-branches`. The hook ignores an unknown flag, and with no `--test` it prints nothing.
- There is no entry for `protect-tests = "off"`, for an empty `[evidence] tests`, or at level `none`. `--reconfigure` removes the handler by the prefix `spec-dna hook protect-tests`.
- Input: the `PreToolUse` event of Claude Code (<https://code.claude.com/docs/en/hooks.md>, read on 2026-11-15). The hook reads `tool_name`, `tool_input.file_path` and `cwd`. For `Edit` and `Write`, `file_path` is always absolute, with backslashes on Windows. The hook reads `CLAUDE_PROJECT_DIR` from the environment.

The steps. Each failure gives no output and exit code 0:

1. Read at most 1 MiB of stdin, and parse the JSON. `tool_name` must be `Edit` or `Write`.
2. The root is `CLAUDE_PROJECT_DIR`, else `cwd`. Change each `\` to `/` in both paths. The relative path is `file_path` after `<root>/`. If `file_path` is not under the root, canonicalize the root and the parent folder of `file_path` (for example `/var` and `/private/var` on macOS) and try again. A relative path with a `..` or `.` segment gives no output.
3. Match the relative path against each `--test` glob with `glob::matches`. With no match, stop. No process starts.
4. For `fix-branches` only: run `git -C <root> symbolic-ref --short -q HEAD`. Continue only if the output starts with `fix/`. A detached HEAD stops.
5. Run `git -C <root> ls-files --error-unmatch -- ':(literal)<relative path>'`. Continue only on exit code 0. Thus a new test file passes.
6. Print one line. With `always`, the reason is "spec-dna protect-tests: `<path>` is a test file that git tracks. Approve the edit only if the test is wrong."

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"spec-dna protect-tests: <path> is a test file that git tracks, and <branch> is a fix branch. A fix changes the code, not the test. Approve the edit only if the test is wrong."}}
```

- Git runs with `GIT_OPTIONAL_LOCKS=0`. The output holds the path and the branch only, and the hook stores nothing.
- The function in `src/hook.rs` takes the git call as a parameter, so a unit test counts the processes and tests a Windows path.
- `docs/commands.md`, section `hook`: after "It reads at most one more file", add "`protect-tests` reads no file, and runs `git` at most 2 times, only for a path that matches a test glob".
- The probe of the main session (2026-11-15, Claude Code 2.1.325): in `claude -p --permission-mode dontAsk --allowedTools Edit`, the hook answer `ask` denies the edit, so the hook guards an eval.

An eval is `<dir>/<id>.json`. SD506 and `eval run` share one validator, `evals::parse_eval` in `src/evals.rs` (S6). It returns the first rule that fails, in the order of this table, as a key and a message. The first row applies to the whole file.

| Key | Type | Required | Default | Rule |
| --- | --- | --- | --- | --- |
| - | - | - | - | At most 64 KiB, UTF-8, one JSON object. A key that is not in this table: "unknown key `<k>`" |
| `id` | string | yes | - | `[a-z0-9][a-z0-9-]{0,63}`, equal to the file stem (D46) |
| `task` | string | yes | - | Not empty, at most 8,000 bytes, and does not start with `-` |
| `fixture` | string | yes | - | A folder under `<dir>/` (D46) and not under `<dir>/results/`. `/` separators, no `..` or `.` segment, no `\`. At least one file of the tree is under it |
| `branch` | string | no | none | `[A-Za-z0-9][A-Za-z0-9._/-]{0,99}`, no `..` or `//`, and does not end with `/` or `.lock`. `main` is the base branch, so `main` gives no switch |
| `allowed-tools` | array of strings | no | `[]` | Each not empty, with no control character |
| `max-turns` | integer | no | `20` | From 1 to 1,000 |
| `max-budget-usd` | number | yes | - | Above 0, and at most `[evals] max-total-usd` |
| `runs` | integer | no | `[evals] runs` | From 1 to 100 |
| `pass-at` | integer | no | The runs of the eval | From 1 to the runs of the eval |
| `checks` | array of objects | yes | - | Not empty. Each object has exactly `name` (`[a-z0-9][a-z0-9-]{0,63}`, once in the file) and `run` (not empty) |

An integer key needs a JSON number with no fraction. `evals::skeleton_paths(dir)` gives the 4 starter paths of the table "Starter files".

#### The runner (S6)

```text
spec-dna eval run [<id>...] [--runs <n>] [--min-pass-rate <r>] [--max-total-usd <n>] [--out <dir>] [--dry-run] [--isolate] [--json]
```

- `<id>...` selects the evals. With no id, it selects each eval, in the order of the id. An unknown id gives exit code 2. There is no `--filter`.
- `--runs` (1 to 100), `--min-pass-rate` (0 to 1) and `--max-total-usd` (above 0) replace the values of the files and of the table. A bad value gives exit code 2.
- `--out <dir>` is relative to the repository root. The runner creates it. It must not be `[evals] dir` (exit code 2), because SD506 reads the `*.json` files there. `stats --sdlc` reads only `<dir>/results` (D52).
- `--dry-run` validates, prints each eval with its runs and the estimate, and starts no process. Exit code 0, or 3 for the cap.
- `--isolate` (O2) adds `--setting-sources project`. It is off by default.
- `spec-dna eval` with no subcommand, or with another subcommand, gives exit code 2.

Exit codes: 0 when the pass rate is at least `min-pass-rate`; 1 when it is lower; 2 for a usage error; 3 for no `[evals]` table, an invalid eval (the path and the SD506 message), an estimate above the cap, a stop by the cap, or a `claude` that is absent or cannot start; 4 for a git or file error of the runner itself: the temporary folder, the copy or the base commit (D47, O1).

The steps:

1. Load the configuration, with the pin rule of each command. Read and validate each eval file of the working tree: the tracked files, and the untracked files that git does not ignore. Select the evals.
2. The estimate is the sum of `runs × max-budget-usd` of the selected evals. If it is above the cap, stop with exit code 3. No process starts.
3. Run `claude --version` once. A start error gives exit code 3: "`claude` did not start (`<error>`); install Claude Code (<https://code.claude.com/docs/en/setup.md>) and put it on PATH". The version is the first word of stdout if it has only digits and dots, else `null`.
4. For each eval and each run (each run runs; there is no early stop):
    1. Make the folder `<temp>/spec-dna-eval-<pid>-<n>` with `create_dir`, mode 700 on Unix.
    2. Copy from the working tree. First the files under the fixture that `git ls-files --cached --others --exclude-standard` lists, into the root of the folder. Then the files of `CLAUDE.md`, `AGENTS.md`, `REVIEW.md` and `.claude/` at their paths, except `.claude/settings.local.json`. A file of the project replaces a fixture file at the same path. A symbolic link is not copied, and stderr gets a warning.
    3. Run `git init -q -b main` and `git add -A`. Then run `git -c user.name=spec-dna -c user.email=eval@spec-dna.invalid -c commit.gpgsign=false -c core.hooksPath=<folder>/.git/no-hooks commit -q --no-verify -m "spec-dna eval base"`, with `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` set to `2000-01-01T00:00:00Z`. Keep the commit id. If `branch` is set and is not `main`, run `git switch -q -c <branch>`.
    4. Start `claude` in the folder with this argv, in this order: `-p`, the task, then `--allowedTools` and each tool as its own argument (only for a list that is not empty), then `--output-format json --max-turns <n> --max-budget-usd <usd> --permission-mode dontAsk`, then with `--isolate` `--setting-sources project`. Never `--bare`. The environment is the environment of the runner without `CLAUDE_PROJECT_DIR`. Stdin is empty, stderr goes to stderr, and the runner keeps at most 16 MiB of stdout in memory.
    5. From stdout, read only `total_cost_usd` (a number of 0 or more) and `subtype` (kept only if it matches `[a-z_]{1,40}`). If the cost is absent, the cap counts `max-budget-usd` for the run.
    6. Run each check as `sh -c` with the script `. "$SPEC_DNA_CHECK_SH" || exit 97`, a newline and the `run` text, in the folder. The environment is that of sub-step 4, plus `SPEC_DNA_CHECK_SH` (the absolute path of `<dir>/check.sh` of the project) and `SPEC_DNA_EVAL_BASE` (the commit id). The checks run also when `claude` failed. A check passes on exit code 0. A run passes when `claude` exits with code 0 and each check passes.
    7. Delete the folder, also after an error.
    8. Add the cost to the spend. If the spend is above the cap and a run is left, stop: exit code 3 after the output.
5. An eval passes when its passed runs are at least `min(pass-at, runs)`. The pass rate is the passed evals over the selected evals. The suite passes when the pass rate is at least `min-pass-rate`.

The text output:

```text
eval run: 2 evals, 4 runs, estimate 7.00 USD, cap 20.00 USD
example: 1 of 1 runs passed, pass-at 1: pass, 0.12 USD
fix-keeps-tests: 1 of 3 runs passed, pass-at 2: fail, 1.80 USD
pass rate 50.0 percent (1 of 2 evals), min-pass-rate 80.0 percent: fail
spend 1.92 USD
```

A stop adds the line `stopped: the spend <s> USD is above max-total-usd <c> USD; <n> runs did not start`.

The result goes to stdout with `--json`, and with `--out` to `<out>/eval-<YYYYMMDD>T<HHMMSS>Z.json` (the UTC time of the start; if the file exists, `-2`, `-3` and so on). The file is `json::pretty`. The runner reads the clock only for `started`, with no new crate. This sample is a run of the example eval only:

```json
{"spec_dna":"0.5.0","claude_code":"2.1.325","started":"2026-11-15T10:15:00Z","evals_dir":"evals","min_pass_rate":0.8,"max_total_usd":20,"estimate_usd":1,"spend_usd":0.12,"stopped":null,"pass_rate":1,"passed":true,"evals":[{"id":"example","runs":1,"pass_at":1,"max_budget_usd":1,"passed_runs":1,"passed":true,"spend_usd":0.12,"results":[{"claude_exit":0,"subtype":"success","cost_usd":0.12,"checks":[{"name":"notes-done","passed":true}]}]}]}
```

- `stopped` is `null` or `"max-total-usd"`. After a stop, `pass_rate` is `null`, `passed` is `false`, and an eval that did not start has `"results":[]`.
- `cost_usd` is `null` when `claude` gave no cost. `spend_usd` is the sum that the cap uses.
- The result has no task text, no check command, no output text of `claude`, no path of the machine and no environment value.
