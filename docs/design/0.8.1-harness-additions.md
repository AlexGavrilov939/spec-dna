# Harness additions of 0.8.1

Status: design, proposed. Date: 2026-11-24. This page is a design only. It adds no code.

This page designs 5 additions to the harness that `spec-dna init` writes. The owner took the 5 items from the harness of an anonymized mature project. This page gives a generic form for any repository, stack and agent. It is for the owner, who answers the questions, and for the agents that build the items.

## 1. The items

| Item | Name | Cost class | Build order | Recommendation |
| --- | --- | --- | --- | --- |
| 18 | Subagent card, task brief and return states | Hook | 1 | The card and the check of the state line are 2 hooks. The template of the task brief is in the skill `execute` |
| 20 | Lessons | Text only | 2 | A part `Lessons:` in the report, and a note of `finish`. Nothing goes into the repository before the person accepts a lesson |
| 19 | The limit of 3 failed fixes | Hook | 3 | A hook counts the failed fixes of one command for each agent, and tells the agent to stop at 3 |
| 22 | `outline` | New command | 4 | Line rules for 5 language families, with no new dependency |
| 21 | The cost report | New command (a mode of `transcript`) | 5 | `transcript --cost`, with a price table in the binary and the option `--prices` |

The cost classes:

- Text only: a change of a text that spec-dna writes or prints.
- Hook: a new `spec-dna hook` handler and its entries in `.claude/settings.json`.
- New command: a new command, or a new mode of a command.

The reasons for the order:

1. Item 18 comes first, because items 19 and 20 use its report form: the state `BLOCKED` and the part `Lessons:`.
2. Item 20 is text only, and the card of item 18 carries its line for subagents.
3. Item 19 is a hook with a state file, in the form of the context meter.
4. Item 22 needs no other item. It can go in parallel with item 19.
5. Item 21 comes last. The build must first confirm 3 facts of the transcript format on a fixture. These are the 2 facts of E7 and the field that gives the type of a subagent. The owner must also answer Q11.

The design is for the harness that `init` writes in a consumer project. The team of this repository (`.claude/agents/`) can take the same rules in a separate change of the owner.

## 4. Item 18: subagent card, task brief and return states

**Problem**:

A main session sends a subagent a prompt in free form. The subagent can grow the scope, commit, read files in any order, and return a long text with no clear result. Example: the prompt is "fix the timeout". The subagent also renames a module, commits the work and returns 2 pages. The main session cannot tell if the task is done, or if the subagent stopped on a question.

**Mechanism**:

1. The subagent card is one fixed text of 800 bytes or fewer. The hook `spec-dna hook subagent-card` runs on `SubagentStart` for each subagent and adds the card as `additionalContext` (E4). Thus the card reaches each subagent: a generated agent, the `helper` with no agent file, and an agent file of the project.
2. The agent file and its brief have priority over the card, and the first line of the card says so. Thus `acceptor`, `verifier`, `Explore` and `fallback-advisor` keep their own scope and report form. One line depends on the role: for `agent_type = "acceptor"`, line 3 is "Commit only `acceptance.toml`, as your agent file says. Do not push."
3. With the key, the team page `.claude/agents/model-team.md` prints the card. Thus a pull request shows each change of the card, and `check` reports SD502 when the page differs from the text of the binary.
4. The hook `spec-dna hook return-state` runs on `SubagentStop` with the matcher `.+`, so an internal agent with an empty `agent_type` does not match (E1). It reads the last line of `last_assistant_message` that is not empty. After a `SubagentHandback` call, it reads the `message` of the last such call in `agent_transcript_path` (E2).
5. When that line is not a state line and `stop_hook_active` is false, the hook returns `decision: "block"` with the reason "End your report with one line: `State: <state>`." When `stop_hook_active` is true, it gives no output. Thus it adds at most one request.
6. The text of `execute` says: "If the report of a subagent ends with a state line, act on the state." A report with no state line gets the same review as before. Thus the static text of `execute` is true with each value of the key.
7. The task brief is the text that the main session writes for a subagent. The main session takes `Task`, `Files` and `Done when` from `next_task` of `spec-dna next <slug> --json` (`text`, `files` and `verify`).
8. The acceptor gets no task brief. Its prompt stays the line that `next` prints, and the builder adds no word ([ADR 0032](../adr/0032-acceptance-in-one-pass.md)). The card adds nothing to the output of `accept --brief`, so the brief format 2 and its hash stay. The state line is never an input of a gate: `next` and the acceptance record stay the source of truth. An acceptor that commits a record with `result = "rejected"` ends with `State: COMPLETE`.
9. ADR 0032 rejected a `SubagentStart` hook for the brief of the acceptor. That brief needs the slug, and it can be longer than 10,000 characters (E4). It must also be the output of the call of the acceptor, so that its hash binds the input. The card needs no slug, is short, and binds nothing.
10. The key `[harness] subagent-card` (`true` or `false`) writes both entries. `init` writes `true` for a new configuration of `standard` and `strict`, and `false` for `lite`. A file with no key has the effect of `false`. The skill `execute` of `lite` keeps the bytes of 0.7.1, so `lite` changes in nothing.
11. The harness arms of `eval run` (`--harness` and `--arms`) set `subagent-card = false`. Thus a measure keeps the setup of 0.8.0 until a new protocol turns the key on.

The 4 return states:

| State | Meaning | The main session |
| --- | --- | --- |
| `COMPLETE` | The task is done, and the check of `Done when` passes | Verify the work as usual |
| `COMPLETE_WITH_CONCERNS` | The task is done. The report lists each concern: a risk, a skipped check or a doubt | Read each concern before the verification |
| `NEEDS_CONTEXT` | The subagent stopped, because it does not have a fact. The report names the fact | Give the fact, then start the task again |
| `BLOCKED` | The subagent cannot complete the task. Causes: a check fails outside the scope, the agent host denies a tool, the fix limit occurs (item 19), or the task needs more scope | Do not send the same brief again. Remove the cause, or tell the person |

The card:

```text
Subagent card. Your agent file and your brief have priority over this card.
1. Do only the task of the brief. Change only the files of `Files`. If the task needs more, stop and report it.
2. Read the brief first, then the files that it names. Run `spec-dna context <file>` before you edit a file. Search only for a fact that these do not give.
3. Do not commit, push or change the git state.
4. Report the result, the files that you changed, the commands that you ran with their result, and the open issues.
5. If you found a rule that the files of the project do not state, add `Lessons:` before the last line (item 20).
6. End the report with one line: `State: COMPLETE`, `State: COMPLETE_WITH_CONCERNS`, `State: NEEDS_CONTEXT` or `State: BLOCKED`.
```

The template of the task brief:

```text
Task: <the result, in one sentence>
Files: <the paths to change>
Out of scope: <the paths and the work to leave>
Read first: <the documents and the files>
Done when: <the command, and its expected result>
```

**Files and agents**:

- `init-engineer`: `src/hook.rs` (the 2 hooks), `src/harness.rs` (the settings entries and the team page), `src/harness_text.rs` (the card, and the template and the actions of the states in the skill `execute`), the preset of the key in `src/init.rs` and `docs/init.md`, `docs/harness.md`, the `hook` section of `docs/commands.md`, `tests/golden/harness/`, `tests/hook.rs`, `tests/init_profiles.rs` and the harness tests.
- `diagnostics-engineer`: the function `check` of `src/harness.rs` (SD502 and SD504 for the new entries) and the section "Check" of `docs/harness.md`.
- `core-engineer`: the key `subagent-card` in `src/config.rs`, `schema/spec-dna.schema.json` and `docs/config.md`, and the value `false` in the harness arms of `src/eval_run.rs`.
- Change sets: "Hook", "Harness role or generated file" and "Config key". `test-engineer` is C. `release-engineer` adds the entry to `CHANGELOG.md`.
- Proof: `tests/hook.rs`. A `SubagentStart` input gives the card, with the role line for `acceptor`. A `SubagentStop` input with no state line gives `decision: "block"`, and the same input with `stop_hook_active` true gives no output. An input with an empty `agent_type` gives no output. The golden file of the team page holds the card.

**Cost**:

- Each subagent gets 800 bytes or fewer in its context, and each of its requests sends them again from the cache. The request of the main session gets no byte.
- A report with no state line costs one more request over the whole context of the subagent. An acceptance run on a slice of this repository had about 190,000 to 250,000 tokens (E10).
- 2 processes for each subagent. They read stdin, and after a `SubagentHandback` call, one transcript. They run no git.
- The template and the actions must fit in the room of the skill `execute`: 326 bytes (E12). `execute` has no frozen hash (E11).
- No frozen hash changes, because no frozen file changes (E11). The pack evals start no subagent, and the harness arms keep the key off (step 11), so each verdict and each protocol keeps its setup.
- Each teammate needs spec-dna 0.8.1 or later on `PATH`. With an older binary, the hooks do nothing.

**Does not prove**:

- That a subagent obeys the card. The card is text in its context.
- That the state is true. A subagent can write `COMPLETE` for work that fails. The verifier and the acceptance record stay the controls.
- That an agent other than Claude Code gets the card. That agent gets it only when the main session pastes it into the task brief, from `docs/harness.md`.
- That the hook skips an internal agent of a session that starts with `--agent <name>`. That agent has the name of the session as its `agent_type` (E1). The build checks it.

**Questions**:

**Q1. Where does the card live?** (a) A paragraph in each generated agent file, as the paragraph "Scratch folder:". It does not reach the `helper` or an agent file of the project. It changes the frozen hash of `acceptor.md`, and `lite` keeps the agent files of 0.7.1. (b) The hook `subagent-card`, for each subagent. (c) Both. Recommendation: (b).

**Q2. How does spec-dna check the state line?** (a) The line of the card only. (b) The hook `return-state`, with one more request at most. (c) A `PostToolUse` hook on the tool `Agent` that tells the main session, with no request of the subagent. No source confirms the form of its input for the report of a subagent. Recommendation: (b).

**Q3. Where does the main session get the template and the actions of the states?** (a) The skill `execute`, in 326 bytes, and the full form in `docs/harness.md`. (b) Also one sentence in the model-team line of `CLAUDE.md`, which each request sends. Recommendation: (a).

## 5. Item 19: the limit of 3 failed fixes

**Problem**:

An agent fixes a failure by guesses, and nothing stops it. Example: `pytest tests/test_valve.py` fails. The agent changes the code 5 times, each time with a new guess, and each run fails. The context grows with each try, and no person hears of the problem.

**Mechanism**:

1. The ladder exists as text (E9). At 2 occurrences of the same error, the model-team line tells the agent to consult the advisor. At 3 failed fixes, the skill `debug` and the discipline "Cause first" tell it to stop and ask the person. The hook adds a count at the time of the failure. ADR 0004 found that prose rules on the context size and the agent count did not change agent behavior. Hooks at the time of the problem did.
2. The same problem is the same shell command that fails again. Each run of white space in the command counts as one space.
3. A failed fix is a failure of that command after the same agent made at least one edit since the last failure. A run with no edit between is no fix. The first failure is the problem, not a fix, so the red run of `tdd` never counts.
4. `spec-dna hook fix-limit --limit 3 --intent '<dir>'...` has 3 settings entries:
    - `PostToolUseFailure`, matcher `Bash` (E3): the first failure of a command makes its count, at 0. A later failure adds 1 when the agent has an edit mark. Each failure removes the mark, so one edit counts for one failure only. At the limit, add the message once.
    - `PostToolUse`, matcher `Bash`: the command passed, so delete its count.
    - `PostToolUse`, matcher `Edit|Write`: set the edit mark of the agent. An edit below an `--intent` folder sets no mark, so the record of the acceptor and an edit of `plan.md` are no fix.
5. The key of a count has 3 parts: the session, the agent (`main` or the agent id) and a hash. The hash is the first 8 bytes of SHA-256 of the session id and the command. The state is one small file for each key in `<temp>/spec-dna-fix/`, with no text. The hook removes a file after 3 days, as the context meter does.
6. Each agent has its own count, so 2 subagents in parallel do not add to one count. A verifier makes no edit, so its probes never count.
7. The key `[harness] fix-limit` is the limit, an integer. `0` turns the hook off. `init` writes `3` for a new configuration of `standard` and `strict`, and `0` for `lite`. A file with no key has the effect of `0`. The harness arms of `eval run` set `0`, so a measure keeps the setup of 0.8.0.
8. The hook says "the person". A project names its own escalation in its instruction files. In this repository, `.claude/agents/ownership.md` sends "The same fix fails 3 times" to `architect` and `failure-analyst`.

The message at the limit:

```text
spec-dna fix limit: this command failed after 3 fixes. Stop the fixes of this problem. Tell the person the command, the cause that each fix assumed, the error now, and the next step that you propose. A subagent ends its report with `State: BLOCKED`.
```

**Files and agents**:

- `init-engineer`: `src/hook.rs` (the hook), `src/harness.rs` (the 3 settings entries), the preset of the key in `src/init.rs` and `docs/init.md`, `docs/harness.md`, the `hook` section of `docs/commands.md`, `tests/hook.rs` and `tests/init_profiles.rs`.
- `diagnostics-engineer`: the function `check` of `src/harness.rs` for the 3 entries, and the section "Check" of `docs/harness.md`.
- `core-engineer`: the key `fix-limit` in `src/config.rs`, `schema/spec-dna.schema.json` and `docs/config.md`, and the value `0` in the harness arms of `src/eval_run.rs`.
- `architect`: the amendment of ADR 0004 for the hash in the state file.
- Change sets: "Hook", "Harness role or generated file" and "Config key".
- Proof: `tests/hook.rs`. The sequence failure, edit, failure, edit, failure, edit, failure gives the message at the fourth failure, and only once. Failures with no edit between give no message. A pass deletes the count. An edit below an `--intent` folder sets no mark. The state files hold no byte of the command.

**Cost**:

- One process for each shell call and each edit. It reads stdin and writes at most one small file. It runs no git and uses no network.
- The message has about 250 bytes, once for each key that reaches the limit.
- ADR 0004 says that no hook stores command text. The hash is no text, but it comes from a command. The amendment states the rule: a hash of 8 bytes with the session id as salt, in the temporary folder, removed after 3 days.

**Does not prove**:

- That the agent stops. The message is context, and `PostToolUseFailure` cannot block (E3).
- A fix through `Bash`, such as `sed -i`, sets no edit mark.
- A command in a pipe, such as `cargo test | tail`, has the exit code of the last command, so the hook sees no failure.
- A changed command, such as `pytest -x` after `pytest`, starts a new count.
- 3 fixes by 3 subagents in sequence: each agent has its own count. The text rule of `debug` covers this case.
- A command that runs the whole test suite counts different defects as one problem, until the command passes once.

**Questions**:

**Q4. Where does the count live?** (a) The text rule only, as now. (b) The hook, with a state file. Recommendation: (b).

**Q5. What is "the same problem"?** (a) The same command. (b) The same first line of the error. This needs a read of the output, and each tool has its own error format. (c) The same failed test. This needs a parser for each test runner. Recommendation: (a).

**Q6. What does the hook do at the limit?** (a) The message only. (b) Also a question to the person before the next edit of that agent, through a `PreToolUse` entry on `Edit|Write`. In `claude -p`, nobody answers, so Claude Code denies the edit. Recommendation: (a). Change to (b) if the transcripts show that agents ignore the message.

## 6. Item 20: lessons

**Problem**:

An agent finds a fact that the rules and the skills of the project do not state. It uses the fact once, and the next agent must find it again. Example: the tests of a module need a database that a fixture starts. No rule says so, and each new agent loses time on the same failure.

**Mechanism**:

1. A lesson is one fact that a rule, an instruction file or a skill of the project does not state yet. Its form in a report:

    ```text
    Lessons:
    - Target: <file>. Text: <the sentence to add>. Evidence: <what happened>.
    ```

2. A subagent adds the part when it has a lesson, before the state line (line 5 of the card, item 18).
3. At the end of a change, the main session lists the lessons of the change, with the lessons of its subagents. `spec-dna finish` prints one note on stderr at success, as its other notes: `note: list the lessons of this change for the person: the target file, the text and the evidence of each; edit no target file before the person accepts the lesson`. The `--json` output does not change. The note prints in `standard` and `strict`, and not in `lite`. Thus each agent gets the rule at the end of a change, and no skill text changes.
4. Nothing goes into the repository before the person accepts a lesson. The lessons stay in the report, and the main session puts them in the body of the pull request.
5. The person accepts or rejects each lesson in the chat. An accepted lesson enters by the class of its target:

    | Target | Example | How the lesson enters |
    | --- | --- | --- |
    | An instruction file or a skill that a person writes | `AGENTS.md`, the text of `CLAUDE.md` outside the generated lines, a skill of the project | The agent edits the file in a commit of its own, after the word of the person in the chat |
    | A document with a status | A rule or a decision | The change process of the project: `spec-dna new intent <slug>` |
    | A generated file | A file with a spec-dna marker line | No edit, because `check` reports SD501. The person sends the lesson to the maintainers of spec-dna |

6. The agent never edits a target on its own initiative. The rule has the same form as the rule of the approval commit. The pull request shows each edit to the person who merges it. A document with a status also needs its approval (SD910 with `approval = "branch"`).

**Files and agents**:

- `hygiene-engineer`: the note in `src/finish.rs`, the `finish` section of `docs/commands.md`, `tests/finish.rs`.
- `init-engineer`: line 5 of the card (item 18) and `docs/harness.md`.
- `architect` for the facts and `docs-editor` for the language: `docs/guides/change.md` and the term `lesson` in `docs/glossary.md`.
- Change set: "Command, option, help text or exit code" for the note of `finish`.
- Proof: `tests/finish.rs`. A success in `standard` prints the note on stderr. A stop, and a success in `lite`, print no note. The `--json` output is the same as before.

**Cost**:

- The note has about 160 bytes, once for each change. It also enters each measured run of the evals of `finish`. The text of the skill and its frozen hash do not change, but the verdict of `finish` measured runs with no note.
- The part `Lessons:` costs output tokens of the agent, only when the agent has a lesson.
- No rerun of an eval. A step in the skill `finish` would need a cut of other text, because its body has 2,499 of 2,500 bytes (E12). It would also need a rerun of the evals of `finish`. The last rerun cost 28.57 USD (E11).

**Does not prove**:

- That a lesson is true or general. The person decides.
- That an agent writes its lessons. The note asks for them, and no check reads the report.
- That a lesson stays. A lesson that the person does not answer stays only in the pull request.

**Questions**:

**Q7. Where do the lessons wait for the person?** (a) Nowhere in the repository: in the report and in the pull request. (b) A file `lessons.md` in the folder of the change. `accept` refuses an untracked file in the folder, and `finish` deletes the folder. An archive under `.spec-dna/accepted/` meets the hook `protect-approvals`, which denies a new file there. (c) One lessons file of the project. Agents can read its text as a rule before a person accepts it. Recommendation: (a).

**Q8. Where does the lesson rule of the main session live?** (a) A note of the command `finish`, for each agent. (b) A step of the skill `finish`: a cut of other text, and a rerun. (c) One sentence in the model-team line, which each request sends. Recommendation: (a).

**Q9. Does a hook guard the targets?** (a) No: the rule and the pull request. (b) A hook that asks the person before an edit of an instruction file or a skill of the project. `protect-tests` asks in the same way for a test file. Recommendation: (a). The trust root stays the person who merges (ADR 0032).

## 7. Item 21: the cost report

**Problem**:

`spec-dna transcript` gives tokens, not USD. It gives no sum for one change, one model or one role. Example: the person wants the cost of the change `sensor-timeout`, with 3 sessions, 4 subagents and some advisor calls. The person must price each model by hand, and cannot tell which sessions belong to the change.

**Mechanism**:

1. `spec-dna transcript <file or folder>... --cost [--change <slug>] [--prices <file>] [--json]` is a mode of `transcript`. It uses the same adapters, the same count of each request by its id (E8), and the same privacy rule. It prints the cost in place of the read report. A folder argument also gives the files of the subagents. When a session has calls of the tool `Agent` and no file of a subagent, the report says so.
2. The price table has one row for each model id. A row gives the USD for 1 million tokens of input, output, a 5-minute cache write, a 1-hour cache write and a cache read. The table has a date and the address of its source page. A table in the binary is the default (`src/prices.rs`), beside the table of model ids of the release. `--prices <file>` reads a TOML file with the same columns, and its rows replace the rows of the same model.
3. The count:
    - Input, output and cache read: the tokens of each request, at the rate of the model of the request.
    - Cache writes: with the split of the usage (E7), each part at its own rate. With no split, all at the 5-minute rate, and the result has the mark `estimated`.
    - The advisor: the count of `server_tool_use` blocks with the name `advisor` (E5). The usage of the request has no tokens of the advisor (E7). Thus each call gives a lower limit. It is the context of the request with the call (input, cache read and cache write), at the input rate of the advisor model. The model is `advisor` of `[harness.roles]`, else no price.
    - A model with no row has no price. Its USD is `null`, the output lists it in `unpriced`, and the total has the mark `partial`.
4. The role of a request is `main`, `advisor`, or the type of the subagent that made it. The build confirms which field of the transcript gives the type.
5. The change of an episode, in this order:
    - `--change <slug>` puts each given session on that slug.
    - The slug that an episode names: the argument of `spec-dna new intent`, `next`, `accept`, `approve` or `finish`, or an edit below `<intent folder>/<slug>/`.
    - The session of an acceptor entry in a record or in the archive (`accept --session`).
    - Else, the slug of the episode before it in the same agent. A subagent gets the slug of the main agent at its start. With none, the change is `null`.
6. The new printed fields keep the privacy rule. A slug prints only when it names a change of the repository. That is a change folder of the head tree, a record under `.spec-dna/accepted/`, or a change that `spec-dna log` lists. Else the change is `null`. A role prints only when it matches the pattern of a tool name, else `<redacted>`. The output has no path and no text of the transcript. The field `tokens.cache_creation` keeps its meaning. The split is in 2 new fields.

An example. The prices file has example values, not real prices:

```toml

[model-x]
input = 1.0
output = 5.0
cache-write-5m = 1.25
cache-write-1h = 2.0
cache-read = 0.1
```

The token counts are those of `tests/fixtures/transcripts/session-1.jsonl`: 9 requests of `model-x`, with 23 input, 1,200 cache write, 10,930 cache read and 170 output tokens. The fixture has no split, and it names no change. `spec-dna transcript tests/fixtures/transcripts/session-1.jsonl --cost --prices example.toml --json` gives:


**Files and agents**:

- `transcript-engineer`: `src/transcript.rs`, the reader in `src/json.rs`, `src/prices.rs` (new), `docs/transcript.md`, the `transcript` section of `docs/commands.md`, new fixtures in `tests/fixtures/transcripts*/` (an advisor call, the split of the cache writes, a subagent with a type), and the cases in `tests/cli.rs`.

- `release-engineer`: compares the table with the public price page before each release. `architect` adds the step to `.claude/agents/release-engineer.md`. The owner accepts a new row in the release pull request.
- Change sets: "Transcript format or output", "Command, option, help text or exit code" and "`--json` shape".
- Proof: the sums of each new fixture in `tests/cli.rs`, and a test with secret text in each field, as for the read report. In the lab, for one headless run, the total of the report must agree with the `total_cost_usd` that `eval run` records (E6). The difference must come only from the advisor part and from the last decimal places.

**Cost**:

- No dependency and no network. The command reads the transcripts and, for the slugs, the head tree.
- A release that has an old table gives an old price. The output names the date of the table.
- No byte in a request of an agent: a person runs the command.

**Does not prove**:

## 8. Item 22: `outline`

**Problem**:

An agent must change one function in a long source file. It reads the whole file, and the file stays in its context for each later request. The agent has no map of the file, so it cannot read only the part that it needs.

**Mechanism**:

1. `spec-dna outline <path>... [--json]` prints the definitions of each file with their line ranges. The agent then reads one range, for example with the `offset` and `limit` of its read tool.
2. The paths follow the rule of `context` (E14). Git tracks the path, or the path is relative, has no `..` and names a file of the working tree. The command reads no `spec-dna.toml`, so it works in each git repository.
3. A definition starts at a line that the rule of the language finds. Comments, doc comments, attributes and decorators directly above it belong to it.
4. A definition ends before the next start of the same or a lower depth, and before the comments and attributes of that start. Blank lines at its end do not belong to it.
5. Depth 0 is the top level. Depth 1 is a member of a container: an `impl`, `trait` or `mod` block, or a class. A member ends at the end of its container at the latest. A last line of the container that holds only the bracket that closes it, such as `}`, belongs to the container, not to the member. The lines before the first definition are the item `(header)`.
6. Thus each line that is not blank is in a range of depth 0. A start that the rule does not see adds its lines to the definition before it. A false start splits one definition into 2 adjacent ranges. The ranges lose no line, and 2 adjacent ranges give the whole definition.
7. Each rule skips the lines inside a multi-line string or comment, when the language has a simple marker for it. Examples are `"""` in Python and `/*` in the C family.
8. Limits: a file of at most 4 MiB with no NUL byte (E13), and at most 300 items for each file. A longer list ends with the line `<n> more items`. The text of an item is its start line with no indent and no final `{`, at most 120 characters.
9. For an unknown language, a binary file or a larger file, the output gives the path and the line count, with no items. A note gives the reason, for example `no outline rule for this file type; read it by ranges`. With `--json`, `language` is `null` and `items` is empty.
10. Exit codes: 0 for an outline or a note, 2 for no path, 5 for a path that names no file (as `context`).

| Family | Extensions | Depth 0 | Depth 1 |
| --- | --- | --- | --- |
| Rust | `.rs` | A line with no indent: `fn`, `struct`, `enum`, `union`, `trait`, `impl`, `mod`, `type`, `const`, `static` or `macro_rules!`, after `pub` and other modifiers | The same words with one indent level, in an `impl`, `trait` or `mod` block |
| Python | `.py` | `def`, `async def` or `class` with no indent | `def` or `async def` in a class, with one indent level |
| Go | `.go` | `func`, `type`, `var` or `const` with no indent. A method `func (r T) Name` is depth 0 | None |
| JavaScript and TypeScript | `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.tsx` | `function`, `class`, `interface`, `type`, `enum`, or `const`, `let` or `var` with a name and `=`, with no indent. Also after `export` or `export default` | A method, `get`, `set` or a field with a modifier, with one indent level in a class |
| Java | `.java` | `class`, `interface`, `enum` or `record`, after its modifiers | A method or a constructor with one indent level: a name and `(` before `{` |

An example. The file `src/valve.rs` has 19 lines:

```rust
use std::time::Duration;

/// A valve of the line.
pub struct Valve {
    open: bool,
}

impl Valve {
    pub fn open(&mut self) {
        self.open = true;
    }

    pub fn close(&mut self, wait: Duration) {
        std::thread::sleep(wait);
        self.open = false;
    }
}

fn main() {}
```

`spec-dna outline src/valve.rs` prints:

```text
src/valve.rs: rust, 19 lines
1-1 (header)
3-6 pub struct Valve
8-17 impl Valve
  9-11 pub fn open(&mut self)
  13-16 pub fn close(&mut self, wait: Duration)
19-19 fn main() {}
```

With `--json`:

```json
{"files":[{"path":"src/valve.rs","language":"rust","lines":19,"items":[{"start":1,"end":1,"depth":0,"kind":"header","name":null,"text":null},{"start":3,"end":6,"depth":0,"kind":"struct","name":"Valve","text":"pub struct Valve"},{"start":8,"end":17,"depth":0,"kind":"impl","name":"Valve","text":"impl Valve"},{"start":9,"end":11,"depth":1,"kind":"fn","name":"open","text":"pub fn open(&mut self)"},{"start":13,"end":16,"depth":1,"kind":"fn","name":"close","text":"pub fn close(&mut self, wait: Duration)"},{"start":19,"end":19,"depth":0,"kind":"fn","name":"main","text":"fn main() {}"}],"more":0,"note":null}]}
```

The relation to the other commands:

- `context <file>` gives the documents that cite the file: the reason for the code. `outline <file>` gives the map of the code. `show` reads a document by its id. An agent runs `context`, then `outline`, then reads one range.
- `outline` reads no document, so a change of the corpus does not change its output.
- `transcript` counts the spec-dna subcommands from a fixed list. `outline` joins the list, so a measure can count its use. Without it, `outline` counts as `other`.

**Files and agents**:

- `context-engineer`: `src/outline.rs` (new), the `outline` section of `docs/commands.md`, `tests/outline.rs`, and one golden file for each family in `tests/golden/outline/`.
- `core-engineer`: the dispatch, the help and the exit codes in `src/main.rs`, and the summary and the table of exit codes of `docs/commands.md`.
- `transcript-engineer`: the name `outline` in the list of `spec_dna_commands` in `src/transcript.rs`.
- `init-engineer`: the sentence for the agents (Q16), in the change set "Adapter or skill text".
- `test-engineer`: C for the fixtures and the golden files.
- Change sets: "Command, option, help text or exit code" and "`--json` shape". `architect` adds the row of `src/outline.rs` to `.claude/agents/ownership.md`.
- Proof: one golden file for each family, with a container, a doc comment and a multi-line string. A test checks for each golden file that each line that is not blank is in a range of depth 0.

**Cost**:

- No dependency. The rules are lines of code in one module, with one golden file for each family.
- No byte in a request, unless Q16 puts a sentence in a line that each request sends.
- tree-sitter needs a new dependency that the owner approves. Its grammars are C code, so each cross-build needs a C compiler for each target (`scripts/cross-build.sh`).

**Does not prove**:

- That agents use the command. The count of `transcript` can show it.
- That a read by range lowers the cost of a task. An agent can read many ranges. A measure must compare the reads of code files in the transcripts, before and after.
- That a range is exact. A signature on many lines, a macro that makes definitions, generated code, a minified file and code in a string can move a boundary. The agent checks the first and the last line of a range.

**Questions**:

**Q14. Line rules or tree-sitter?** (a) Line rules, no dependency. (b) tree-sitter: exact ranges, a new dependency, and a C compiler in the cross-builds. Recommendation: (a).

**Q15. Which languages in 0.8.1?** (a) The 5 families of the table. (b) Each stack of `MANIFESTS` that `init` detects (`src/detect.rs`), also Ruby, PHP, Elixir, Swift and Dart. Recommendation: (a). A new family is one rule and one golden file.

**Q16. Where do agents learn of `outline`?** (a) The adapter skill `spec-dna`, and the text of `Explore`, which now says "Read a large file in parts". (b) Also the line of `AGENTS.md` and `CLAUDE.md`, which each request sends. The line has a limit of 400 bytes. (c) The first message of the context meter, at the time when the context is large. Recommendation: (a).
