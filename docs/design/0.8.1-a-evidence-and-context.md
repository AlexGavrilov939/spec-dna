# Design of spec-dna 0.8.1, part A: evidence and context

Status: a design for the owner. It adds no code. It settles the contracts of items 1, 2, 3, 4 and 10 of part A of 0.8.1, and of the issues 111 and 113, as the decisions D82 to D86. The [design of 0.8.0](0.8.0.md) ends at D81, and this page uses its form. [Section 7](#7-amendments-for-the-owner) gives the text of the amendments of ADR 0024 and ADR 0028 for the owner to accept. [Section 10](#10-what-stays-open) asks Q1 to Q3. The names E1 to E24 and Q1 to Q3 are local to this page.

## Overview

| --- | --- | --- | --- |

A bind by name only gives SD621 | 0024 (amendment) | A tag above no test, and a `case:` with a part of a name, prove nothing until the author moves the tag or writes the full name |
| 2 Summaries in `context` | D83: the tier `summary` fills the title sections first, from the deepest summary up, and uses at most a half of the budget | 0028 (amendment) | `context` serves the summary of the area of the file |

| A test file outside the tree hash (issue 113) | D85: a tag proves a requirement only in a test file of the code tree | 0024 (amendment) | `git add` a new test file before the tests and the stamp |
| 10 One page for the test reports | D85: the new page `docs/test-report.md` | none | One reference page |
| 4 A plan older than 0.8.0 | D86: one note line in `next` and `finish`. A record in the folder of the change opts in | none | One line, and a way to opt in |

The upgrade from 0.8.0, in short:

- `check` without `--reports` gives the output of 0.8.0. The bind rule applies only where a report is read.
- A tag that bound by the rule of 0.8.0 and binds no test now makes its requirement unproven. SD616 is a state code and SD617 is new only for the requirements of the change that `finish` finishes. Thus such a tag stops a gate only at the `finish` of a change that touches its requirement. D82 gives the fix. This is the one item where a current corpus needs edits: the bind of 0.8.0 was a false proof in each of these cases.
- With no key `rolls-up`, the roll-up gives the result of 0.8.0, and SD646 is the one new finding (a warning in `standard`).

## 2. The bind of a tag (item 1)

### D82. A tag binds the test under it

**Problem**:

A tag can prove a requirement through a test that does not check it. Example: `tests/valves.test.ts` starts with `// covers: requirements/valves/closing#close-on-timeout`, and the next line is `import { describe, it, expect } from 'vitest'`. The block of the tag starts at the import line. No other word or literal of the block names a case of the report, so the bind tries the keyword `it` last. The case `Pumps > stops it` of `tests/pumps.test.ts` ends with a space and `it`, and its Vitest `classname` is a path, which names no test file by the dotted rule. Thus the case binds a tag of any file (E1, E2). The case passed, and `close-on-timeout` reads as proven (E22). In a real project, requirements of other tests read as proven in this way.

**Mechanism**:

1. The test of a tag. The scan starts at the line after the tag and reads at most 50 lines. It skips these lines:
    - a blank line;
    - a comment line, as today (`//`, `/*`, `*`, `--`, `<!--`, and `#` that does not start `#[`);
    - a decorator, an annotation or an attribute: an item at the start of a line that is `@<name>` with an optional group `(...)`, `#[...]` or `[...]`. An item continues on the next lines while one of its brackets `(`, `[` or `{` stays open. The count of the brackets ignores the text in quotes. The scan removes each such item from the start of the line. When text stays after the items, that text is the definition line: `@Test fun closes() {` and `[Fact] public void ClosesOnTimeout()` are tests with an annotation. When no text stays, the scan skips the line.

    The first other line is the definition line. A definition on the line of the tag, before `covers:`, is the test of the tag (`def test_x():  # covers: ...`).
2. The forms of a test. The definition line is a test when one form of this closed list matches it. The first form that matches decides. The forms apply to each file, so the rule needs no language detection and no new dependency.

    | Form | Languages | The definition line | The name of the test |
    | --- | --- | --- | --- |
    | `def` | Python | `def <name>(` or `async def <name>(` | `<name>` |
    | `fn` | Rust | `fn <name>(`, after any of `pub`, `pub(crate)`, `async`, `const` and `unsafe` | `<name>` |
    | `func` | Go | `func <Name>(`, or `func (<receiver>) <Name>(` | `<Name>` |
    | call | JavaScript, TypeScript, Ruby | `it`, `test`, `specify`, `example` or `scenario`, with any of `.only`, `.skip`, `.todo`, `.concurrent` and `.failing`, then `(` or a space, then a literal in `'`, `"` or a backtick | the text of the literal |
    | method | Java, Kotlin, C#, PHP, Scala | a word and `(`, where the skipped lines had an annotation or an attribute, or the line has `void`, `fun`, `function` or `def` before the word. In Kotlin, `` fun `<text>`( `` | the word, or the text in the backticks |
    | explicit | each | `case:<name>` in the tag (item 8) | `<name>` |

3. No test. A tag binds no case in these cases, and the reason goes into SD616 and SD617:
    - `no-test`: the definition line matches no form, for example an import, a statement in the body of a test, or a helper function that a runner does not collect. A tag in the body of a test is such a case.
    - `group`: the definition line opens a group: it starts with `describe`, `context` or `suite` (with `(` or a space), or with `class`, `object`, `mod`, `impl`, `module` or `namespace` and a space. A tag above a group binds no test of the group.
    - `template`: the literal of a call has a placeholder (`%`, `$`, `${` or `#{`), or the call has `.each`. One literal gives many names.

    The fix of each is to put the tag on the line above one test, or to add `case:"<name>"`.
4. The name forms. A case names the test only in the forms of this closed list. Each form is one test that gives one case or more:
    - The forms `def`, `fn`, `func` and method. The head of the case name is the part before the first `(`, `[`, `/` or space. `::` and `.` split the head into segments. The case names the test when the name of the test is one segment of the head. Examples: `test_closes[1-2]` (pytest parameters), `tests::closes` (a module path of nextest), `closes::case_1` (the cases of a Rust macro), `TestTimeout/no_reply` (a Go subtest), `test1(String) [1] a` (JUnit 5 parameters), `testOne with data set #0` (PHPUnit data), `ValveTest.ClosesOnTimeout` (.NET with `MethodFormat=Class`).
    - The form call. The case name equals the literal, or ends with the literal after one of ` `, ` > ` and ` › `. Examples: `closes on timeout`, `Valves closes on timeout` (jest-junit, RSpec), `Valves > closes on timeout` (Vitest).
    - A word of the block that is not the name of the test never binds. The keywords of 0.8.0 (`KEYWORDS`) go.
5. 2 tests that one case names. A case can name 2 tests of the file. Example: the case `Valves never closes` ends with both `closes` and `never closes`. The case belongs to the test whose name ends nearer the end of the case name, and on a tie to the test with the longer name. Thus it belongs to `it('never closes', ...)`, and a tag above `it('closes', ...)` does not bind it.
6. The file of a case. A case fits the test file of the tag by the first row that applies:

    | The case has | It fits the test file of the tag when | Runners |
    | --- | --- | --- |
    | `file` | the 2 paths are equal, or one ends with `/` and the other. `./` at the start goes, and `\` reads as `/` | pytest `xunit1`, PHPUnit, RSpec, jest-junit with `addFileAttribute`, the line format |
    | a `classname` with `::` | the part after the last `::`, and after its last `/`, is the stem of the test file, or the name of its folder when the stem is `main` | cargo-nextest |
    | a `classname` with `/`, whose last segment has a `.` | the `classname` is the path of the test file, by the rule of `file` | Vitest, jest-junit with `classNameTemplate: "{filepath}"` |
    | a `classname` with `/` | the folder of the test file ends the `classname` in whole segments. When several folders do, only the longest one fits | go-junit-report, gotestsum `full` and `relative` |
    | another `classname` | `$` reads as `.`. The dotted path of the test file ends with the `classname`, or with its part before the last `.`, in whole segments. A `classname` of one segment also fits a test file whose folder ends with it | pytest `xunit2`, JUnit, .NET, gotestsum `short` |

    When the row names no test file of the tree, the case fits by its name only. A case with no `file` and no `classname` also fits by its name only (a line of the line format with `-`). The test files are the test files of the code tree and the test files that git does not track, as today: more files only narrow a fit. The rule of 0.8.0 "when no test file has such a path, the case binds a tag of any test file" goes.

    The precedence: when one case of the test fits by `file` or by `classname`, the cases that fit by name only do not bind the tag. Thus a passed case of an unknown file never hides a skipped case of the file of the tag.
7. Shared cases. The cases of a tag are shared in 2 cases: 2 tests of the file have the name of the test, or the cases that fit by name only are not one case (one name, `classname` and `file`, at most once in each report). A shared set proves the requirement only when each of its cases passed. Thus a skipped twin never hides behind a passed twin.
8. `case:<name>`. The tag binds the cases whose name equals the value, byte for byte. It needs no test under the tag. The partial match of 0.8.0 goes. A case with a `file` binds only when the file is the file of the tag. For a case with no `file`, the `classname` does not exclude the case. It only decides the strength (item 9): the bind is exact when the `classname` names the file of the tag, or when the fresh reports have one case of that name. Else it is a bind by name (SD621), and the precedence of item 6 applies. Thus `case:` is the escape for each layout that the file rule reads wrongly. A value in double quotes can hold a space and a `#`. A binary before 0.8.0 read a `#` after `case:` as an id, but a tree that pins 0.8.1 does not run with such a binary, so the limit of 0.8.0 on `#` goes too.
9. The strength of a bind. A bind is exact when each bound case fits by `file` or by `classname`, or when `case:` names it and the fresh reports have one case of that name (one name, `classname` and `file`). Else it is a bind by name, and SD621 reports the tag. A bind by name counts: the requirement is proven when its cases passed. SD621 makes the weak link visible, and the profile sets its weight.
10. The proof. As in 0.8.0: a requirement passed when at least one bound case passed and no bound case failed. A skipped case is no pass. A pass after a rerun is a fail. A shared set (item 7) needs a pass of each case.

Two limits of the runners. A nextest report has no skipped test by default (E6), so the tag of a skipped test finds no case (`no-case`), and the requirement stays unproven: this is the correct result. Surefire with the phrased names on writes the display names, so the name of the method is not a segment of the case name, and the tag needs `case:`.

**Formats**:

The reasons of SD616 and SD617 for a tag with no passed case, a closed list. The text of `failed` and `skipped` stays as in 0.8.0:

| Reason | Text of the message |
| --- | --- |
| `no-test` | ``the tag at <path>:<line> stands above no test (line <n> is not a test); put the tag on the line above the test, or add `case:"<name>"` `` |
| `group` | ``the tag at <path>:<line> stands above a group, not a test; put the tag above one test, or add `case:"<name>"` `` |
| `template` | ``the test under the tag at <path>:<line> has a template name; add `case:"<name>"` with one name of the report`` |
| `no-case` | ``no case of a fresh report names the test `<name>` of the tag at <path>:<line> in that file; check the name, or add `case:"<name>"` `` |
| `outside-tree` | the text of D85 |
| shared | ``the tests of the name `<name>` in <path> share their cases, and the case `<case>` was skipped`` (or `failed`) |

`show` gets the option `--reports`:

```text
spec-dna show <id>[#<anchor>] [--reports] [--json]
```

- Without `--reports`, the evidence line of each full tag adds the test under the tag, from the test file: `- requirements/valves/closing#close-on-timeout: tests/test_valves.py:12 [test test_closes_on_timeout]`. A tag with no test shows its reason: `[no test: no-test]`.
- With `--reports` and a `[evidence] reports` list that is not empty, `show` reads the reports as `check --reports` does, and the line shows the result: `tests/test_valves.py:12 [passed test_closes_on_timeout]`, `[skipped test_closes_on_timeout]`, `[passed Valves closes on timeout, by name]` or `[unbound: no-case]`. With no fresh report, the line says `[unbound: no-report]`. With no key, `--reports` changes nothing. `--reports` with `--conventions` is a usage error (exit code 2).
- A `verified-by` source and a partial tag get no bracket.

`show --json`: each item of `evidence` keeps `key`, `sources` (a list of strings, as in 0.8.0) and `partial`, and gets the new field `binds`. It has one object for each full tag, in the order of `sources`, and it is empty when the requirement has no full tag:

```json
{"key":"close-on-timeout","sources":["tests/test_valves.py:12"],"partial":[],"binds":[{"tag":"tests/test_valves.py:12","test":"test_closes_on_timeout","by":"definition","case":"test_closes_on_timeout","cases":1,"fit":"classname","shared":false,"result":"passed","reason":null}]}
```

| Field | Value |
| --- | --- |
| `tag` | `<path>:<line>` of the tag, the string of `sources` |
| `test` | the name of the test under the tag, or the value of `case:`; `null` for `no-test` and `group` |
| `by` | `"definition"` or `"case"` |
| `case` | the name of the case that decides the result, as SD616 and SD617 name it; `null` with no bound case or without `--reports` |
| `cases` | the number of bound cases; `0` without `--reports` |
| `fit` | `"file"`, `"classname"` or `"name"`; `null` with no bound case |
| `shared` | `true` for a shared set (item 7) |
| `result` | `"passed"`, `"failed"`, `"skipped"`, `"unbound"`, or `"not-read"` without `--reports` |

## 3. The tier `summary` in `context` (item 2)

### D83. Title sections first, and a half of the budget

**Problem**:

`context` never serves a summary when the top documents are larger than the share of the tier (E14). Example: the fixture below has a `product` and a `system` document of about 4,100 bytes each, with `rests-on`, and a summary of the area of `src/motor.rs`. `context src/motor.rs` serves the title of `product` and 2 of its sections, lists 6 stubs, and gives no line of `system` and none of the summaries. At the default budget the output uses 2,277 of the 8,000 characters, so the budget is not the limit: the share of the tier is (E15).

The defect has 2 causes:

- A: the tier fills its sections in the output order. Each section of `product`, then each section of `system`, comes before the first summary. The share ends inside `product`.
- B: a summary can have 3,000 to 6,000 characters (the budget of its type), but the share is a quarter of the budget, 2,000 of 8,000. A summary over about 1,950 characters is never in full at the default budget, also with no top document.

**Mechanism**:

1. The documents of the tier do not change. They are the chain of the request: each `product` and `system` document with `rests-on`, and the summary of each area that the plan serves, with the summaries of the areas above it.
2. The output order does not change: from the top down, `product`, `system`, then the summaries from the shallow folder to the deep one. In each document, the title section comes first.
3. The fill order is new (cause A). The tier fills its sections in this order:
    1. the title section of each document of the chain, from the deepest summary up: the deep summaries before the shallow ones (by id in one depth), then `system`, then `product`;
    2. the other sections, in the same order of the documents, each document in heading order.
4. The share is new (cause B). The tier, in full text and in stubs together, uses at most a half of the budget: 4,000 of the 8,000 characters of the default. A summary at its soft budget (3,000 characters) and its header fit at the default budget.
5. The fill. The sections of the fill order are in full while each fits in the rest of the share. From the first section that does not fit in full, each later section of the fill order is a stub while the rest of the share has room for its stub line. The other sections are not listed. The line `<!-- <n> more sections did not fit; raise --budget to list them -->` counts them, as for the other tiers. Thus the served sections are a prefix of the fill order: no title is cut while a later section is in full.
6. The tier still comes after the sections of the entry and of the citing documents in the packing order, so it never takes their room. The share is a limit, not a reserve: a small chain uses less.
7. A stub of the tier keeps the form of the other tiers: id, hash, size, tier and heading, and `[stale]` for a stale document. Example: ``- `summaries/valves#valves` h:5d0e7c2a91b3f4e8 2960 chars (summary): valves``. A stub tells the agent that the summary exists. `spec-dna show summaries/valves` reads it.

**Formats**:

- The text and the `--json` output keep their form. A unit of the tier keeps `"tier":"summary"`, `"mode"` and `"stale"`, and the units stay in the output order. Only the set of the units in full and in stubs changes.
- The `context` section of `docs/commands.md` changes 2 sentences: the fill order (item 3), and "uses at most a half of the budget: 4,000 of the 8,000 characters of the default".

**Codes**: none. **Config**: none: the share stays a constant of the tier.

## 4. Interfaces, decisions and research in the roll-up (item 3, issue 111)

### D84. The source layers of the roll-up

**Problem**:

The roll-up pins only the active requirements of the layer `requirements` (E17). Example: a project keeps its decisions in `decisions/storage/` and its studies in `research/storage/`. `summaries/storage.md` gives SD644, because `requirements/storage/` does not exist. A pin to `decisions/storage/use-sqlite` gives SD643. A project with only decisions and research gets no benefit from the roll-up. The same holds for the interfaces, whose documents have requirement keys.

**Mechanism**:

1. The source layers. The layer whose types hold `summary` gets the key `rolls-up`: a list of layer names. The default is the layer whose types hold `requirements`, so a project with no key keeps the result of 0.8.0. Each name is a layer of `[layers]` whose types hold `requirements`, `interface`, `rule`, `decision` or `research`. Another name, the key on a layer with no type `summary`, and a source layer whose folder is inside the folder of another source layer are errors of the configuration (exit code 3).
2. The area. `<summaries folder>/<area>.md` is the summary of the folder `<area>` under the folder of each source layer. The area exists when one source layer has the folder. The name of an area is a path from the folder of each source layer, so an area of the requirements with the name of a layer does not mix with that layer: `summaries/decisions.md` is the summary of `requirements/decisions/` and of `decisions/decisions/`. SD644 keeps its meaning: the path of the summary names no area. The root area is the folder of each source layer: a `system` document with `rests-on` rests on the root area.
3. The items of the frontier, by the type of the source document:

    | Type of the source | Item | Pin | In the frontier when | A pin no longer holds |
    | --- | --- | --- | --- | --- |
    | `requirements`, `interface`, `rule` | each requirement | `<doc-id>#<key>@<hash>`, as in 0.8.0 | the document is `active` | SD641: its text changed, it was removed, it is not active, or it left the frontier |
    | `decision` | the whole document | `<doc-id>@<hash>`: the hash of the text in force | the status is `accepted` | SD641: the text in force changed (an amendment), or the decision is no longer `accepted`. The message names the successor of a `superseded` decision |
    | `research` | the whole document | `<doc-id>@<hash>`: the hash of the text in force | always (the type has no status) | SD647, a warning: the note changed, was removed, or left the frontier |

    An interface document thus gives its requirement keys, not one hash of the whole document. The reasons: the same pin, the same compare (`hash_matches`) and the same active rule as a requirement; the message names the changed key; and an edit of a part with no key does not make the summary stale. An interface document with no key gives no item, as a requirements document with no key.
4. The text in force. A pin to a whole decision or research document matches the hash of its chunks outside the history and live sections, without link destinations. It is the input of `frozen_hash` plus the amendment sections (E18). Thus a new amendment of an accepted decision makes the pin stale, and an edit of its live section `Status` does not. The status is read from the front matter, and the frontier rule of item 3 uses it. The hash is a second definition of a document hash for a pin, in `src/model.rs`. It combines the frozen hashes of the chunks that the parser gives and the cache holds, as `frozen_hash` does (`src/model.rs:1199-1205`, `src/index.rs:307-308`). Thus `src/hash.rs`, `src/parse.rs`, the cache and `PARSER_VERSION` do not change. A pin to a summary, a `system` or a `product` document keeps `frozen_hash`.
5. A pin resolves as in 0.8.0: the aliases of a moved document, the aliases of a moved key, the section aliases of a split and the legacy ids.
6. SD643 keeps its meaning: a pin names a target that no frontier can hold. With `rolls-up`, a decision or a research document of a source layer is such a target only when it is not in a source layer.
7. A roll-up document that rests on nothing. A summary with no pin and an empty frontier, or a `system` or `product` document with `rests-on: []` and an empty frontier, has no finding today. When another roll-up document pins it, that chain rests on nothing. SD646 reports it on the document that has no pin, with the pinning document as its target. Thus each pinning document gives one finding. SD646 runs only where SD641 and SD642 are silent: an empty frontier gives no SD642, and a `system` with no field `rests-on` stays SD641 at the pin of `product` (the meaning of 0.8.0).
8. `context`. The chain takes the area of each served document of a source layer: an active requirements, interface or rule document, an accepted decision, and a research document that a target names. The key `areas` and the option `--group` keep their rule of the first folder of the layer `requirements`.
9. `refresh` writes the frontier of item 3 with the current hashes. Its guard also refuses a document that has SD647 and the text of the base, so a refresh with no edit after a changed note is a named claim (`--holds`, SD645).
10. `finish` and `next`. The due roll-up documents come from the delta (E19). A delta line names a requirement key, so a source of the types `interface` and `rule` makes a document due as a requirement does. A decision and a research document never make a document due. Their findings show in `check` during the build, because the edit of a decision or a note is in the diff of the branch, not in the delta. `finish` and `next` do not change.
11. `mv` names the summaries whose frontier a move changes, also for a document of a source layer.
12. The budget of the tier `summary` is the one of D83 for each kind of summary.

**Formats**:

```toml
[layers.summaries]
types = ["summary"]
rolls-up = ["requirements", "interfaces", "decisions", "research"]
```

## 5. A test file outside the code tree (issue 113), and one page for the test reports (item 10)

### D85. A tag proves only in a file of the code tree

**Problem**:

A report binds to the hash of the code tree. A test file that git does not track is not in that hash, but its tag can bind a case that passed (E20). Example: `tests/test_new.py` is new and not added. Its tag binds the passed case `tests.test_new::test_new`, and the stamp names the tree. An edit of the file after the stamp does not make the report stale, so the requirement stays proven by a test that no longer exists in that form.

**Mechanism**:

1. The choice: a tag proves a requirement only when its test file is a path of the code tree: git has the file in its index, and `[evidence] tree-exclude` does not match it. A tag in another file binds no case, with the reason `outside-tree`.
2. The tree definition of ADR 0024 does not change. Another choice, an untracked test file in the tree hash, was rejected. The hash would depend on the files of one working copy and would not be the hash of a clean checkout (`git ls-tree`). It would also change the tree of the acceptance record (ADR 0025), and `accept` already refuses an untracked code path of its scope.
3. The test files that git does not track still name their `classname` for the file rule of D82 (more files only narrow a fit), as today.
4. `check` without `--reports` keeps the rule of 0.7.1: a tag alone is evidence, also in an untracked file.

**Formats**: the reason `outside-tree` of SD616 and SD617: ``the tag at <path>:<line> is in a file that is not in the code tree (git does not track it, or `[evidence] tree-exclude` matches it), so the stamp does not cover it; `git add` the file, then run the tests and `spec-dna evidence stamp` again``.

**Codes**: no new code. SD616 and SD617 carry the reason.

**Upgrade**: a project that stamps after `git add`, as the docs say, sees no change. A tag in an untracked file now gives SD617 at `finish`, and the fix is `git add`, the tests and the stamp.

**Cost**: none. The read of the reports computes the paths of the code tree already.

**Does not prove**: that the test file is committed. A file in the index and not in a commit is in the tree, as for each code file of ADR 0024.

**The statement for the docs**, in `docs/test-report.md`, section "The code tree and the stamp": "A tag proves a requirement only when its test file is in the code tree: git has the file in its index, and `tree-exclude` does not match it. A tag in another file binds no test case, and SD616 or SD617 names the file. Run `git add`, then the tests and `spec-dna evidence stamp`." ## 6. A plan older than 0.8.0 (item 4)

### D86. One line, and an opt-in by the record

**Problem**:

A plan that a commit added when `spec-dna.toml` pinned a version before 0.8.0 needs no acceptance record. `finish` prints a note on stderr, and `next` prints nothing (E21). Example: a `higher-risk` change of 0.7.1 is still open after the upgrade. `next` shows the review of 0.7.1 and no word on the record, so the agent does not know that the change skips the acceptance, or how to ask for one.

**Mechanism**:

1. The exemption stays: a plan of an older pin needs no record.
2. `next` and `finish` print one line, the same text, when the change would need a record if its plan were new: the acceptance is on, `[change] acceptance-for` or a role of `[owners]` asks for it, and the plan is approved and old.
3. The opt-in: a file `acceptance.toml` in the folder of the change ends the exemption for that change. The need rule then gives the result of a new plan: `next` shows the record item, and step 5.2 of `finish` checks the record as for a change of 0.8.0 (SD927 to SD933, SD941). Today `finish` checks only the structure of such a record (SD928), and `check` already compares its brief. The acceptor writes the file, so the line names the prompt of the acceptor.
4. A change with no record keeps the exemption, and the line repeats in each `next` until `finish`.

**Formats**:

The line, in `next` (stdout, after the checklist, one more line as the note of the roll-up) and in `finish` (stderr, in place of the note of 0.8.0):

```text
note: `docs/intent/dose-limit/plan.md` was added when spec-dna.toml pinned 0.7.1, before 0.8.0, so the change needs no acceptance record; to opt in, start one agent `acceptor` with the prompt `cd '/repo' && spec-dna accept dose-limit --brief`: its record ends the exemption
```

- `<plan>`, `<pin>`, `<root>` and `<slug>` are the values of the change. `<root>` is quoted as in the record item of `next`.
- Where the harness writes no agent `acceptor`, the text says "one agent that did not build the change", as the record item does.
- `next --json`: the line is an entry of `notes`, before the note of the roll-up.
- `docs/commands.md:507` and `:544` change: the output of `next` has at most 12 lines, and the note of the roll-up and this note are one more line each. A change that needs no record has the lines of 0.7.1, plus this note when its plan is old.

The docs on the opt-in, in `docs/config.md`, section "The acceptance record", and in the `next` and `finish` sections of `docs/commands.md`: "A plan that a commit added when `spec-dna.toml` pinned a version before 0.8.0 needs no record. `next` and `finish` print one note for it. To opt in, start the acceptor with the prompt of the note. When the folder of the change has `acceptance.toml`, the change needs its record as a change of 0.8.0 does."

**Codes**: none. **Config**: none.

**Upgrade**: a change of 0.7.1 that is open gets one line in `next` and a new text in `finish`. A change of 0.7.1 that already has a record in its folder now gets the full check of step 5.2 at `finish`. The record is in the folder because an agent wrote it, so the check is the intent.

**Cost**: one line in each `next` of such a change: the example line above has 274 bytes with its line end. Only open changes of a version before 0.8.0 have it, so it ends with them.

**Does not prove**: that the old change was reviewed. The line makes the exemption visible. It does not close it.

**Files and agents.** `src/acceptance.rs` (the need rule with the record in the folder, the text of the line): `diagnostics-engineer`. `src/stage.rs` (the note of `next`): `core-engineer`. `src/finish.rs` (the note, step 5.2 with the opt-in): `hygiene-engineer`. `docs/commands.md` (`next`: `core-engineer`; `finish`: `hygiene-engineer`), `docs/config.md`: `core-engineer`.

**Tests** (each fails before the fix, unless it says "guard". The "before" results come from the code of 0.8.0):

- `tests/accept_next.rs`: a `higher-risk` change in `standard` whose plan the base added at the pin 0.7.1: `next` prints the line, byte for byte, and `next --json` has it in `notes` (before: no line).

- The same change in `lite`, or a `routine` change in `standard`: no line (guard).

## 10. What stays open

**Q1. The share of the tier `summary` (D83).** (a) A half of the budget: a summary at its soft budget is in full at the default budget. (b) Keep a quarter: a summary over about 1,950 characters is always a stub at the default budget, and an agent reads it with `show`. (c) The larger of a quarter and the soft budget of the type `summary`, at most a half. Recommendation: (a). It is one constant, and it serves the summary that the type budget allows. (c) gives the same result at the default budget with a more complex rule.

**Q2. The pin of a decision (D84).** (a) A new hash of the text in force: the locked text and the amendments. A new amendment makes the summary stale. (b) `frozen_hash`, with no new hash definition: an amendment does not make the summary stale, and the docs state the limit. Recommendation: (a). In this repository, an amendment changes the rules of an accepted decision, so a summary that does not see it is wrong. The cost is one hash of bytes in memory, and no cache change.

**Q3. The opt-in of an old plan (D86).** (a) A record in the folder of the change ends the exemption, and `finish` checks the record in full. (b) No opt-in: the line says only that the change needs no record. A project that wants a record closes the change and starts a new one. Recommendation: (a). It needs no new key, and the acceptor that `next` already names writes the file.

## Amendment of the build, 2026-11-24

The build of `test-tag-bind` found that some rules of D82 gave a false proof: a rule that lets one case hide another case can drop the failed or skipped case of the test under the tag. The build keeps one rule in their place: no case hides another case. This section lists the rules of D82 items 4, 5, 6, 7 and 9 as the code has them. The text of D82 above stays as it was written.

- Item 4, the name forms. A case names the test when the name of the test is a whole segment of the name of the case. The separators of a segment are ` > `, ` › `, `::`, `/`, `.` and `#`. A name in a literal also matches at the end of the case name after a space (a weak match), unless the case name has a segment of ` > `. The titles of the groups above the test, joined with a space, ` > ` or ` › `, and the name of the test give the expected name, which is a strong match. RSpec reads `RSpec.describe` as a group, and it joins a title that starts with `#` or `.` to the title before it with no space. A template (`it.each(rows)('%s opens')`) is no test of the file and claims no case. A case with a name of more than 256 characters, or with more than 32 separators, has no key but its whole name, and only `case:` binds it (the new reason `long-name`).
- Item 5, 2 tests that one case names. The rule of the nearer name goes. A tag binds each case that item 4 links to its test, so a case that two tests name belongs to both. A test of one name that the file defines twice, a template with the same literal, a group with the title of the test, and a Go test, a suite method and a subtest of one name all give cases to the set.
- Item 6, the file of a case. The rules by row stay. A file of a folder of `tests/` (`tests/it/valves.rs`) also fits the nextest binary id of the folder (`<crate>::it`). The only case that the file rule leaves out is a case that fits by its name only, when another case fits by `file` or by `classname`.
- Item 7, shared cases. The worst case decides in each set that is not one case: a failed case, then a skipped case, then a passed case. A set is not one case when the file has 2 tests of the name, or more than one case fits. The subtests and the rows of a table are in the set, so a skipped row leaves the requirement unproven.
- Item 9, the strength of a bind. A bind is exact when its cases fit by `file` or by `classname`, one of them has the whole name of the test (it equals the name, or its last segment does), and the cases are one test (they differ only after the name of the test), or when `case:` names it and the fresh reports have one case of that name. Else SD621 reports the tag: a case that fits by name only, no case with the whole name of the test (a case only ends with it, or it is a segment of a longer name), or more than one test that fits. The cases of a test that the file defines twice are no cause.

The build leaves these limits as they were in 0.8.0, and the user documentation says so: 2 test files with one name in 2 packages of pytest; the .NET rule that strips a class by its upper case letter; a nextest crate with a name that is not the stem of a test file, and a `src/lib.rs` (they read as proven with SD621); the root package of Go and RSpec files in the root (SD621).

**The rule of the identity, 2026-11-25.** This rule replaces items 4 to 9 of D82 as the list above amends them. Each earlier mechanism let a last segment count as the case of the test, or left out a case because another case fit better, and 4 reviews and 1 acceptance pass found a false proof in them. The rule is now one invariant. A bind is silent only when each of its cases has the identity that the scanner builds from the definition under the tag, and nothing else builds that identity. A case leaves the set only by a field that the report and that identity both hold in full. Each other case that names the test is a weak link (SD621). [Test reports](../test-report.md#the-rule-of-a-bind) gives the rule, the row of each runner and the limits, so this page does not repeat them.

- `case:` (item 8) and the strength of a bind (item 9): one case of a name is exact only when a full field ties it to the tag file.
- SD621 means that no full identity ties the case to the test, or that the identity is not unique. Its causes are `no-identity`, `not-unique` and `by-name`. In `binds`, `fit` is the full field that tied the own cases, and `shared` is true when the worst of more than one identity decided.
- Cost: a bind of a Rust or Go tag also reads the nearest `Cargo.toml` and `go.mod` at or above the test file, each one once. It needs no new dependency.
- A newer Surefire writes the outer class for a test of a nested class. So a nested method with the name of the tagged method makes the identity not unique, and a nested test with the outer `classname` is weak. For a case of the nested class itself, the `$` form of Surefire 3.2.5 is exact.
- JunitXml.TestLogger takes the name of a case from the method in its current source. Other sources can write a display name, so a method with a display name gives a weak bind.

**The check of the rule, 2026-11-25.** A check of the build of the rule found false proofs, binds that were weak or silent in error, and loads that ran for more than 60 s. These changes of the text above follow. [Test reports](../test-report.md#the-rule-of-a-bind) holds the rule, so this list names the changes only.

- Item 6, the scope. A `file` or a `classname` can name each file of the code tree, and each test file that git does not track, not the test files only. The scope applies to the 2 steps that follow.
- A new step: a case whose field names another file in full is another test, also when no row pairs its shape with the form of the tag. The identity that ties a case to the tag file keeps it.
- A unique identity: a call with any modifier counts, now also `.fails`, `.sequential`, `.runIf(...)` and `.skipIf(...)`. So do a template of the same chain that can give the title, a `func` of the same name in another `_test.go` file of the folder, and a line `include_examples` or `include_context` in a group of the chain. For the JVM and .NET, the full class name counts, never the stem of the file.
- Repeats: in one report, a repeat is a run only for the projects of Playwright, which a title with ` › ` or a `[<project>]` prefix shows. A Playwright test with neither is 2 cases.
- A unit test of Rust: `src/lib.rs` and `src/main.rs` tell the target of a module file.
- Cost: a bind reads the nearest manifests, the 2 root files of a crate and the `_test.go` files of the folder of a Go tag, each one once, and it keeps the paths of the code tree. It builds the definitions of a test file and their chains once for all tags. A tag then costs its lines, the cases that can name its test and the definitions with that name. The index has at most 67 keys for a name, and the names over the caps have their keys in a map that serves only the reason `long-name`.

**The class index, 2026-11-25.** A probe of the build found a silent bind: 2 files declared one full class name of the JVM or .NET, and no folder showed the namespace or the package. The count of dotted paths does not see such a twin. So for a tag in a `.java`, `.kt` or `.cs` file, the identity is also not unique when another file of these kinds declares the class. This applies to the test under the tag and to `case:`.

- Cost: a run reads each of these files of the code tree one time, only when such a tag needs it. It keeps a hash of each declared class name and the namespace lines, and no text.
- [Test reports](../test-report.md#the-class-index) gives the rule, and [its limits](../test-report.md#the-limits-of-the-bind) name the declarations that it does not read.
