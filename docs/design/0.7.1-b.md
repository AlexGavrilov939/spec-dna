## 2. Decisions

### B1. A task that runs `finish`

Invariant: `finish` never waits for a task that only `finish` can do.

- One predicate in `src/change.rs`: `PlanTask::closes_with_finish(slug)`. It is true when the text of the task (the part before the first label) holds `spec-dna finish <slug>` with the slug of its change, followed by the end of the text or by a character that is not a letter, a digit, `-` or `_`. Inside a code span it counts.
- `stage::tasks`, `Change::next_open_task` and step 0 of `finish` treat such an open task as closed. Its estimate counts in the hours. When each other task is closed, `next` leaves `build`, and at the stage `deploy` its last line names `spec-dna finish <slug>`.
- The counts line of `next` and `status` gets ``, <n> for `finish` `` after the part `not needed`. `status --json` gets `tasks.finish` (a number).
- Step 0 of `finish`: if an open task holds `spec-dna finish` and the predicate is false, the reason ends with ``; a task closes with `finish` only when its text names `spec-dna finish <slug>` `` (the real slug).
- A review task is a task of a person, not of `finish`. A person ticks it before `finish`. Its `Verify:` names a step before `finish`. It is optional: a project whose owner reviews at the merge writes none.
- `write-plan`, item 7, new text: "7. Write no task for `spec-dna finish`: it runs after the last task. If the owner reviews the code before `finish`, end the plan with `- [ ] tN: Review by the owner. Files: none. Verify: the owner reviewed the code of the pull request. Hours: <n>.` Only the owner ends this task: an agent never ticks it and never writes `Skip:` for it. After the review, a person ticks it with `Actual: <n>`. Then `spec-dna finish <slug>` runs, and its result goes in a commit of the same pull request."
- Files: `src/change.rs`, `src/stage.rs`, `src/finish.rs`, `src/main.rs` (`status --json`), `src/harness_text.rs`, `docs/guides/change.md`, `docs/commands.md` (`next`, `status`, `finish`). Agents: `core-engineer`, `hygiene-engineer` (`finish.rs`), `init-engineer` (skill text).
- Tests: `tests/finish.rs`, "a task that names `spec-dna finish demo` closes with finish": `t1` done, `t2` open as in B1 of section 1; `finish demo` exits 0 and deletes the folder. A second case with ``Run `spec-dna finish` `` (no slug) stops at step 0 with the hint. `tests/lifecycle_commands.rs`: `next demo` is not at `build`, and its last line names `spec-dna finish demo`.

### B2. Spell checkers and the hashes

- The hash forms in text: `h:<16 hex digits>` in each marker (`<!-- spec-dna v… h:… -->`, `<!-- spec-dna:begin … h:… -->`, `<!-- spec-dna harness … h:… -->`), `@<16 hex digits>` in a `CHANGE` or `REMOVE` delta line, and 64 hex digits in `[spec-dna-sha256]`.
- Only typos changes them (section 1). Its pre-commit hook writes its fixes by default, and a marker with a changed hash gives SD501. The pattern covers the delta form also, at no cost, because the second project reports it.
- typos (`_typos.toml`, `typos.toml` or `.typos.toml`): `[default]` and `extend-ignore-re = ['(?:h:|@)[0-9a-f]{16}\b']`. codespell and cspell need no exclude. Another tool: exclude the regular expression `(?:h:|@)[0-9a-f]{16}\b`.
- Detection, a line scan with no YAML parser: a line of `.pre-commit-config.yaml` at the repository root that, with its indent, a leading dash with its space and a trailing comment (a `#` after a space) removed, is `id: <name>` or `entry: <command>`. `<name>`, or the first word of `<command>`, is `typos` or starts with `typos-`. No note if `.pre-commit-config.yaml`, `_typos.toml`, `typos.toml`, `.typos.toml` or `pyproject.toml` holds the text `[0-9a-f]{16}`.
- The note, from `init` (each mode) and `upgrade`: ``note: the pre-commit hook `typos` can rewrite the 16-digit hashes of the spec-dna markers (`h:<hash>`), and a marker with a changed hash gives SD501. Add this line under `[default]` in _typos.toml: extend-ignore-re = ['(?:h:|@)[0-9a-f]{16}\b'] (docs/init.md#spell-checkers)``
- Files: `src/detect.rs` (a new pure function of the file text; no new field of `Facts`), `src/init.rs` (`notes`), `src/upgrade.rs`, `docs/init.md` (section "Spell checkers"). Agent: `init-engineer`.
- Tests: `tests/cli.rs`, init: a hook `- id: typos` gives the note; with `_typos.toml` that holds the pattern, or with `- id: codespell`, no note. `tests/upgrade_cli.rs`: the same for `upgrade`.

### B3. One commit for an upgrade

Cause: 2 rules meet. The exact pin (ADR 0003) makes the hook refuse each commit while the pin is older than the binary, so the upgrade must be the first commit. SD503 compares the whole pull request with the merge base in CI, but only the index with `HEAD` in the hook. Thus the upgrade passes the hook and fails CI when the branch also holds other work. SD913 also warns on each file that `upgrade` writes, because a change of the branch has a plan.

- SD503, in each binary: `spec-dna.toml` does not count when its base text and head text differ only in the pin line and in the table `[spec-dna-sha256]`, and the base pin is a version before the head pin. The compare reads `\r\n` as `\n` (ADR 0019). The tree binary rule of ADR 0013 stays. The pin stays exact. A move back to an earlier version counts, because the head binary is then older than the base pin.
- SD913 does not report a file that SD503 does not count: an adapter, a harness file, a hook file, a starter file of the evals and a file whose name starts with `spec-dna`. One function, `init::is_tool_file(config, path)`, holds this list for both codes.
- `upgrade` prints one line after `to commit:`. It reads its own list of the edits of `spec-dna.toml` beyond the pin (the report has it), so it needs no new compare:
  - Pin only: ``next: commit the paths above in one commit of their own. Only the pin of spec-dna.toml changes, so the pull request can also hold other work (SD503 does not count a pin that moves to a later version).``
  - Other edits: ``next: commit the paths above in one commit, in a pull request of its own: spec-dna.toml has edits beyond the pin (SD503).``
- The message of a tree that is not clean (D151) ends with: ``stash the changes with `git stash`, run `spec-dna upgrade`, commit its paths, then run `git stash pop`. upgrade changes nothing``
- Files: `src/main.rs` (`config_not_alone`), `src/config.rs` (a helper beside `pin_line_only_change`), `src/init.rs` (`is_tool_file`), `src/lifecycle.rs` (`outside_plan`), `src/upgrade.rs`, `docs/diagnostics.md` (SD503 row, "Files that SD503 counts", SD913), `docs/commands.md` (`upgrade`), `docs/guides/upgrade-0.6.md`. Amendment of ADR 0019 (section 3). Agents: `core-engineer`, `diagnostics-engineer` (`outside_plan`), `init-engineer`.
- Tests: `tests/upgrade_pin.rs`: base pin `0.6.1`, head pin = the version of the binary, and a change of `src/a.sh`: `check --base main` gives no SD503. The same with a changed `max-fanout`: SD503. The same with a valid `[spec-dna-sha256]`: no SD503. `tests/lifecycle_checks.rs`: a branch with a plan and the files that `upgrade` writes gives no SD913. `tests/upgrade_cli.rs`: the 2 `next:` lines and the stash text.

### B5. A plan of an earlier version and SD923

The templates of 0.6.0 and 0.6.1 already have `Files:` and `Verify:`, so the text cannot show the version. The history shows it.

- Detection: the newest commit that added the path of the plan (`git log -1 --diff-filter=A --format=%H -- <path>`), and the pin of `spec-dna.toml` in that commit. A pin before 0.7.0 is the earlier form. No such commit (a plan that is not committed, or a shallow clone) or no pin: the current form. The lookup runs only for an `approved` plan with a finding of SD923 or SD924.
- Effect: `check` drops the SD923 and SD924 diagnostics of such a plan. It prints one note for the plan when a dropped diagnostic would show (new, or with `--all`): ``note: `<path>` was added when spec-dna.toml pinned <pin>, before 0.7.0, so SD923 and SD924 skip its <n> task(s) with a finding; to check them, give each task exact paths in `Files:` and one `Verify:` ``. No new code and no new severity. A note is not in `--json`, as the notes of the lifecycle base.
- Files: `src/lifecycle.rs` (a new function), `src/git.rs` (the lookup), `src/main.rs` (the `check` handler), `docs/diagnostics.md` (SD923, SD924, the one-tree list), `docs/profiles.md` (line 45), `docs/guides/upgrade-0.6.md`. Agents: `diagnostics-engineer`, `core-engineer` (`git.rs`).
- Tests: `tests/task_checks.rs`: a plan added when the pin was `0.6.1`, with a folder in `Files:` of a task, and a later commit that moves the pin: `check --all` gives no SD923 and the note. A plan with the same task added after the move, `strict`: SD923 is an error.

### B7. The actual hours

The tool has no log of actual hours. A person wrote the real hours over the estimate, and `finish` deleted the plan.

- A task label `Actual: <n>`: the real hours of the task, with the number form of `Hours:`. A range is not valid. The label follows the rules of the other labels. The tasks are parsed from the cached list items, so `PARSER_VERSION` stays.
- `finish` adds the `Actual:` values of each task that is not a duplicate, also of a skipped task (its time was spent). It prints `Hours: <estimate>, actual <n>`, or `Hours: actual <n>` with no estimate, or `Hours: <estimate>` as before. Notes: ``the task `<id>` has the value "<v>" in `Actual:`, which is no number of hours; no actual total``, and ``the done tasks `<id>`, `<id>` have no `Actual:`; the actual total leaves them out``.
- `log` reads the last line that is `Hours: <estimate>`, `Hours: <estimate>, actual <n>` or `Hours: actual <n>`, with spaces or tabs around the `,`. `<estimate>` keeps the rule of 0.7.0, so an old line reads as before. The text gets the pair `actual <n>` or `actual -` after `hours`. `log --json` and `finish --json` get `"actual": <number>` or `null`. `stats --sdlc` reads the estimate, as before.
- `write-plan`, item 6: "6. A task can end with `Hours: <n>` or `Hours: <a>-<b>`: the estimate. When the task is done, add `Actual: <n>`: the real hours. `spec-dna finish` adds them and prints the line `Hours:`. For a spike, write one task for each branch. After the spike, add `Skip: <reason>` to each task that is not needed, and tick it." The `finish` skill, step 3, says "a line `Hours:`".
- Files: `src/change.rs`, `src/finish.rs`, `src/main.rs` (the `finish` output), `src/sdlc.rs`, `src/harness_text.rs`, `docs/types.md` (labels), `docs/commands.md` (`finish`, `log`), `docs/guides/change.md`. Amendment of ADR 0020. Agents: `core-engineer`, `hygiene-engineer` (`finish.rs`), `init-engineer`.
- Tests: `tests/finish.rs`: `t1` with `Hours: 1-2. Actual: 3`, `t2` with `Hours: 1. Actual: 0.5`: the line `Hours: 2-3, actual 3.5` and `"actual":3.5`. `tests/lifecycle_log.rs`: the message `Hours: 2-3, actual 3.5` gives `hours 2-3 actual 3.5`; `Hours: 4` gives `actual -`.

### B8. Shared documents and SD913

- Key `[change] shared-paths`: a list of globs from the repository root, the form of `high-risk-paths`. Default `[]`. Schema: `{"type": "array", "items": {"type": "string", "minLength": 1}, "uniqueItems": true}`. An empty string is an error (exit code 3).
- Effect: SD913 does not report a path that a glob of `shared-paths` matches. No other check changes: SD910, SD905, `finish` and `next` ignore the key.
- `init` writes `shared-paths = [...]  # documents that each change can edit (SD913)` in `[change]`. The values: the path of each top file of each layer whose `types` has `roadmap` or `questions` (as `spec-dna new` writes it), and each Markdown file whose name, in lowercase and without `.md`, is `roadmap`, `questions` or `open-questions`. Sorted, unique. The default graph gives `["docs/questions.md", "docs/roadmap.md"]`. `--reconfigure` keeps the value. `upgrade` does not add the key.

- Tests: `tests/lifecycle_checks.rs`: a diff that edits `docs/questions.md` outside `Files` gives SD913 with no key and none with `shared-paths = ["docs/questions.md"]` (before: exit code 3, unknown key). `tests/change_config.rs`: an empty string gives exit code 3. `tests/init_graph.rs`: the 2 default paths, and a root `ROADMAP.md`.

### B10. `--base` across releases

ADR 0006 already says that the base tree is the merge base with the default branch. An older `--base` makes the change checks walk the squash commits of merged pull requests, which hold no approval commit.

- Decision: when `--base <rev>` is given, `refs/remotes/origin/HEAD` exists, and the merge base of `<rev>` and `HEAD` is an older ancestor of the merge base of `origin/HEAD` and `HEAD`, the change checks use the newer merge base. The document checks keep `--base`. SD503 uses the same newer base. `next`, `status` and `finish` follow the same rule.
- Only `origin/HEAD` starts the rule, not `[change] base`. A repository with no remote, the fixtures of the eval pack and the tests have `base = "main"`, work on `main` and check with `--base <commit>`. There the merge base with `main` is `HEAD`, so the rule would turn the change checks off. They keep the result of 0.7.0.
- The note: ``note: `--base <rev>` is older than the merge base of HEAD and origin/HEAD (<sha12>), so the change checks use that merge base: the commits between them are merged pull requests, and a squash merge keeps no approval commit``.
- Cost: 2 merge-base calls and one ancestor test, only with `--base`. No per-commit trust and no new status source.
- Files: `src/lifecycle.rs` (`change_base`, `merge_base_of`, and a policy-free helper for SD503), `src/main.rs` (the base of `config_not_alone` in the `check` handler, and the help text of `check`), `docs/commands.md` (`check`), `docs/config.md` (the order of the base), `docs/diagnostics.md` (SD910 and SD503). Agents: `diagnostics-engineer`, `core-engineer`.
- Tests: `tests/lifecycle_base.rs`: the squash replay of section 1 with `origin/HEAD` at the tip: `check --base <tag>` exits 0 with no SD910 and with the note (before: 4 SD910, reason 4). With no `origin/HEAD`: SD910 reason 4 stays. With `[change] base = "main"`, no remote, `HEAD` on `main` and `check --base <older commit>`: SD913 still reports a path outside `Files` (the shape of the pack fixtures).

### B11. A path outside `Files`, and the eval copy

With a yes, add the path to `Files` of `plan.md` in the commit of the edit; a plan with an approval commit in this branch needs a new approval commit first (SD910, reason 8)." The trap of `execute-6` (stop and ask) stays true, and its check allows `plan.md`.

(b) and (c): `prepare` in `src/eval_ab.rs` sets `SD501 = "off"` and `SD502 = "off"` under `[rules]` of the copy's `spec-dna.toml` (with `config_text`, so an existing `[rules]` keeps its keys), beside `pin_version`. Both arms get the same edit. A plain `eval run` does not change.
- Files: `src/harness_text.rs`, `src/eval_run.rs`, `src/eval_ab.rs`, `docs/evals.md`. Agents: `init-engineer` (skill text), `core-engineer` (runner).
- Tests: `tests/harness_skills.rs` and the golden file of `execute`; `cargo test --test eval_pack` keeps `execute-6` green. `tests/eval_ab.rs`: a project line of another version (a valid marker `v0.6.1`), a stub that runs `spec-dna check --all`: no SD501 or SD502 in each arm, and the copy has the line of this binary.

## 3. Amendment texts

Each text goes under `## Amendments` of an accepted ADR, as a section `### 2026-11-19`. No ADR changes its status. ADR 0006 and ADR 0012 are near the hard budget, so they get no text. ADR 0013 is over its soft budget (a trial gave SD703, 7,289 to 7,938 characters), and its amendments already point to ADR 0019, which amends "The pin line and SD503". Thus the text of B3 goes to ADR 0019. B5, B8 and B10 need no amendment: B10 follows ADR 0006, and B5 and B8 change the scope of a diagnostic only. A trial of the 3 texts in the ADRs gave no SD605.

ADR 0019 (B3):

> In each binary, SD503 does not count `spec-dna.toml` when its text differs from the base text only in the pin line and in the table `[spec-dna-sha256]`, and the base pins an earlier version. This is the edit of `spec-dna upgrade` for a release that needs no other edit of the configuration. A hook that runs `check` refuses each commit while the pin is older than the binary, so the upgrade is the first commit of a branch. With this rule, the same branch can also hold other work. An edit of another line counts as before. The pin stays exact (ADR 0003). SD913 does not report the files that SD503 does not count. The feedback of a second project gave the reason (design 0.7.1 part B, B3).

ADR 0020 (B1, B7):

> - A task can have the label `Actual: <n>`: the real hours of the task, in the number form of `Hours:`. `Hours:` stays the estimate. `finish` adds the estimates as before, and the `Actual:` values of each task, also of a skipped one. It prints `Hours: <estimate>, actual <n>`, or `Hours: actual <n>` with no estimate. Thus the commit message keeps the real hours after `finish` deletes the plan. This replaces the option "2 labels, `Estimate:` and `Hours:`" that this ADR did not choose: here the 2 values count apart, so no rule chooses between them.
> - An open task whose text names `spec-dna finish <slug>`, with the slug of its change, closes with `finish`. `next`, `status` and step 0 of `finish` treat it as closed, so `finish` never waits for a task that only `finish` can do. A task of a person, such as the review by the owner, stays open until a person ticks it.

ADR 0023 (B4):

> An upgrade from a pin before 0.7.0 adds to a list `skills` that is not empty each skill that is new in 0.7.0 (`tdd`, `execute`, `verify`, `finish`, `debug`, `post-mortem`) and that `init` proposes for the profile and the level of the project. The project had no way to choose these skills, so the addition changes no choice of the project. A name of the list keeps its place, and an empty list stays empty. The report names each skill that it adds. For these skills only, this replaces the option "the preset of a profile in `upgrade`" that this ADR did not choose.

## 7. Risks

1. The predicate of B1 needs the slug. A plan with "Run `spec-dna finish`" still stops at step 0 (the stop gives the hint). A task of real work whose text names `spec-dna finish <slug>` closes with `finish`. The skill tells agents to write no such task.
2. B3 lets a pin move ride with other work, so the new rules of a release check that work in the same pull request. CI installs the binary of the head pin. A cached older binary stops with exit code 3, not with a pass.
3. B1, B6, B7 and B11 change the text of `write-plan`, `specify`, `execute` and `finish`. The table of the release has verdicts of the old text (`execute` inconclusive, `write-plan` not run again). A rerun before the tag is a cost decision of the owner.
4. B5 reads history. A shallow clone (CI with `fetch-depth: 1`) finds no commit, so SD923 reports each task there as in 0.7.0, and a local run and CI can differ. One `git log` runs for each flagged plan.
5. The line `Hours: <estimate>, actual <n>` gives no hours to `log` of 0.7.0 or to a script that reads the old form. The text of `log` gets one more pair, so a script that splits on spaces must change.
