## D87. SD915 for a change with no delta reads the tasks of the plan (item 5)

**Problem**:

The guide says that with `approval = "branch"` the intent, the approvals, the plan and the code can be in one pull request, and `finish` follows in a later one (`docs/guides/change.md:235`). For a change with no delta, SD915 then always reports the pull request of `finish`. `finish_incomplete` (`src/lifecycle.rs:3219`) asks the diff of that pull request for a changed `Files` path or a changed requirement hash (`:3263-3285`), and the code merged before. `finish` itself checks no code: step 0 stops only on an open task (`src/finish.rs:405-422`). Thus `finish` succeeds, and `check` rejects its result.

Example: the change `team-measurement-2` (`routine`, `branch`) merged its work in pull request #119. Its plan had 6 ticked tasks. A `finish` in its own pull request gives SD915, so pull request #120 set the intent to `closed`, and #121 deleted the folder. `log` now lists a closed change, not a finished one.

The same rule rejects each plan that states "no files" (`Change::no_files`, `src/change.rs:178`). Its `Files` has no pattern, so only a changed requirement hash clears SD915, and a research change changes none.

ADR 0012 sets the floor at 2 pull requests and says that `check` does not enforce the order of the design and the code (`docs/adr/0012-approval-in-the-branch.md:94`). The guide and the check must accept both orders.

**Mechanism**:

1. A change with a delta keeps the rule of 0.6: the head has the result of each delta line.
2. A change with no delta keeps the rule of 0.6 as the first test: the diff changes a `Files` path or a requirement hash. When the rule of 0.6 finds the change incomplete, SD915 reads the tasks of the newest plan, and it reports nothing when the plan has at least one task and each task is closed. The plan then says that the work is done, and `finish` passed its step 0 on it.
3. The newest plan is the last text of `plan.md` in the commits of the branch before the delete, else the plan of the base tree. A task is open when it is not closed, not a duplicate, and does not close with `finish` or `accept`: the filter of step 0 of `finish`. One function gives the filter to `finish` and to SD915.
4. The rule only relaxes. Each pull request that 0.8.0 passes still passes, so the rule of ADR 0003 (a new rule starts as a warning in a minor release) does not apply. A pull request with an open task and an edit of a `Files` path passes, as in 0.8.0.
5. A plan that states "no files" passes when each of its tasks is closed. A plan with no task (for example a plan before 0.7.0) and a change with no plan keep the rule of 0.6 alone.
6. The guide gives both orders for both classes: the code in the pull request of the approvals, or in the pull request of `finish`. With the code in the first pull request, the acceptor runs in that pull request, after the code. For a routine change, the edits of requirements go into the pull request of `finish`, because `finish` and SD916 check the evidence of each requirement whose hash differs from the base (`docs/guides/change.md:237`, `src/lifecycle.rs:3312-3316`).

Rejected: read the history for SD915, as the fallback of `accept` does (`src/accept.rs:251-258`). That needs the full history. Also, that fallback diffs from the commit that added the plan (`Git::added_by`, `src/git.rs:944`), so it leaves out the code of a squash commit that holds the plan and the code ("What stays open").

**Formats**:

The message of SD915 when the plan has an open task:

```text
the diff deletes the change `<slug>`, its base status is `<status>`, the diff changes no `Files` path and no requirement hash, and its plan has <n> open task(s) (<ids>); do each task, or close it with `Skip: <reason>`, and run `spec-dna finish <slug>`, or set the intent to `closed` in an earlier pull request
```

A plan with no task keeps the message of 0.8.0.

The last sentence of the row SD915 of `docs/diagnostics.md` becomes: "For a change with no delta, the diff changes no `Files` path and no requirement hash, and the newest plan of the branch has no task or an open task."

The guide, section "A routine change", second paragraph:

```text
With `approval = "branch"`, the intent, its approval commit, the plan, its approval commit and the code can be in one pull request. `finish` follows in a later pull request. That pull request can hold no code when each task of the plan is closed (SD915). Put the edits of requirements in the pull request of `finish`: `finish` checks the evidence of each requirement whose hash differs from the base.
```

**Codes**:

SD915 keeps its name and its severities (a warning in `lite`, an error in `standard` and `strict`). Its meaning stays: the diff deletes the folder of a change that is not finished. It reports fewer pull requests, and no new one.

**Upgrade**:

No key. `check` reads no merged change again, and no pull request that passed in 0.8.0 fails.

**Cost**:

When the rule of 0.6 finds a change incomplete, SD915 reads the newest plan of the branch: one read of the history of the folder (`branch_version`, `src/lifecycle.rs:2005`). SD913 and SD938 share that read (`BranchScope`, `:1857`, kept in a `OnceCell`), so a diff that needs both makes it once.

**Does not prove**:

- A ticked box is a claim. The check shows that the plan says that the work is done, not that the code exists. The rule of 0.6 had the same limit: one edit of a path cleared it.
- With the code and the edits of requirements in the first pull request, no check reads the evidence of these requirements: SD916 runs only where the folder is deleted, and there no hash differs from the base. The guide asks for the edits of requirements in the pull request of `finish`, and no check enforces it.

**Files and agents.** `src/lifecycle.rs` (`finish_incomplete`) and `docs/diagnostics.md`: `diagnostics-engineer`. The filter of step 0 as one shared function, in `src/change.rs` (`core-engineer`), called from `src/finish.rs` (`hygiene-engineer`, C). `docs/guides/change.md`: `architect` for the facts, `docs-editor` for the language.

**Tests**:

- `tests/lifecycle_finished.rs`, `a_routine_change_finishes_in_a_pull_request_of_its_own`: the base has the change with an approved plan, each task ticked, and the code. The pull request deletes the folder only. Before the fix: SD915. After: no SD915.
- `a_plan_that_states_no_files_finishes`: `- None: this change is research.` and 1 ticked task. Before: SD915. After: none.
- `an_open_task_with_no_edit_gives_sd915_with_the_ids`: 1 open task, and the pull request deletes the folder only. Before and after: SD915. After, the message names the id.
- `an_open_task_with_an_edit_of_files_passes_as_in_0_8_0`: it pins the relaxed rule.
- `a_person_task_ticked_in_the_branch_counts`: the base plan has an open task `By: person`, a commit of the branch ticks it, and a later commit deletes the folder only: no SD915.
- `a_routine_change_needs_a_changed_files_path_or_a_changed_hash` (its fixture plan has no task) passes with no edit.

## D88. One id for each deviation, and the acceptor starts on valid sections only (item 6)

**Problem**:

Each item of `Deviations` has its own id: a later item with the same id is not valid (SD939, `src/change.rs:1417-1437`). Each `[[deviation]]` of the record has its own id (SD928, `src/record.rs:712-717`). The skill `execute` gives the form `- <id> (plan): <text>` and no rule for the id (`src/harness_text.rs:156`). A builder that uses the id of a task, and finds 2 deviations in that task, writes the id 2 times.

`next` then names the acceptor: the checks of the sections run only when a record exists (`first_stop`, `src/acceptance.rs:1219`, `let rec = rec?;`). `accept` writes a skeleton with no entry for the item that is not valid (`src/accept.rs:66`). The commit of the acceptor runs the hook `check --staged`, and SD939 reports the plan, a file that the acceptor must not edit.

Example from the owner: a plan with 2 deviations of one task, and the first commit of the acceptor failed. This repository does not reproduce it: no record here has a deviation. Thus the cause above is the likely one, not a proved one. Q7 asks for the code and the message of the failed commit. A second candidate gives the same fix: the acceptor copies both items with one id into the record, and SD928 refuses the commit.

**Mechanism**:

1. The format stays: one id for each item, in the plan and in the record. A task with 2 deviations has 2 items, for example `t3-a` and `t3-b`. An id needs no relation to a task. A key of 2 parts would change SD928, SD938 and the acknowledgement for no gain.
2. The item `review` of `next` runs the checks of the sections (SD936, SD937, SD939 and SD940) before it names the acceptor, with the function that `first_stop` uses. A finding gives an open item for the builder.
3. `accept` and `accept --brief` refuse with exit code 1 on the same findings, before any write and before the brief.
4. The message of SD939 for a repeated id names the fix.
5. The skill `execute` gets one sentence in step 5. `execute` is not in the freeze table of the reruns (`docs/evals.md:537-544`), so no rerun is necessary.

**Formats**:

The item of `next`:

```text
the plan of the change `<slug>` has an item that is not valid (<code> at <path>:<line>: <message>); the builder fixes it and commits, and then starts the acceptor
```

The refusal of `accept` (exit code 1):

```text
spec-dna accept: `<path>` has an item that is not valid (<code> at line <n>: <message>); the acceptor does not edit the plan or the spec: the builder fixes the item and commits, then run accept again
```

SD939 for a repeated id:

```text
the id `<id>` is used already in `Deviations`: give each item its own id, for example `<id>-2`; a task with 2 deviations has 2 items
```

The new sentences of step 5 of `execute` (88 bytes): "Give each item its own id, for example `d1`, `d2`. A task with 2 deviations has 2 items."

**Codes**:

No new code. SD939 keeps its severity.

**Upgrade**:

Nothing. An open change with an item that is not valid already gets SD939 from `check`.

**Cost**:

`next` reads the sections, which `first_stop` reads already when a record exists. The body of a skill is not in each request. The body of `execute` grows from 2,174 bytes (measured on `tests/golden/harness/skills/spec-dna-execute.md`, with no front matter and no marker) to 2,263 bytes. A test limits a body to 2,500 bytes (`src/harness_text.rs:651`). The page `docs/design/0.8.1-harness-additions.md` proposes 326 bytes more for the same body (its Q3, option (a)). Both together give 2,589 bytes, so the build of both needs a cut of other text.

**Does not prove**:

That the list of deviations is complete.

**Files and agents.** `src/stage.rs`, `src/accept.rs` and `src/change.rs`: `core-engineer`. A function of `src/acceptance.rs` for the sections with no record: `diagnostics-engineer`. `src/harness_text.rs` (`execute`) and its golden file `tests/golden/harness/skills/spec-dna-execute.md`: `init-engineer`. `docs/commands.md` (`accept`, `next`) and `docs/types.md` (section `Deviations`).

**Tests**:

- `tests/accept_next.rs`, `next_stops_before_the_acceptor_on_a_repeated_deviation_id`. Before: the item names the acceptor. After: the item names the builder and SD939.
- `tests/accept_cmd.rs`, `accept_refuses_a_plan_with_a_repeated_deviation_id`. Before: exit code 0 and a skeleton with 1 entry. After: exit code 1, and no file.
- A unit test in `src/change.rs` for the text of the repeated id.

## D89. The hook that runs the tests also stamps the reports (item 7)

**Problem**:

The stamp holds the hash of the bytes of the report (`src/report.rs:482-528`). `check --reports` and `finish` give SD614 when the bytes differ (`:827-836`). A pre-commit hook that runs the tests and writes a JUnit report writes new bytes at each commit, for example new times, after the person ran `spec-dna evidence stamp`. Thus each commit makes the report stale.

`init` detects pre-commit (`src/detect.rs:1381`). It reads `.pre-commit-config.yaml` for the hook `typos` only (`typos_hook`, `:1557`, and `TYPOS_NOTE`, `src/init.rs:2861`).

**Mechanism**:

1. The one documented setup: the hook that runs the tests runs `spec-dna evidence stamp` in the same entry, after the tests. Then each new report gets its stamp.
2. Why it works: pre-commit stashes the edits that are not staged before it runs the hooks, so the tests and the stamp read the tree of the commit. The report and the stamp are ignored files, so pre-commit sees no edit of a tracked file. A code edit that is not staged makes the stamp stale after the commit, which is correct.
3. `init` and `upgrade` print a note when `.pre-commit-config.yaml` has a hook that runs tests and does not stamp. The scan reads lines, as `typos_hook` does. A hook runs tests when the value of its `id:` or `entry:` has one of these words (split at each character that is not a letter or a digit): `test`, `tests`, `pytest`, `nextest`, `jest`, `vitest`, `gotestsum`, `junit`, `junitxml`, `phpunit`, `rspec` or `unittest`. A hook whose `entry:` has `evidence stamp` gets no note.
4. The message of SD614 for changed bytes names the cause.
5. The setup goes into the page of the test reports that D85 decides (`docs/test-report.md`), in a section "A hook that runs the tests". `docs/init.md` names the note and links that section.

**Formats**:

The entry of `.pre-commit-config.yaml`:

```yaml
  - repo: local
    hooks:
      - id: tests
        name: tests
        entry: sh -c '<the test command that writes the report> && spec-dna evidence stamp'
        language: system
        pass_filenames: false
```

The note of `init` and `upgrade`:

```text
note: the pre-commit hook `<id>` runs the tests. If it writes a report that `[evidence] reports` matches, each commit writes the report again after `spec-dna evidence stamp`, and `check --reports` gives SD614. Run the stamp in the same hook: entry: sh -c '<test command> && spec-dna evidence stamp' (docs/test-report.md#a-hook-that-runs-the-tests)
```

SD614 for changed bytes:

```text
the bytes of the report `<path>` changed after its stamp, for example a commit hook or a second test run wrote it again; run the tests and `spec-dna evidence stamp` in one command line, or in one hook entry
```

**Codes**:

No new code. SD614 keeps its severity.

**Upgrade**:

`upgrade` prints the same note. It changes no file of the hooks.

**Cost**:

One scan of one file in `init` and `upgrade`. No byte in a request of an agent.

**Does not prove**:

- The scan reads words, not YAML. It misses a runner whose name is not in the list, and a report that a file of the runner sets. It can name a hook that writes no report, and the note then says "if".
- `sh -c` needs a POSIX shell. On Windows, Git for Windows has one.

**Files and agents.** `src/detect.rs`, `src/init.rs`, `src/upgrade.rs` and `docs/init.md`: `init-engineer`. `src/report.rs` (the message): `diagnostics-engineer`. The section of the page of the test reports: the owner of D85.

**Tests**:

- `tests/init_change.rs`, `init_names_a_test_hook_that_does_not_stamp`. Before: no note. After: the note names the id. A hook with `evidence stamp` in its entry: no note.
- `tests/evidence_reports.rs`, `a_report_written_again_after_the_stamp_gives_the_hook_text`: stamp, write the report again, `check --reports`. The message of SD614 has "one hook entry".
- `tests/evidence_reports.rs`, `the_setup_of_the_hook_keeps_the_stamp_fresh`: run the entry of the setup (`sh -c` with a stub test command that writes new bytes, then the stamp), then `check --reports`: no SD614.

## D90. `layer add` updates the adapter skill (item 8)

**Problem**:

`layer add summaries` writes `spec-dna.toml` only (`src/main.rs:2814-2856`). The adapter skill lists the types of the project (`adapters::skill_file`, `src/adapters.rs:128`), so SD502 reports the skill until `init` runs. The lines `next:` of `layer add` give the commit first and `init` second (`src/main.rs:2843-2854`). A hook that runs `check --staged` refuses that commit.

SD503 counts each document that changes with `spec-dna.toml` in one pull request (`config_not_alone`, `src/main.rs:2177-2210`). It does not count a file that `init` writes (`is_tool_file`, `src/init.rs:1852`), and the adapter skill is such a file. Thus a summary in the same pull request gives SD503.

**Mechanism**:

1. When the types of the project change and `.claude/skills/spec-dna/SKILL.md` exists with no hand edit (no SD501), `layer add` writes the new skill in the same write as `spec-dna.toml`. A skill with a hand edit stays, and the line `next: run spec-dna init ...` comes first.
2. The one path, 2 pull requests:
    1. Run `spec-dna layer add summaries`. Commit `spec-dna.toml` and the skill in a pull request of their own. Merge it.
    2. In a later pull request, run `spec-dna new summary <area>` for each area, write the text, and run `spec-dna check`.
3. SD503 keeps its rule: a configuration change is a change of its own. Q1 asks the owner about an exception.

**Formats**:

The output:

```text
added layer `summaries` (level 0) to spec-dna.toml
updated .claude/skills/spec-dna/SKILL.md: it lists the types of the project
next: commit spec-dna.toml and .claude/skills/spec-dna/SKILL.md in a pull request of their own, and merge it (SD503)
next: after the merge, run spec-dna new summary <id> to write the first document of the layer
```

With a hand-edited skill, the first line `next:` is `run spec-dna init to update the agent skill, which lists the types of the project`, and the commit line names `spec-dna.toml` and the files that `init` writes. The `--json` object gets the key `skill_updated` (`true` or `false`) after `types_added`.

**Codes**:

No new code. The row SD502 of `docs/diagnostics.md` ends with: "`spec-dna layer add` updates the skill, except a skill with a hand edit."

**Upgrade**:

Nothing.

**Cost**:

One more file write in `layer add`.

**Does not prove**:

That no other generated file lists the types. Only the adapter skill takes the types (`src/adapters.rs:97-135`).

**Files and agents.** The handler of `layer add` in `src/main.rs`: `core-engineer`. `src/adapters.rs` is read, not changed. `docs/commands.md` (`layer add`) and `docs/types.md` (the summary): `core-engineer`. The row SD502: `diagnostics-engineer`. `tests/layer_cmd.rs`.

**Tests**:

- `tests/layer_cmd.rs`, `layer_add_updates_the_adapter_skill`. Before: `check --all` gives SD502 after `layer add summaries`. After: no SD502, and the JSON has `"skill_updated":true`.
- `a_hand_edited_skill_stays_and_the_init_line_comes_first`.

## D91. SD401 on a spec or a plan of a change gives the steps of the rework (item 9)

**Problem**:

SD401 reports a step back from `approved` to `draft` when the base tree has the approval (`transitions`, `src/check.rs:1314-1324`). Its fix text says "To return to an earlier status, write a new document" (`src/diag.rs:83`). For a spec or a plan of a change, the skills `specify` and `write-plan` (`src/harness_text.rs:106` and `:140`) and the guide (`docs/guides/change.md:172` and `:214`) say the opposite: set `draft` in the commit of the edit, skip only the hook that runs `spec-dna check` for that commit, and make the approval commit next. SD910 reason 9 says the same for an approval of the branch (`src/approval.rs:117`).

**Mechanism**:

1. A document of type `spec` or `plan` that moves from `approved` to `draft` keeps SD401, with its code and its severity. It gets the message and the fix of the rework. Each other document keeps the text of 0.8.0.
2. The fix follows a mark in the message, as `NO_SUMMARY_LAYER_MARK` does (`Diag::fix`, `src/diag.rs:226-240`).
3. The skill texts stay. They are frozen for the verdicts (`docs/evals.md:535-546`), and their steps are right already. They name SD910 only, and SD401 now gives the same steps.

**Formats**:

The message:

```text
status cannot move from `approved` to `draft`; this is the step back of a rework: a hook that runs `spec-dna check` rejects its commit, so skip only that hook for this commit, name the skip in its body, and make the approval commit next
```

The fix: "To rework an approved spec or plan, set `status: draft` in the commit of the edit. Skip only the hook that runs `spec-dna check` for that commit, and name the skip in the body of the commit. Then the approver makes the approval commit, and SD401 is gone. For another document, write a new document."

**Codes**:

SD401 keeps its code, its name and its severity.

**Upgrade**:

Nothing.

**Cost**:

Nothing.

**Does not prove**:

That the approver read the edit.

**Files and agents.** `src/check.rs`, `src/diag.rs` and the row SD401 of `docs/diagnostics.md`: `diagnostics-engineer`. `docs/guides/change.md`: `architect`.

**Tests**:

- `tests/lifecycle_checks.rs`, `the_step_back_of_a_base_approved_plan_gives_the_rework_steps`: the base has the plan `approved`, the head has it `draft`. Before: the fix says "write a new document". After: the message has "skip only that hook", and the `fix` of `--json` has "rework".
- A decision that moves from `accepted` to `proposed` keeps the text of 0.8.0.

## D92. SD913 needs a change of the diff, and `stats` binds the reports on one tree (item 10)

### SD913

**Problem**:

SD913 runs when a change of the diff has a plan (`outside_plan`, `src/lifecycle.rs:2348-2351`). A change is a change of the diff also when the diff only edits a path of its `Files` (`Origin::FilesMatch`, `:1838-1851`). Example: the change C is open on the default branch with `Files: src/valves.rs`. A small fix edits `src/valves.rs` and `README.md`. C is then a change of the diff, and SD913 reports `README.md` with "add it to `Files` of the plan, or move the edit to a change of its own", for a fix that needs no change.

**Mechanism**:

1. SD913 runs only when the diff has a change with a plan whose folder the diff touches (`Origin::Touched`) or that the branch added (`Origin::Born`).
2. The `Files` of a change of `FilesMatch` stay in the scope of SD913.
3. SD910 keeps `FilesMatch`: code under the `Files` of a plan still needs its approval.
4. The message names a pull request, not a change.

**Formats**:

```text
`<path>` is in the diff, and no `Files` item of a change in the diff matches it; add it to `Files` of the plan, or move the edit to a pull request of its own
```

### `stats`

**Problem**:

`stats --sdlc` reads the `covers:` tags from the tree of `HEAD` (`evidence::load(..., Some(&head), ...)`, `src/sdlc.rs:1063`). It binds them with the lines of the test files on the disk (`bind_covers`, `src/evidence.rs:785-810`), and with the reports whose stamp names the code tree of the working tree (`src/report.rs:838`). With an edit of a test file that `HEAD` does not have, a tag at line 40 of `HEAD` reads line 40 of another text, and a fresh report proves the working tree, not `HEAD`.

**Mechanism**:

`stats` binds the tags only when the code tree of the working tree (`tree::compute`, `src/tree.rs:190`) has the hash of the code tree of `HEAD` (the same hash over the code entries of `git ls-tree -r HEAD`, `src/git.rs:516`). Then the tags, the lines and the reports read one tree. Else `stats` reads no report, each full tag counts as `tagged`, and the line `proof:` says why.

**Formats**:

The text line ends with `; no report read: the working tree has code edits that HEAD does not have`. The object `proof` of `--json` gets the key `reports_read` (`true` or `false`) at its end.

### Both parts

**Codes**:

No new code. SD913 keeps its severity and reports fewer findings.

**Upgrade**:

Nothing.

**Cost**:

`stats` reads one more tree listing when the project has `[evidence] reports`.

**Does not prove**:

## D95. The turns of a run are the sum over the segments (issue #109, item 13)

**Problem**:

The runner reads `num_turns` of the last `result` event of `claude -p --output-format json` (`result_turns`, `src/eval_run.rs:1306-1314`, with `result_object`, `:1256-1268`). A background task that ends after the agent stopped wakes the agent, and each wake-up ends with a `result` event whose `num_turns` counts that segment only. In protocol 2, the transcript of the probe of `lean-no-advisor` has 9 segments of 101, 8, 4, 18, 8, 5, 4, 2 and 2 turns. The sum is 152, the count of the transcript, and the runner recorded 2. In the batch, the recorded turns of 27 of the 42 new runs, and 28 of the 45 runs with the probe, differ from the count of the transcript ([results](../team-measurement-2.md#limits)).

The runner did not keep the output of `claude`, so nothing shows the bytes on stdout. The recorded value is the count of the last segment, so the output that the runner parsed with `--output-format json` held the last `result` event only.

**Mechanism**:

1. The runner passes `--output-format stream-json --verbose` in place of `--output-format json`. Claude Code then writes one JSON event on each line, with each `result` event.
2. The reader keeps a line only when it has the bytes `"type":"result"`. It parses the line, and it keeps the event only when the top-level `type` is `result`, so a tool result that holds these bytes does not count. Thus the memory holds the `result` events only, whatever the size of the stream. The cap of 16 MiB (`MAX_STDOUT`, `:28`) can no longer cut the last event of a long run.
3. `turns` is the sum of `num_turns` over the `result` events. The name stays: the field now counts the whole run, which a reader expects.
4. `segments` is a new key of each result in the result files of `eval run`, `--ab` and `--arms`: the number of `result` events. The records of `eval records` keep their 12 keys, so the record format does not change.
5. `cost_usd`, `subtype`, `modelUsage` and the tokens come from the last `result` event, as in 0.8.0. The measurement found that these values are totals of the session: they agree with the cost of each transcript (rule 1 of the results page).
6. The docs say that `--max-turns` probably limits each segment, so `turns` can be more than `max-turns` when `segments` is more than 1.

Rejected: count the `assistant` events. Nothing measured shows that this count equals the unit of `--max-turns`, and a message can have more than one event.

**Formats**:

```json
{"claude_exit":0,"subtype":"success","cost_usd":0.3,"checks":[],"tokens":{"in":10,"out":20,"cache_read":30,"cache_write":40},"models":["claude-opus-5-5"],"turns":7,"segments":2,"seconds":41.3}
```

None.

**Upgrade**:

No key. A record of 0.8.0 holds the turns of the last segment. The records of protocol 2 hold the count of the transcript already. The docs of `eval records` say so.

**Cost**:

- That `--max-turns` limits each segment and not the whole run.

## D100. The eval runner: one arm alone, and a floor of free space (item 17, decided by the owner)

**Problem**:

`--arms` takes 2 or 3 arms (`parse_arms`, `src/eval_ab.rs:1740-1759`), and it runs the arms of one command one after the other. In protocol 2, the arms of a task could not run at the same time, as the owner asked (rule 4 of the results page). `eval verdict --compare` reads one result file (`compare`, `src/verdict.rs:1029`), so files of one arm each give no verdict. `--ab` measures a skill in pairs of the same eval and run, with and with no skill. Its verdict comes from the pairs of one file, so it keeps its 2 sides.

In wave 1 of protocol 2, the disk was full for a time. 4 runs lost their transcripts, and in 1 run the copy of the hidden tests failed, so its part 1 does not show the work of the agent ([results](../team-measurement-2.md#the-disk-was-full-during-wave-1)). The runner checks no free space.

**Mechanism**:

1. `--arms` takes 1 to 3 arms. With 1 arm, wave `r` runs each eval once in that arm, and the result file `arms-<stamp>.json` has that arm only. `--resume` works as with more arms.
2. `eval verdict --compare <treatment>,<control> <file> [<file>...]` reads 1 or more result files of `--arms`. It joins them by the id of the eval and the number of the run. The arms are the union of the arms of the files. The complete waves are counted on the join. A run of one eval in one arm that 2 files hold is exit code 3. Files with different versions of Claude Code give a note.
3. Before each run (each attempt of `eval run`, `--ab` and `--arms`, also a new attempt after a refusal of the API), the runner reads the free space of 2 folders: the temporary folder of the system, where the copy goes, and the folder of the result file. If a folder has less than `[evals] min-free-mib` MiB free, the runner starts no run. It writes the result as for a stop by the cap (`--ab` and `--arms` keep the complete pairs and waves), sets `stopped` to `"disk-space"`, prints the message, and exits with code 3. `--resume` continues when the person frees space.
4. The runner reads the free space with `df -Pk <folder>` as a child process: POSIX output in blocks of 1,024 bytes. The value is the field before the first field that ends with `%` on the second line, so a name with spaces does not move it. This adds no dependency and no `unsafe` code; a call of `statvfs` would need either. If `df` is absent or its output does not parse, the runner prints one warning and runs with no check.

**Formats**:

```text
spec-dna eval run: stopped before a run: `<folder>` has <n> MiB free, below `[evals] min-free-mib` (<m>); free space, then run the command again with `--resume <result file>`
warning: cannot read the free space of `<folder>` (`df -Pk`); the check of `[evals] min-free-mib` is off for this command
--compare: the run <n> of `<eval>` in the arm `<arm>` is in 2 files: <file>, <file>
```

A plain `eval run` has no `--resume`, so its message ends with "then run the command again".

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[evals] min-free-mib` | integer, 0 or more | `2048` | nothing |

`0` turns the check off. The default is a chosen floor that leaves room for the copy and a small build. It is not a measurement. A project with large builds sets a larger value.

**Codes**:

No SD code. A value that is not an integer of 0 or more is exit code 3 (configuration), as for each other key of the table `[evals]`.

Exit codes, in the table of `docs/commands.md`: `eval run`, `--ab` and `--arms` give 3 also for a stop by the floor of free space. `eval verdict --compare` gives 3 also for a run in 2 files. `--arms` with 1 arm is no longer a usage error.

**Upgrade**:

A project with no key gets the default of 2,048 MiB. A machine with less free space than that now stops before the first run. The message names the key.

**Cost**:

One `df` process for each folder before each run.

**Does not prove**:

- The disk can fill during a run: a build in the copy, or the transcript of Claude Code in its own folder, which can be on another disk. The check limits the loss to the run in flight.
- The floor is one number, not the need of a run.
- Arms that run at the same time share one machine and one account, so their minutes are not those of a quiet run (as in protocol 2).

**Files and agents.** `src/eval_ab.rs`, `src/eval_run.rs`, `src/verdict.rs`, `src/evals.rs` and `src/config.rs` (the key), `schema/spec-dna.schema.json`, `docs/evals.md`, `docs/config.md` and the section `eval` of `docs/commands.md`: `core-engineer`.

**Tests**:

- `tests/eval_ab.rs`, `arms_runs_one_arm_alone`: `--arms none`. Before: exit code 2, "--arms takes 2 or 3 arms, got 1". After: a result file with the arm `none`.
- `compare_joins_2_files_of_one_arm`: 2 files of one arm each give the verdict that one file of 2 arms gives. `a_run_in_2_files_is_exit_code_3`.
