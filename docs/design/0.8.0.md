The upgrade from 0.7.1 (P5). `upgrade` adds no key, and an absent key keeps the behavior of 0.7.1. The owner decided the profiles on 2026-11-19 (section 11, "The profiles"):

- In `lite`, each new mechanism is off. Each new code is off, and `finish` needs no record. Each new code is in a new rule group, so no group rule of 0.7.1 turns it on.
- In `standard`, 2 mechanisms are on with no key: the acceptance, with its deviations, and the roll-up. Each other mechanism is on only by its key. The proof debt has no key: the marker is an act of the author on one requirement, as `verified-by` is, not a switch of the project. Its codes are warnings in `standard`.
- `strict` turns the mechanisms on as this page says, with the keys that `init` writes for a new project. `upgrade` writes none of them.
- Thus a project of 0.7.1 that runs `upgrade` gets no new error without a key that it set, with one exception (Q43). In `standard` and `strict`, a plan that the branch adds needs an acceptance record at `finish`. The cost is one acceptance run for each such change. Amended by D70: in `standard`, only for a `higher-risk` change or a matched role of `[owners]`.
- A plan or a spec that an ancestor of the lifecycle base added at a pin before 0.8.0 keeps the rules of 0.7.1: it needs no record and no section. The stricter rule applies to a plan that the branch adds, and when no adding commit exists (a shallow clone).
- `upgrade` alone gives a clean 0.7.1 repository no new diagnostic. The roll-up gives no finding until the project writes a summary, and the area budget none until the project sets `[budgets.area]`.

The limit of the whole design. The gate checks that a person or an agent made a claim. It checks that the claim is bound to one tree and one text, and that the claim is not stale. It cannot check that the claim is true. The trust root is the person who acknowledges: the merge or the approval commit. Each section ends with what its mechanism does not prove.

## 2. The test report and the proof (items 1 and 2)

### D1. The test report as evidence

**Problem**:

A tag is a claim, not a fact. Example: `tests/test_valves.py` has `# covers: requirements/valves/closing#sensor-timeout` above `test_closes_on_timeout`, and the test has `@pytest.mark.skip`. `check` gives no SD608, and `finish` gives no SD916, because both read only the tag. The same holds for a test that fails.

**Mechanism**:

1. The code tree. One hash covers the code as it was. Its input is each entry of the git index (`git ls-files -s -z`). A tracked file that differs from the index gives the mode and the object id of the file on disk (`git hash-object --stdin-paths`). A symbolic link that differs from the index gives the mode `120000` and the object id of its text (the path that it names, `readlink`), as git stores it. A submodule keeps its entry of the index: the tree does not look into it. A path is bytes: a name that is not UTF-8 stays whole. A file that is deleted on disk does not count. An untracked file does not count. On a clean checkout the result equals `git ls-tree -r HEAD`.
2. The code paths. The tree excludes a path that `[evidence] tree-exclude` matches (default: each Markdown file). It also excludes each path in a folder of a layer of the type `intent`, each path under `.spec-dna/`, each tool file (`init::is_tool_file`), and each file that `[evidence] reports` matches, with its stamp. Thus a change of documents, of the record or of `finish` never changes the tree.
3. The hash. spec-dna hashes the bytes `spec-dna-tree 1\n`, then `<mode> <object id>\t<path>\n` for each entry in the byte order of the paths. The result is the first 8 bytes of SHA-256 as 16 hexadecimal digits, the form of `src/hash.rs`. A new function `tree::matches` compares 2 such hashes (P1). A report binds to the hash of all code paths, because a test runs on the whole tree.
4. Reports. `[evidence] reports` lists globs of report files. spec-dna reads them from the disk, even when git ignores them. It detects the format of each file from its first bytes. The list of formats is closed: `junit` and `lines`. A new format is a new reader in `src/report.rs` and one more name in the list.
5. The stamp. `spec-dna evidence stamp` reads each report, and writes `<report>.stamp` with the tree hash and the hash of the report bytes. CI runs it after the tests, in the same job, so the stamp is exact. Locally, the skills run the tests and the stamp in one command line.
6. The bind of a tag. The tag at line L of file F binds to the test cases that one name gives:
    - The explicit name: `covers: <id> case:<name>` or `case:"<name with spaces>"` after the ids. The value is the `name` of the case as the report writes it, with no `#`: a binary of 0.7.1 reads `case:X#y` as an id, so it reports SD105 for it. A name with no `#` ends the tag for a binary of 0.7.1, so it keeps the same ids.
    - Else the tag binds to the first word or string literal of the first code block after the tag, when it names a case of the reports. The block starts at the first line after the tag that is not blank and not a comment. It ends before the first later line whose indent is not deeper than the indent of the start line, after a deeper line. It also ends before a line with less indent than the tag line, at the next `covers:` line, or after 20 lines. Thus, in the usual layout, the tag of a test that did not run does not bind to the next test. Q42 and "Does not prove" list the limits.
    - A case name matches a word when, without a final `[...]` or `(...)`, it equals the word, ends with the word after one of `.` `::` `/` `#` space `>` `›`, or starts with the word and `/`.
    - A case that has a file binds only a tag of that file. A case with no file and a `classname` binds only a tag of a test file. The dotted path of that file (the path without its extension, with `.` for `/`) must end with the `classname` or with its part before the last `.`, in whole segments. The pytest `classname` `tests.test_valves.TestValves` thus names `tests/test_valves.py`. When no test file has such a path, the case binds a tag of any test file.
    - A tag with no case is not bound. It proves nothing. The message names the fix: put the tag above the test, or add `case:`.
7. The proof. A requirement passes when at least one case that binds to it passed, and no such case failed. A skipped case is no pass and no fail. A case that passed after a rerun (`flakyFailure`, `rerunFailure`) counts as a fail. 2 requirements on one test both bind to it. A case with no tag needs nothing.
8. Where the reports count. `check --reports` and `finish` read them when the key is set. `check` without `--reports` keeps the rule of 0.7.1, so the hook `check --staged` needs no report. With an absent or empty `reports`, `--reports` changes nothing. `init` writes no `--reports`, because its CI job runs no tests. `init` does not know the command of the tests. The change guide gives the 3 steps for the CI job that runs the tests: the tests, `spec-dna evidence stamp`, and `spec-dna check --reports`.
9. A `verified-by` record is a check by a person. It keeps its meaning, with the proof state `verified`. The report does not apply to it.
10. A report is unreadable in these cases: an unknown format, a parse error, a `testsuite` whose `tests` count is not its number of `testcase` elements (a cut file), a file over 64 MiB, an XML `<!DOCTYPE`, or a report or stamp that git tracks (a hand-written report can be in a commit). Each gives SD615. `finish` stops.

**Formats**:

The JUnit subset. spec-dna reads UTF-8 only. It reads the elements `testsuites`, `testsuite` and `testcase`, and the attributes `name`, `classname` and `file`. It reads the children `failure`, `error`, `skipped`, `flakyFailure`, `flakyError`, `rerunFailure` and `rerunError`. It skips comments, CDATA and processing instructions. It reads the 5 predefined entities and the numeric ones. A DTD is an error, so the reader never loads an external entity. The reader is code of spec-dna with no new dependency (Q3).

The line format, for any runner:

```text
spec-dna-report 1
pass<TAB>tests/test_valves.py<TAB>test_closes_on_timeout
fail<TAB>-<TAB>ValveTest.flushesFirst
skip<TAB>tests/sensor_test.go<TAB>TestTimeout/no_reply
```

`<TAB>` is one tab character. The first line is `spec-dna-report 1`. Each other line is `<pass|fail|skip>`, a tab, a path from the repository root or `-`, a tab, and the name of the case. A blank line and a line that starts with `#` do not count.

The stamp, `<report>.stamp`:

```text
spec-dna-stamp 1
tree 3f2a9c1b7e0d4a11
report 9c1b7e0d4a113f2a
```

`spec-dna evidence stamp [--json]` prints `stamped <n> report(s) at tree <hash>: <p> pass, <f> fail, <s> skip`. Exit codes, with the meanings of the table of `docs/commands.md`: 0 stamped, 1 a report is unreadable or no file matches (nothing gets a stamp), 3 configuration (no `reports`), 4 a git or file error. Row 1 of that table gets `evidence stamp`.

**Codes**:

| Code | Name | lite | standard | strict | Where |
| --- | --- | --- | --- | --- | --- |
| SD613 | report-missing | off | error | error | `check --reports`, `finish` 5.1: no file matches `reports`, or a report has no stamp |
| SD614 | report-stale | off | error | error | the same: the stamp names another tree, or the report bytes changed |
| SD615 | report-unreadable | off | error | error | the same: see item 10 |
| SD616 | requirement-unproven | off | warning | error | `check --reports --all`: an active requirement has a full tag, and no bound case passed. A state code, never new |
| SD617 | change-unproven | off | error | error | `check --reports` when the diff deletes the folder, `finish` 5.4: a requirement of the SD916 set has a full tag, and no bound case passed |

The codes are in the new rule group `reports`, so a rule for the group `evidence` of 0.7.1 does not change them (section 11). SD608 and SD916 keep their meaning: no tag and no `verified-by`. The message of SD616 and SD617 gives one reason: no bound case, all skipped, or a case failed, with the case name. The codes run only with a `reports` key that is not empty, in each profile. In `lite` they are off, as each new code (section 11).

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[evidence] reports` | list of globs from the root | `[]`: off | `[]` with a comment in `standard` and `strict` (Q40). `init` detects no runner. Nothing in `lite` |
| `[evidence] tree-exclude` | list of globs | `["**/*.md", "**/*.markdown"]`. A list replaces it | nothing |

**Upgrade**:

No key, no effect: with no `reports`, each profile keeps the rule of 0.7.1. `upgrade` adds no key. A tag of 0.7.1 above its test binds by its place, so it needs no edit. A tag in the body of a test or at the top of a file binds to no case until it gets `case:`.

**Cost**:

- Per change: one test run and one stamp before `finish`, in the checkout where `finish` runs. An acceptor in the same checkout makes this run (D3). An acceptor in another worktree does not, so the builder runs the tests and the stamp again.
- CI: one more command (`spec-dna evidence stamp`) and the flag `--reports`. The tree hash costs 3 git calls. The estimate is 10 to 60 ms for 10,000 files, not a measurement.
- The hook `check --staged`: nothing, because it has no `--reports`.
- The bind reads up to 20 lines after each tag: one `git grep` with context lines in place of the `git grep` of 0.7.1. One `git ls-files` finds a tracked report.
- Agents: the `tdd` and `verify` skills get one sentence on the stamp.

**Does not prove**:

- That the test checks the requirement. A tag is still a claim of the author. The acceptor reads it (D3).
- That a real run wrote the report. A person or an agent can write a report by hand. The stamp binds bytes to a tree, not to a run.
- That the tests ran in CI. `check --reports` reads a file of the disk, outside git. ADR 0024 amends the rule "2 trees and git" of ADR 0001 and ADR 0006 for this flag only.
- That the bound case is the test under the tag. The proof fails in 4 cases. An unrelated case that passes shares a word of the block. A test is in a comment after the tag, so the block starts at the next real test. One case name is in 2 files, in a report with no `file` and no `classname` that names a file. A test is on one line with no deeper line, so the block runs on. `case:` removes each doubt.

**Files and agents.** `src/report.rs` (new: the 2 readers, the stamp), `src/tree.rs` (new: the code tree), `src/evidence.rs` (the bind, `case:`), `src/git.rs` (`hash-object --stdin-paths`, the context lines of `git grep`, and `ls_files` with the full mode, because it keeps only the flag of a submodule today), `src/check.rs` and `src/diag.rs` (SD613 to SD617), `src/config.rs` (keys, the profile table, the group `reports` in `GROUPS`), `schema/spec-dna.schema.json`, `src/main.rs` (`evidence stamp`, `check --reports`), `src/finish.rs` (5.1, 5.4), `src/init.rs` (the key), `src/harness_text.rs` (`tdd`, `verify`), `docs/config.md` (the key, and the group `reports` in the row of `rules`), `docs/diagnostics.md`, `docs/profiles.md`, `docs/commands.md`, `docs/guides/change.md`. Agents: `diagnostics-engineer` (evidence, codes), `core-engineer` (`tree.rs`, CLI, config), `hygiene-engineer` (`finish`), `init-engineer` (`init`, skills), `test-engineer` (fixtures of 5 runners).

**Tests**:

- `tests/evidence_reports.rs`: a pytest `xunit2` report with the case skipped, `check --reports --base main` in `strict`: SD617 for the requirement of an ADD line (before: exit 0).
- The same with the case passed: no SD617. With the case failed: SD617 names the case.
- A tag above `#[test] fn closes()`, a cargo-nextest case `tests::closes`: bound. A Jest case `Valves closes on timeout` and `it('closes on timeout'`: bound. A Go case `TestTimeout/no_reply` and `func TestTimeout`: bound.
- A tag with no case in the report: not bound, and the message names `case:`. A tag with `case:"closes on timeout"`: bound.
- A tag above `def check_timeout():` (pytest does not collect it) and a passed `test_next` below it: not bound (before the block rule: bound to `test_next`).
- A tag in the body of a skipped test, and a passed test after it: not bound (before the indent rule: bound to the next test).
- A skipped `test_init` in `tests/test_a.py`, a passed `test_init` in `tests/test_b.py`, pytest `classname` values: the tag in `tests/test_a.py` binds only the skipped case, so SD617 (before the `classname` rule: proven by `tests/test_b.py`).
- A committed report and stamp: SD615 (before: the hand-written report proves the requirement).
- `tests/init_change.rs`: the CI job of `init` has no `--reports`.
- A code edit after the stamp: SD614. A Markdown edit after the stamp: no SD614.
- A report cut in the middle: SD615, and `evidence stamp` exits 1. A report with `<!DOCTYPE`: SD615.
- With no `reports` key, a fixture of 0.7.1 in each profile: the output of 0.7.1 (golden).
- `tests/finish.rs`: `reports` set and no stamp: `finish` stops at step 5 with SD613 (before: exit 0).

### D2. The proof levels and the proof debt

**Problem**:

A test that passes once can be flaky, and nothing shows it. A requirement with no test looks the same as a requirement whose proof is owed for a known reason. Example: a requirement needs a device that CI does not have. Its author adds a `covers:` tag to an unrelated test to clear SD608. The gate cannot see that the tag is false.

**Mechanism**:

1. The proof state of a requirement, from best to worst: `reliable`, `passed-once`, `verified` (`verified-by`), `tagged` (a tag, with no `reports` key or no fresh report), `owed`, `none`.
2. `passed-once` is the proof of D1. `reliable` is `passed-once`, and each bound case that passed has at least N passes in the reports of the current tree, with no fail. N is `[evidence] reliable-runs`. The runner runs the tests N times and writes N reports. Each report has its stamp. The core keeps no ledger, no retry and no statistics (Q2).
3. `[evidence] reliable-for` selects the changes whose requirements need `reliable` at `finish`: `none`, `higher-risk` or `all`. A requirement of such a change that is below `reliable` stops `finish` 5.4 with SD620. Amended by D70 item 3: the class of the change is the class of `acceptance::record_class`, so a branch cannot lower it. The reliable level needs the test reports (D1) to be on. A `reliable-for` other than `none` with an empty `reports` is a configuration error: exit code 3, and the message says ``[evidence] reliable-for needs [evidence] reports: set reports, or set reliable-for = "none"``. Thus `init` writes `reliable-for` in `strict` as a comment under `reports`, ready to use when the project sets `reports` (Q2).
4. The proof debt. A requirement can end with the marker `<!-- proof-owed: <reason> -->`. The reasons are a closed list: `manual` (a person must look), `environment` (CI has no such device, account or data), `external` (a third party), `pending` (the test is not written). The hash of the requirement does not cover the marker (F3), so a marker gives no SD914 and no SD921.
5. A debt never counts as proof. SD916, SD617 and SD620 stop `finish` as before. For an active requirement with no evidence, SD618 replaces SD608 (Q5). A marker on a requirement that has evidence is stale: SD619.
6. `status` prints one line when a debt exists: `proof: 3 owed (manual 1, environment 2)`. `stats` prints the count of each state. `status --json` gets `proof.owed` and `proof.by_reason`. `stats --json` gets `proof` with one count per state.
7. The record of D3 keeps the state of each requirement of the change at the acceptance. Thus the archive keeps a history of the states with no new store.

**Formats**:

```md
- **sensor-timeout**: When a moisture sensor times out, the controller SHALL close the valve of its bed. <!-- proof-owed: environment -->
```

The marker holds one reason word. It can stand next to `aliases` and `verified-by` markers.

**Codes**:

| Code | Name | lite | standard | strict | Where |
| --- | --- | --- | --- | --- | --- |
| SD618 | proof-owed | off | warning | warning | `check --all`: an active requirement has a debt and no evidence. A state code, never new |
| SD619 | proof-owed-invalid | off | warning | error | `check`: the reason is not in the list, or the requirement has evidence |
| SD620 | proof-not-reliable | off | error | error | `check --reports` when the diff deletes the folder, `finish` 5.4: with `reports`, a requirement of a change that `reliable-for` covers passed fewer than N times |

SD618, SD619 and SD620 are in the new rule group `proof`, so a rule for the group `evidence` of 0.7.1 does not change them (section 11). The profiles (section 11): the proof debt has no key. The marker is an act of the author on one requirement, as `verified-by` is, not a switch of the project. In `standard` its codes are warnings, so a marker never stops a change there. SD618 has the severity of the SD608 that it replaces in `standard`.

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[evidence] reliable-runs` | integer from 2 to 20 | 3 | nothing |

**Upgrade**:

## 3. Independent acceptance (item 3)

### D3. The acceptance record

Amended on 2026-11-21 by [section 15](#d70-to-d79-the-acceptance-in-one-pass) (D70 to D79, [ADR 0032](../adr/0032-acceptance-in-one-pass.md)). Part A built this text. A mark "Amended by D7n" names each item that part B changes, and section 15 gives the new rule.

**Problem**:

The agent that writes the code also says that the code is done, and `finish` deletes the plan. Example: an agent builds `sensor-timeout`, runs its own tests, and runs `finish`. Nobody tried a NaN value from the sensor, which leaves the valve open. No file keeps what was tried.

**Mechanism**:

1. A change needs a record when 2 conditions hold. The acceptance is on: SD927 is not off, which is true in `standard` and `strict` (section 11). SD927 is in the new rule group `acceptance`, so in `lite` only a rule for that group or for SD927 turns it on. The plan is new: a commit added it at a pin of 0.8.0 or later, or the branch added it (P5). This page calls such a change "a change that needs a record". `finish`, `next` and `check` use this one rule. A closed change needs no record. A small fix has no plan, so it needs none. Amended by D70: a third condition is the key `[change] acceptance-for`, the class of `acceptance::record_class` or a matched role of `[owners]`.
2. The acceptor is an agent that did not write the code of the change: a subagent of the building session, or an agent of a new session (Q11). It starts from the brief of item 5 only. It runs the proof, tries to break the change, and writes the record. It edits no code. Amended by D71: the acceptor is also the reviewer of the change, in one pass.
3. The record is one TOML file. Before `finish` it is `<change folder>/acceptance.toml`. `finish` moves it to `.spec-dna/accepted/<slug>.toml`, the one permanent place (P2). If that file exists from an earlier change with the same slug, `finish` writes `<slug>-2.toml`, then `-3`, and so on. The folder is tracked: the cache of spec-dna is in the git directory, and `init` writes no ignore rule for `.spec-dna/`. If the project ignores the path, `finish` stops before it writes, and names the rule (`git check-ignore`).
4. The record binds to a scope, a list of paths and their content (P1, Q7):
    - `accept` writes `scope`: the paths and globs of the scope of the plan (the items of `Files` and the `Files:` of the tasks, as SD913 reads them), and the globs of `[change] shared-paths`.
    - `accept` writes `paths`: the code paths (D1, item 2) of the diff of the change against the lifecycle base that `scope` matches, sorted. Thus the number of open changes does not change the list (Q44).
    - When the diff has no code path in `scope`, for example in a pull request after the code merged, `accept` takes the code paths that changed since the commit that added the plan, in `scope`.
    - `tree` is the hash of D1 over these paths only: one line `<mode> <object id>\t<path>` for each, or `absent\t<path>` for a path that the tree does not have.
    - The record is stale (SD929) when the hash differs, or when the diff of the change now has a code path that `scope` matches and `paths` does not list. `finish` and the checks after it read `scope` and `paths` from the record, not from the plan. Amended by D73: the hash compares with the `tree` of the last follow-up, when the record has one.
    - After `finish`, SD929 has one fix, and its message names it: revert the commit of `finish`, merge the base, run the acceptance again, and run `finish` again.
    - In CI, the checkout of a pull request is the test merge of the branch into the base. The hash reads the content of the paths in that checkout. A base commit that edits one of the paths is a real conflict of meaning, so the record must be stale. A base commit to other paths changes nothing. A Markdown edit changes nothing.
5. The command `accept` has 2 forms. Exit codes of both: 0 written or printed, 1 refused, 2 usage, 3 configuration, 4 git or file error, 5 no folder for the slug. Rows 1 and 5 of the exit-code table of `docs/commands.md` get `accept`. Both forms refuse (exit code 1) while the folder of the change, except `acceptance.toml`, or `spec-dna.toml` has an edit that `HEAD` does not have, in the index or in the working tree. The message says: commit the work, then accept. Thus the brief and its compare (item 8) read the same committed files. Amended by D73 (the rule of part A as built, `refuse_dirty_code`): both forms also refuse while a code path that `scope` matches has an edit that `HEAD` does not have, or is untracked. Thus `tree` is the hash of committed code.
    - `spec-dna accept <slug> [--role <name>] [--session <id>]` writes the skeleton. The skeleton has the computed fields (`scope`, `paths`, `tree` and `acknowledged-by = []`), one `[[acceptor]]` entry, and one `[[proof]]` entry for each requirement of the SD916 set. It also has one `[[invariant]]` entry for each item of `Invariants` (D6, with `[change] invariants`) and one `[[deviation]]` entry for each item of `Deviations` (D7), and each answer starts as `pending`. The entry has `brief = "pending"`, `session` (the value of `--session`, or `unknown` when the value is absent or empty) and `agent = "unknown"`. A second run adds one `[[acceptor]]` entry, with the same role or another, and prints its number. Each `[[attempt]]` and `[[finding]]` names the number of its acceptor. If the code changed, the command refuses: delete the record and accept again. The `toml` crate of the build has no writer (the feature `display` is off), so `accept` and `approve` write the TOML text by hand.
    - `spec-dna accept <slug> --brief [--role <name>]` writes no file. It prints the brief (Q11): one text that is a function of the repository state only. The first line is `spec-dna-brief 1 <slug> <role>`, with the role `acceptor` when `--role` is absent. Then come the task of the acceptor and the rules of the record, as fixed text of the brief format 1 (about 3 KB). Then come the files `intent.md`, `spec.md` (if it exists) and `plan.md` of the folder, whole. Then come `scope`, `paths` and `tree` as item 4 computes them, the items of `Invariants` (with `[change] invariants`) and `Deviations`, and the roles of `[owners]` that match a path of `paths` (D5). The last line is `brief <hash>`: the first 8 bytes of SHA-256 of the text before it, as 16 hexadecimal digits (the form of `src/hash.rs`). The change files and `spec-dna.toml` are the committed ones, by the rule above. The fixed text belongs to the record format: a binary that changes it writes `format = 2`, and it still computes format 1 for a record of format 1.
    - The builder gives the whole output of `--brief`, unchanged, as the prompt of the acceptor, and writes no word of its own. The acceptor copies the hash of the last line into `brief` of its entry.
    - Amended by D72 and D75: the brief has format 2, with the duties of the review and the matched roles by default. The prompt of the acceptor is the line of `next`, `cd '<root>' && spec-dna accept <slug> --brief`, and the acceptor runs it. The form `--follow-up` is new (D73).
6. A person can write the same file by hand, also with the harness level `none`. A skill is no precondition of the gate (ADR 0006).
7. The number of acceptors. A `routine` change needs 1 entry. A `higher-risk` change needs `[change] higher-risk-acceptors` entries (default 1, Q9). Each role of `[owners]` that matches a path of `paths` of the record needs an entry with that role (D5). The brief names the roles of the same set. One entry can count for both. Amended by D72 and D77: an entry has `roles`, so one entry of one pass answers each matched role. The class is the class of `acceptance::record_class` (D70).
8. "Not the author". spec-dna checks 3 signs. None of them is a proof:
    - The brief. SD928 computes the brief of each entry again: the function of item 5, with the role of the entry, the `scope`, `paths` and `tree` of the record, and the files of the change and `spec-dna.toml` from the tree of the entry. The identity of an entry is the triple of its `role`, `session` and `brief`. The tree of an entry is the tree of its adding commit. The commits of the branch are the output of `git rev-list --reverse --first-parent <base>..<tip>`. The tip is `HEAD`. When `HEAD` is a merge commit with 2 parents and its first parent is the lifecycle base, the tip is the second parent. This merge is the test merge that a code host makes for a pull request, and it is not a commit of the branch. The adding commit is the oldest commit of the latest unbroken run of commits whose `<folder>/acceptance.toml` holds an entry with that triple. A later commit of the record does not move it: an approval commit, the commit of a second acceptor, or an edit of the findings. A record that is deleted and written again starts a new run. An entry that no commit has takes the index with `--staged`, else the working tree. An entry whose `brief` differs gives SD928. The message says: ``the brief of acceptor <n> is not the brief of its adding commit <commit>; remove the entry, and accept again from a new brief``. Thus a later tick of a box does not change the result, and SD938 covers a later deviation. Amended by D72 and D73: the triple holds `roles` in place of `role`. A `[[follow-up]]` entry has the pair of its `session` and `brief` as its identity, and the same rule finds its adding commit.
    - Where the compare runs: where the branch adds an entry to the record in the folder of the change, and in `finish` 5.2 for such an entry. An entry that the base already has was compared in its own pull request, so no compare runs for it, also in a later pull request of `finish`. The compare does not run on an archive file or on the default branch. When a shallow clone cuts the history of the branch, SD928 names the cause and the fix (`fetch-depth: 0`), as SD927.
    - The claims. 2 entries with the same `session` and the same `agent` give SD931. The value `unknown` matches no value. A subagent has the session of its caller and an agent id of its own (F12). The skill passes `--session "$CLAUDE_CODE_SESSION_ID"` (F23). No tool gives a subagent its agent id, so `accept` writes `agent = "unknown"`. Thus SD931 never fires on a record that `accept` writes. It fires only on an `agent` value that a person or an agent writes by hand, and it cannot catch a forger, who writes 2 different values.
    - With `approval = "branch"`, a commit that adds or edits the record changes no other path (SD932). Thus the builder cannot change code and record in one commit. The commit of the result of `finish` is the exception: it deletes the folder and adds the archive file.
9. `finish` step 5.2 reads the record of the head: present, valid, fresh, complete, accepted, and with the acceptors that it needs. It stops at the first code of SD927 to SD933 and SD936 to SD940 that is not off. Part 5.3 prints the deviations and, with `branch`, checks the acknowledgement (SD934). Part 5.5 adds the archive file to the writes of `finish`. `check` runs the record codes in 2 places:
    - Where the diff adds or changes a record: only the codes that read the record and its commits (SD928 with the brief of item 8, SD931, SD932). Thus the first of 2 acceptors can commit, and a fix or a new deviation of the builder after the record passes the hook.
    - These checks also run where the diff deletes the folder, and for a change that the branch added and deleted (a branch-born change, with its newest artifacts, as the scope of SD913 reads them). They are the counts, the state and the answers (SD927, SD929, SD930, SD933, SD934, SD938). SD927 needs the archive file in the head. A record that stays in the folder of the base does not count, so a folder that a person deletes with no `finish` gives SD927. A branch-born change also gets SD910 reason 7, so these codes only name the absent record.

    `next` names `accept` again after a code edit. A later change never makes an old record stale. Amended by D71, D73 and D74: `next` has one item `review`. It names a follow-up after a fix of a note, a full run after another code edit, and the owner after 2 rejected records. SD941 joins the checks of the record.
10. The acknowledgement of the record. It is needed when the record has a deviation (D7, Q12). The way depends on `[change] approval` (P4):
    - `base`: the merge of the pull request of `finish`. spec-dna checks nothing more (Q41).
    - `branch`: `spec-dna approve <slug> acceptance` adds the e-mail of its author to `acknowledged-by` and commits that file alone. `approve` refuses an author outside `approvers`, as for each artifact (F10). The walk counts an entry only when 4 conditions hold: the commit added the entry, its author has that e-mail, the commit changes nothing else, and no later commit changes the record. Another such commit and the commit of `finish` are the exceptions. The commit of `finish` moves the same bytes to the archive. A record commit of the acceptor writes `acknowledged-by = []`. Any other commit that changes the record and keeps an entry gives SD932, so no entry outlives the text that it acknowledged. An approval commit of a second approver keeps the first entry, and the commit of `finish` moves entries: each clause of SD932 has these 2 exceptions. The approver then runs `approve` again. Thus an approver never acknowledges a text that changed after the approval. The rule extends condition 3 of the approval commit (ADR 0012).

    The profile `strict` reads the approvals of the base only (F11), so a `strict` project acknowledges a deviation by the merge. The persons of `[owners]` and the acknowledgement by a review moved to 0.8.1 ([note](0.8.1-note.md#5-the-acknowledgement-by-a-person-and-by-a-review)).
11. Who writes what. The builder runs `accept --brief` and passes its output. It never writes the brief, and it never edits the record. The acceptor writes the record and commits it alone, in each mode. An agent never adds an entry to `acknowledged-by`: `APPROVAL_RULE` gets a sentence that says so, and the hook `protect-approvals` denies a commit that adds an entry to the record of a change folder. It allows the commit of `finish`, which deletes that record and adds the same bytes under `.spec-dna/accepted/`. An approval commit comes from `spec-dna approve`, and rule A of the hook already keeps that command for a person. Amended by D75: with `[harness] protect-approvals = true`, rule D of the hook denies a commit of the agent `acceptor` that commits a path other than one record, as far as the text of the command shows it.
12. The trust root. A forged record costs one file and one commit. spec-dna cannot show who wrote it, which model ran, which text the acceptor read, or that the acceptor worked apart from the builder. The person who acknowledges (the merge or the approval commit) and the evals of the `accept` skill are the trust root. The record makes the work visible and keeps it. The brief makes the input of each acceptor recomputable, not true.
13. A new session in `strict`. The gate cannot check that an acceptor ran in a new session: CI sees no session, and the session of the builder is not in the repository (Q10). No profile asks for a new session as a rule. The skill `accept` gives advice only: for a `higher-risk` change, prefer an acceptor in a new session. A session trailer of the builder would give a check, and the [0.8.1 note](0.8.1-note.md#1-what-stays-open) keeps that item.

Rules of a valid record (SD928):

- The file parses as TOML, has `format = 1`, has no unknown key, and is at most 16,384 bytes.
- `change` is the slug. `tree` has 16 hexadecimal digits.
- `scope` is not empty when the plan has a path in `Files`. `paths` is sorted, has no duplicate, and holds code paths that `scope` matches.
- `paths` is not empty when a task of the plan has `Files:` other than `none`. A record of a pull request with no code thus fails, unless `accept` took the paths since the commit that added the plan.
- No value is `pending`.
- Each `[[acceptor]]` has `brief`, `session` and `agent`. Each `brief` is the hash of the brief of that entry, computed again from the tree of the commit that added the entry (item 8).
- Each `[[attempt]]` and `[[finding]]` names the number of an `[[acceptor]]` entry. Each acceptor has at least one `[[attempt]]`.
- A `not-affected` or `violated` answer has a `reason`.
- Each finding has a path from the root and a text.
- The top `result` is `accepted` only when each acceptor accepted, no `important` finding exists, no invariant is `violated`, and no deviation is `rejected`.
- Amended by D72 and D78: a `blocker` takes the place of an `important` finding, a `rejected` result needs a reason, the ids of `[[deviation]]` and `[[invariant]]` are unique, and each `[[follow-up]]` follows D73.

The `accept` skill, the 5 parts of D2 of 0.7.0. Amended by D71: the skill `accept` merges into the skill `review`, whose text in `standard` and `strict` holds these steps. `lite` keeps the `review` of 0.7.1 (D76).

- When to use: the tasks of a change are done. The builder starts the acceptor, and the acceptor writes the record.
- Commands: (1) If you built the change, do not accept it. Run `spec-dna accept <slug> --brief`, with `--role <name>` for each role of `[owners]` that the brief names. Give each whole output, unchanged, as the prompt of one agent `acceptor`. Add no word before or after it. For a `higher-risk` change, prefer an acceptor in a new session. (2) As the acceptor, work from the brief only. If your prompt is not the output of `spec-dna accept <slug> --brief`, run that command and read its output. (3) Run each command of `Proof`. With `[evidence] reports`, run the tests and `spec-dna evidence stamp` in one command line. (4) Run `spec-dna accept <slug> --session "$CLAUDE_CODE_SESSION_ID"`, with the `--role` of your brief. Write the number that it prints as `acceptor` in each of your attempts and findings. Copy the hash of the last line of your brief into `brief` of your entry. (5) Try to break the change: bad input, limits, errors, each path of `Files`, and each requirement read as a test. Write each try as `[[attempt]]`. (6) Answer each invariant, and read the rules that `spec-dna context` serves for `Files`. If `spec-dna next` lists summaries that the change made stale, read each edited summary against its requirements. Write a finding with the path of the summary if it is wrong. (7) Read each deviation, and compare it with the diff. (8) Write each defect as `[[finding]]` with its path. Set each `result`. (9) Commit the record alone, in a call of its own after the write: the hook `protect-approvals` denies one call that writes `accepted` and runs `git commit`. Edit no other file.
- Artifact: `acceptance.toml` in the folder of the change.
- Check: stage the record with `git add`, because `--base` reads tracked files only. Then `spec-dna check --base origin/HEAD` gives no SD928. After the record is committed, `spec-dna next` and `spec-dna finish <slug> --dry-run` show SD929 (stale) and SD930 (rejected): `check` does not.
- If the check fails: fix the record. Never fix the code: write a finding.

The agent file `.claude/agents/acceptor.md` (a new role of the levels `lean` and `full`, model `opus`, effort `high`): tools `Read`, `Grep`, `Glob`, `Bash` and `Write`. Description: "Tries to break a finished change from the brief of `spec-dna accept --brief`, and writes its acceptance record. It edits no code." Body: "Your prompt is the output of `spec-dna accept <slug> --brief`. If it is not, run that command first, and work from its output." Then steps 3 to 9 of the skill, the sentence "Write only `acceptance.toml`", and "Report each defect as a finding. Do not fix it." The role comes with the skill `accept`: `init` and `upgrade` write the agent file only where they write the skill, so `lite` gets neither (section 11). `next` gets the item `accept` in the stage `deploy`, after `review` and before `finish`, with the skill `accept`. It gets the item only for a change that needs a record (item 1). Amended by D71 and D75: the role comes with the skill `review` where the acceptance is on. `next` has one item `review`, with the prompt line. The body tells the acceptor to run its prompt first and to start each shell call with the `cd '<root>' &&` of the prompt.

The outline of the cost measurement (D62 gives the full method):

- The oracle reads `<folder>/acceptance.toml` before `finish`: the top `result`, and the `path` and `severity` of each `[[finding]]`. It also counts `[[acceptor]]` and `[[attempt]]`.
- A fixture with a planted defect in the path P passes when `result = "rejected"` and an `important` finding has the path P. A clean fixture passes when `result = "accepted"`. Amended by D72: a `blocker` finding.
- The cost of a run is `total_cost_usd` of the agent output. The report gives the mean and the maximum per run, and the share of planted defects that the acceptor found.

## 5. Owners, invariants and write-back (items 5 to 7)

### D5. Owners by path

**Problem**:

A change can touch a sensitive path, and nothing asks for the review that the path needs. Example: an agent edits `src/auth/session.rs` in a `routine` change. No security review happens, and `check` passes.

**Mechanism**:

1. `[owners]` maps a glob from the root to a list of role names. A role is `[a-z][a-z0-9-]*`, at most 40 characters. The glob form is the form of `high-risk-paths`, with the match of `src/glob.rs`. Another entry, for example a login or an e-mail, is exit code 3: the persons of `[owners]` moved to 0.8.1 ([note](0.8.1-note.md#4-the-persons-of-owners-item-5-of-080)). Amended by D77: an entry `@<login>` or an e-mail gives a warning that names 0.8.1, needs nothing, and keeps the exit code. Another entry that is no role name stays exit code 3.
2. Each glob that matches a path of `paths` of the record applies. No order and no last match exist, so the result is the union.
3. The paths that `[owners]` reads are `paths` of the record (D3 item 4): the code paths of the diff of the change that its `scope` matches. The brief names the roles of the same set, and SD933 reads the same set. Thus the number of open changes does not change the roles, and a glob that matches only Markdown, or a path outside `scope`, needs no role. The folder of the change and the archive are never code paths. Amended by D70 item 7 and D77: `[owners]` reads the role paths. They add each code path of the diff that no `scope` matches, so such a path needs its role, and the paths since the commit that added the plan for a pull request with only `finish`.
4. A role is satisfied by an `[[acceptor]]` entry with that role in the record (D3). Each role of each matched glob is needed. The role has no file of its own: the builder runs `accept --brief --role <name>`, and the acceptor reads the paths as a reviewer of that role. Amended by D72 and D77: an entry has `roles`, and the brief names each matched role by default. Thus one pass answers each role, and the builder passes no `--role`. A matched role also makes a record needed for a `routine` change (D70).
5. `[owners]` has no R, A, C or I letters, no persons and no list of personas. A role name is a word that the record repeats.

**Formats**:

```toml
[owners]
"src/auth/**" = ["security-reviewer"]
"migrations/**" = ["db-reviewer"]
```

The first line needs an acceptor with the role `security-reviewer`.

**Codes**:

SD933 (a role) of D3. A bad glob or entry is exit code 3. The table needs the acceptance, so in `lite` it has no effect (section 11).

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[owners]` | table: glob to a list of role names | `{}` | nothing |

**Upgrade**:

No table, no effect.

**Cost**:

- One more acceptance run for each role that matches. A `higher-risk` change counts a role entry as its second acceptor.
- Amended by D77: no run more for a role, because one entry answers each matched role. A matched role costs one run for a `routine` change in `standard`, which needs no record without it.

**Does not prove**:

- That the role acceptor has the skill of the role. The role is a name.

**Files and agents.** `src/config.rs` (the table), `schema/spec-dna.schema.json`, `src/owners.rs` (new: the match, the roles), `src/record.rs`, `src/accept.rs` (the roles of the brief), `docs/config.md`, `docs/guides/change.md`. Agents: `core-engineer` (config, brief), `diagnostics-engineer` (SD933).

**Tests**:

### D6. Invariants with ids

**Problem**:

A rule of the layer `rules` must stay true, but no change says which rule it can break. Example: a rule says "the controller SHALL close each valve on a fault". A change of the timeout path breaks it. Its spec names no rule, and the review does not see the link.

**Mechanism**:

1. The id of an invariant is the requirement id of a rule: `<doc-id>#<key>` of a document of the type `rule`. It is stable (SD202 and the aliases keep it). No new id is needed: a second id would be a second name for one sentence.
2. The key `[change] invariants = true` turns the mechanism on (section 11). With the key, `spec-dna new spec` writes the section `Invariants` with the item `- none`, and a spec declares its invariants there, one item each: `- <doc-id>#<key>@<hash>`. `spec-dna show <id>` prints the hash. `- none` says that none applies. The skill `specify` gives one instruction: "If the spec has the section `Invariants`, list each rule that the change must keep true, or keep `- none`." Without the key, the template has no such section, and a section `Invariants` is plain text, as in a spec of 0.7.1. Thus a project gets no SD936 to SD938 for an invariant with no act of its own.
3. `check` resolves each item: the id names a requirement of a `rule` document, and the hash matches (`hash_matches`, P1). A delta line, `rests-on` (D51) and the section `Invariants` are the places where a hash in a reference counts. ADR 0027 amends ADR 0006 ("Only a delta line checks it"). The delta of the same spec can change the rule of an item (`CHANGE`). Then spec-dna compares the hash of the item with the hash of that delta line, not with the rule now. The delta line pins the old text (SD914), and after step 4 of `finish` the text is new by design. A rule that the same delta adds or removes is no invariant of the change. It cannot stay true across the change, and an added rule has no hash to pin. SD936 reports such an item at once, before the approval, and its message says to remove the item.
4. The record answers each declared item with the same pin: `held`, `not-affected` with a reason, or `violated` with a reason. `violated` makes the result `rejected`.
5. A change with no spec declares no invariant (Q18). The skill `accept` still reads the rules that `context` serves for the files of the change, and writes a finding for a rule that the change breaks.

**Formats**:

```md
## Invariants

- rules/safety#valve-closed-on-fault@a1b2c3d4e5f60718
```

**Codes**:

| Code | Name | lite | standard | strict | Meaning |
| --- | --- | --- | --- | --- | --- |
| SD936 | invariant-invalid | off | error | error | An item is not `<doc-id>#<key>@<hash>` or `none`, names no requirement, names a requirement that is not in a `rule` document, or names a rule that the delta of the same spec adds or removes |
| SD937 | invariant-stale | off | error | error | The hash of an item is not the hash of the rule now. For a rule that the delta of the spec changes, the hash of the item is not the hash of that delta line. A warning for a spec that the diff does not touch, as SD914 |
| SD938 | record-incomplete | off | error | error | Where the diff deletes the folder: the record has no answer with the same pin for a declared invariant, or no entry with the same text for a deviation (D7) |

The codes are in the rule group `acceptance` (D3). SD936 and SD937 run only with `[change] invariants = true`. SD938 runs with the acceptance, and it reads the invariants only with the key. `finish` stops on each at step 5.2. When the default branch changes a pinned rule before `finish`, the author pins it again in a pull request of its own, as for SD914.

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[change] invariants` | boolean | `false` | `true` in `strict` |

Why a key, and not the section alone: the owner turns on each mechanism of `standard` other than the acceptance and the roll-up by a key (section 11). A section that the skill and the template ask for is no act of the project. The key also tells `new` to write the section, so the skill text stays the same in each profile.

**Upgrade**:

`upgrade` adds no key, so nothing changes. With the key, the section is read only in a spec that a commit added at a pin of 0.8.0 or later (the lookup of D3). A spec of 0.7.1 with a heading `Invariants` keeps its meaning.

**Cost**:

- One line of about 60 bytes for each invariant in the spec, and one answer in the record.
- When a rule changes, each open spec that pins it gives SD937. The author runs `show` and pins it again.

**Does not prove**:

- That the spec names every rule that applies.
- That `held` is true. The acceptor states it.

**Files and agents.** `src/change.rs` (the section, `ItemSection::Invariants`), `src/parse.rs` (if the section items need the cache), `src/lifecycle.rs` (SD936, SD937), `src/record.rs` (SD938), `src/harness_text.rs` (`specify`, `accept`), `src/templates.rs` (the section of the spec template with the key), `src/config.rs` and `schema/spec-dna.schema.json` (the key), `src/init.rs` (the key in `strict`), `docs/config.md`, `docs/types.md`, `docs/diagnostics.md`. ### D7. Write-back of deviations

**Problem**:

The work differs from the plan or the spec, and the record of the difference is deleted with the plan. Example: the builder moves the timeout check to `src/sensors.rs` and closes the valve after 2 failed reads, not 1. `finish` applies the old delta and deletes the plan. Nobody acknowledged the change of behavior.

**Mechanism**:

1. The plan has the optional section `Deviations`. The builder adds one item for each deviation, in the commit of the work. The edit changes the plan body after its approval, as the tick of a box does. SD910 reads the status and the `Files` of the plan at its approval commit only (`src/approval.rs`, `code()`), so the edit gives no finding.
2. An item is `- <id> (<kind>): <text>`. The id is unique in the section. The kind is `plan` (the files, the tasks, the order or the approach) or `spec` (the behavior differs from a requirement or a delta line).
3. A `spec` item needs a way to fix the difference: `Delta: <verb> <doc-id>#<key>`, which names a line of the delta of the spec, or `Follow-up: <slug>`, which names a change folder that the tree has. A change of the delta of an approved spec needs a new approval, as B6 of 0.7.1. A `plan` item needs only the acknowledgement.
4. The acceptor copies each item into the record (`[[deviation]]`), checks it against the diff, and gives the verdict `accepted` or `rejected`. A deviation that the acceptor finds and the plan does not list is a finding.
5. `finish` prints each deviation after the line `Hours:`, as `Deviations: <n>` and one line each, also with `--dry-run`. Amended by D78 item 2: it prints the `[[deviation]]` entries of the record, with their verdicts. `finish --json` gets `deviations`: a list of `{"id","kind","text","verdict"}`. With a deviation, the record needs an acknowledgement (D3, item 10). Slice S6 builds the check of it (SD934). In part A (slices S0 to S5), the merge acknowledges a deviation in each mode.
6. After `finish`, the deviations live in the archived record. When the diff deletes the folder, CI reads the plan of the base tree, which may not have them, so the record is their only carrier (F8).

**Formats**:

```md
## Deviations

- d1 (plan): The timeout check moved to `src/sensors.rs`, because the sensor owns the timer.
- d2 (spec): The valve closes after 2 failed reads, not 1. Delta: CHANGE requirements/valves/closing#sensor-timeout
```

**Codes**:

| Code | Name | lite | standard | strict | Meaning |
| --- | --- | --- | --- | --- | --- |
| SD939 | deviation-invalid | off | error | error | An item of `Deviations` is not `- <id> (<kind>): <text>`, has a kind outside `plan` and `spec`, or repeats an id |
| SD940 | deviation-unresolved | off | error | error | A `spec` item names no line of the delta and no change folder of the tree |

SD938 covers a deviation that the record does not answer. The codes are in the rule group `acceptance` (D3). `finish` stops on each at step 5.2. The deviations are a part of the acceptance: the record is their carrier, and the acceptor checks them. Thus they need no key, and they are on where the acceptance is on (section 11).

**Config**:

None.

**Upgrade**:

The section is read only in a plan of a change that needs a record (D3 item 1).

**Cost**:

- One line of about 100 bytes for each deviation, and its copy in the record.
- With `branch`, one approval commit of an approver for a change with a deviation. With `base` and in `strict`, the merge.

**Does not prove**:

- That the list is complete. The acceptor compares it with the diff, and can miss one.

**Files and agents.** `src/change.rs` (the section), `src/lifecycle.rs` (SD939, SD940), `src/finish.rs` (5.2, 5.3, the output), `src/main.rs` (`finish --json`), `src/harness_text.rs` (`execute`, `finish`, `accept`), `docs/types.md`, `docs/commands.md`, `docs/guides/change.md`. Agents: `core-engineer`, `diagnostics-engineer`, `hygiene-engineer`, `init-engineer`.

## 6. Roll-up (item 8)

The chain is: requirements, then area summaries (one level for each depth of the folders), then `system`, then `product`. Each upper document stores pins of the documents below it. The gate checks the pins, never the meaning.

### D50. The type `summary` and the layer `summaries`

**Problem**: an agent that edits `requirements/valves/closing.md` has no short text of the area `valves`. No tool tells the agent that `system.md` still says "a valve closes after 60 seconds" when the requirement now says 30. `DocType` has no summary type, and "Summary" is only a heading of `incident` and `intent`.

**Mechanism**:

- A new type `summary`, the 16th `DocType`. No statuses, no required sections, no requirement keys (`has_requirements` is false), not normative. `context` serves it in its own tier (D56).
- A new layer `summaries` in the default graph: types `summary`, folder `summaries`, `keep = "forever"`, `context = "always"`, no edges, level 0. The small graph does not get it. `spec-dna layer add summaries` adds it, with `types = ["summary"]` when the command has no option of content. Each file in the folder of the layer is a summary, also a `README.md`: `summaries/<area>/README.md` names the area `<area>/README` and gives SD644 (S8a).
- The path gives the area: `<summaries folder>/<area>.md` is the summary of the folder `<requirements folder>/<area>/`. `summaries/valves.md` is the summary of `requirements/valves/`, and `summaries/valves/drives.md` is the summary of `requirements/valves/drives/`. A folder of any depth is an area. Thus a split area gets a deeper summary, and the number of levels follows the folders.
- The top of the chain: a `system` document or a `product` document with the field `rests-on` (D51). Such a document rests on the whole layer `requirements`. A `product` with `rests-on` rests on each `system` document that has `rests-on`.
- `spec-dna new summary <area>` writes `summaries/<area>.md` with the pins of D51 and a body with `{{...}}` placeholders (SD306 until an agent writes the text). An area with no folder is a usage error.
- The implied graph of a project with no `[layers]` table does not get the layer. Reason: a 0.7.1 project can have a folder `summaries/` with other documents, and a new place type would change their type (P5).
- `init` writes the default graph (`Graph::default_graph()`) for a project of 30 documents or more, in each profile. In `standard` and `strict`, such a new project gets `[layers.summaries]` with `types = ["summary"]`. In `lite`, the roll-up is off (section 11), so `init` leaves the layer `summaries` out of the graph that it writes. A project of fewer than 30 documents gets the small graph, with no such layer.

**Formats**: `summaries/valves.md` (with the pins of D51):

```md
---
rests-on:
  - requirements/valves/closing#close-on-timeout@3f2a9c1b7e0d4a11
  - requirements/valves/closing#max-angle@0b7e2d91c4a5f310
  - summaries/valves/drives@9a1c44e0d2b7f6a3
---

# Valves

A valve closes 30 seconds after its sensor stops. It never opens more than 80 degrees. The drives of the valves have their own summary.
```

**Codes**: SD644 (D52). **Config**: the layer `summaries` (`types`, `dir`). Budget of the type: soft 3,000, hard 6,000 characters (the budget of `rule`), with `[budgets.summary]` as for each type.

**Upgrade**: `upgrade` adds no layer. A project with no summary has no new diagnostic. A project with `[layers]` gets SD303 for a summary until it runs `layer add summaries`; the message names that command.

**Cost**: none until a project writes a summary. A summary is at most 6,000 characters, about 1,500 tokens.

**Does not prove**: that a summary is true, complete or useful. The type gives a place and a budget, not a meaning.

Files and agents: `src/model.rs` (`DocType`, `COUNT` 16), `src/layer.rs` (`DEFAULT_GRAPH`, a flag that keeps the layer out of `implied`), `src/config.rs` (`DEFAULT_BUDGETS`), `src/templates.rs`, `src/main.rs` (`new summary`), `docs/types.md`, `docs/config.md`, amendment of ADR 0001 and ADR 0005 by ADR 0028: `core-engineer`. `src/detect.rs`: no change.

Tests: `tests/templates_new.rs`: `new summary valves` writes the pins of the current tree; `new summary nope` exits 2. `tests/layer_cmd.rs`: `layer add summaries` adds the layer. The unit test `the_implied_graph_keeps_the_layers_of_the_types_in_use` (`src/layer.rs`) asserts that the implied graph equals the default graph; it changes to "the default graph without the layer `summaries`". `tests/init_graph.rs`: `init` of 30 documents writes `[layers.summaries]` in `standard` and none in `lite`, and `init` of fewer writes none. `tests/config_layers.rs`: a project with no `[layers]` and a folder `summaries/` of `research` documents keeps their type (before: no layer; after: still no change).

### D51. The pins: `rests-on`

**Problem**: no field stores "the text as it was" of a requirement. ADR 0001 reserves the suffix `@<hash>` for suspect links, and spec-dna parses it and ignores it. Thus a summary cannot become stale.

**Mechanism**:

- The front matter field `rests-on` holds a list of pins in the reference form of P1: `<doc-id>#<key>@<16 hex>` for a requirement, `<doc-id>@<16 hex>` for a document. The front matter is not in the body. Thus a pin is not in the hash of the body, the budget or `context`. A new pin never makes the level above stale.
- A list with one pin for each requirement, not one combined hash. Reasons: it uses `hash_matches` and the current hashes (no new hash definition). A diagnostic names the requirement that changed, also with no base. A pin resolves through aliases one by one. The cost is one line of about 60 bytes for each requirement in the front matter. The area budget (D55) bounds the number of lines.
- The frontier of a document is the set of items that it must pin:
  - A summary of the area `a`: each active requirement under the folder of `a`. If the requirement is under a sub-area that has a summary, the item is the summary of the highest such sub-area, not the requirement.
  - A `system` document with `rests-on`: the same rule over the whole layer `requirements` (the folder is the root area).
  - A `product` document with `rests-on`: each `system` document with `rests-on`. With no such document, the frontier of the layer.
  - An active requirement is a requirement of a document with the status `active`, as SD608 reads it (`evidence::needs_evidence`), in a document of the layer `requirements` (S8a).
  - A `system` or `product` document is a roll-up document when its front matter has the key `rests-on`, also with an empty list. An empty list gives SD642 for each item of the frontier (S8a).
- A pin resolves as a reference: the aliases of a moved document, the inline aliases of a moved key, the section aliases of a split, and the legacy ids. An ambiguous alias is an invalid pin (SD643). `refresh` writes the canonical id.
- A pin to a requirement matches when `hash_matches(req, hash)` is true (the hash of `show`, or `frozen`). A pin to a document matches when the hash equals the `frozen_hash` of the document.
- A removed requirement: its pin resolves to nothing. The pin is stale (SD641, "removed"). `refresh` drops it.
- Cycles: a pin must name an item of the frontier. The frontier holds only items below the document (deeper folders, requirements, or `system` for `product`). A summary that pins its parent, or a `system` that pins a `product`, is an invalid pin (SD643). Thus no cycle can pass `check`.

**Formats**: see D50. The pins are sorted by id. `system.md` at the top:

```md
---
rests-on:
  - summaries/sensors@c41f0a9e7b2d6183
  - summaries/valves@5d0e7c2a91b3f4e8
---
```

**Codes**: SD641 to SD643 (D52). **Config**: none.

**Upgrade**: a document with no `rests-on` is not a roll-up document. A 0.7.1 tree has none. The front matter parser already reads a list of strings, so `PARSER_VERSION` changes only if the cached data gets the field.

**Cost**: front matter bytes only. `context` and `show` do not print front matter.

**Does not prove**: that the text of the document says anything about a pinned requirement. A pin says "the author saw this text", not "the summary covers it".

Files and agents: `src/rollup.rs` (new: the pin parser, the frontier, the match; pure functions that `check`, `finish`, `refresh`, `new`, `next` and `context` share), `src/model.rs` (the field), `src/change.rs` (`hash_matches` stays): `core-engineer`.

Tests: unit tests in `src/rollup.rs`: the frontier of a nested area with and without a sub-summary; a pin through a document alias, a key alias and a section alias of a split; a pin to the parent gives an invalid pin; the frozen hash of a summary does not change when a link destination changes.

### D52. The codes of the roll-up: SD641 to SD645

**Problem**: `finish` changes `requirements/valves/closing#close-on-timeout`, and `check` says nothing about `summaries/valves.md` and `system.md`.

**Mechanism**: `check` reads each document of the type `summary` and each `system` or `product` document with `rests-on`. It compares the pins with the frontier and the hashes of the head tree. A new rule group `rollup` holds SD641 to SD645. Each stale pin is one diagnostic, with the pin id as its target. Thus the gate sees a second stale pin of one summary as new.

**Formats**: messages, for example ``SD641 summaries/valves.md: the pin `requirements/valves/closing#close-on-timeout` is stale: its text changed; read the requirement, edit the summary, then run `spec-dna refresh summaries/valves` ``.

**Codes** (all default to Warning, P6; the profile table sets the rest):

| Code | Name | Finding | lite | standard | strict |
| --- | --- | --- | --- | --- | --- |
| SD641 | `summary-stale` | A pin no longer holds: the text changed, the target was removed or is not active, or the target is no longer in the frontier (it moved to another area, or a sub-summary now stands for it) | off | error | error |
| SD642 | `summary-incomplete` | An item of the frontier has no pin: a new requirement, a requirement that became active, or a new sub-summary | off | error | error |
| SD643 | `pin-invalid` | A pin is not in the pin form, is ambiguous, names a document of the same or a higher level, or sits in a type other than `summary`, `system` and `product` | off | error | error |
| SD644 | `summary-no-area` | A summary whose path names no folder of the layer `requirements` | off | error | error |
| SD645 | `summary-repinned` | Against the base, the set of pins of a document changed and its text did not (a refresh with `--holds`). The set compares resolved targets and hashes. A pin that `refresh` rewrites from an alias to the canonical id is no change. A document that a change finished in the diff edited (the compare of D54, step 2) is not reported | off | warning | warning (Q28) |

SD641 or SD643 for a pin that names no item of the frontier (S8a): SD641 when the frontier of the document can hold such a target and now does not (it moved to another area, a sub-summary now stands for it, a `system` lost its `rests-on`). SD643 when no frontier of the document can hold it: another type, a heading that is no requirement, a document of the same or a higher level, or an ambiguous alias. A document of 0.7.1 with a field `rests-on` gets SD643 in `check --all`. The base has the same finding, so it is not new, and the gate does not stop.

SD645 needs a base, as SD921 does. Its base and the base of the guard of D53 are the lifecycle base, else the `--base` of the command. A document whose version in the base has no `rests-on` gets its first pins: it gets no SD645 and no guard (S8a). The owner decided the severity of staleness (SD641, SD642) on 2026-11-18: an error in `standard` and `strict`, a warning in `lite`. On 2026-11-19 the owner turned each new mechanism off in `lite`, so the 5 codes are off there (section 11).

**Config**: the group name `rollup` in `[rules]` (`rollup = "off"` turns the 5 codes off).

**Upgrade**: no roll-up document in a 0.7.1 tree, so no finding. An error fails the gate only when it is new against the base. Thus a stale summary of the base does not stop a later change.

**Cost**: one pass over the pins and the active requirements: linear in their number.

**Does not prove**: the meaning of a summary. A summary with a wrong text and correct pins passes. SD645 shows a claim, it does not check it.

Files and agents: `src/check.rs` (calls `src/rollup.rs`), `src/diag.rs`, `src/config.rs` (profile table, `GROUPS`), `docs/diagnostics.md`, `docs/profiles.md`: `diagnostics-engineer`, `core-engineer` (`config.rs`).

Tests: `tests/rollup_checks.rs` (new, DIA): a summary that pins a changed requirement gives SD641 in `standard` (error) and nothing in `lite` (off); a removed requirement gives SD641 "removed"; a new requirement gives SD642; a pin to the parent summary gives SD643; `summaries/nope.md` gives SD644; a re-pin with the same body against the base gives SD645, and none with no base. The `check` golden files of a corpus with no summary do not change.

### D53. `spec-dna refresh` and its guard

**Problem**: an agent that rewrites a summary must write the new pins. If the command writes pins with no condition, an agent can silence SD641 with one command and read nothing.

**Mechanism**:

```text
spec-dna refresh <id>... [--holds] [--base <rev>] [--dry-run] [--json]
spec-dna refresh --all [--base <rev>] [--dry-run] [--json]
```

- For each named roll-up document, `refresh` writes `rests-on` as the frontier of D51, with the current hashes and canonical ids, sorted. It changes only the front matter.
- The guard applies to a document that has a finding of SD641 or SD642, and whose `frozen_hash` equals the one in the base. `refresh` refuses that document (exit code 1) and names the stale pins. The base is the base of the change checks; with no base, `HEAD`. A document that is not in the base has no guard, and neither has a document whose version in the base has no `rests-on`.
- `--holds` writes the pins of a refused document. The person or the agent says that the text still holds, for example after a typo fix in a requirement. The diff then shows a changed front matter and an unchanged body, and `check` gives SD645.
- `--all` refreshes each roll-up document with a finding, with the guard. It lists each refused document, so its output is also the list of the work. `--all` with `--holds` is a usage error, so a claim names each document.

The guard stops a silent refresh: it makes a refresh with no text change a named claim that the diff, SD645 and the output of `finish` show. The guard does not check that a new text is true or that it is about the changed requirement. A one-word edit passes the guard. Whitespace does not count, because the hash normalizes it. After one edit against the base, each later refresh of that document in the same branch passes the guard. Only a reader can check meaning: the acceptor (item 3) or the owner.

The acknowledgement (P4): a summary is not an artifact of a change, so it needs no status and no approval commit of its own. An edit of its text, and a claim with `--holds`, are in the diff of the pull request. The acceptance record does not carry the claim in 0.8.0 (Q28).

| Refresh | `base` | `branch` |
| --- | --- | --- |
| With a text edit | The merge of the pull request | Nothing more (the diff) |
| With `--holds` | The merge of the pull request | Nothing more: SD645 shows it |

**Formats**: output lines `refreshed <id>: <n> pins (<a> added, <c> changed, <r> removed)`, `held <id>: the text did not change (SD645 shows it)`, `refused <id>: ...`. `--json`: `{"refreshed":[...],"held":[...],"refused":[{"id","pins"}]}`. A named document that is current counts as `refreshed`, with 0 added, 0 changed and 0 removed. With `--dry-run`, the lines start with `would refresh` and `would hold`, a `refused` line stays, the exit code is the same, and `--json` keeps its shape (S8a). The flag `--holds` of `refresh` takes no value, because the ids of the command name each document of the claim. `finish` names them with `--holds <id>` (D54).

**Codes**: SD645. Exit codes, with the meanings of the table in `docs/commands.md`: 0 done; 1 the guard refused a document (a refusal, as the preservation check of `mv`); 2 usage, also `--all` with `--holds` and an id that is not a roll-up document; 3 configuration or pin; 4 git or file error; 5 an id names no document. The table gets `refresh` in rows 1, 2 and 5.

**Config**: none.

**Upgrade**: a new command. No effect on a tree with no roll-up document.

**Cost**: one command for each roll-up document that an agent rewrote or found true.

**Does not prove**: that a reader read the requirement. It proves only that the text changed, or that someone wrote `--holds`.

Files and agents: `src/rollup.rs` (the write, with `config_text` style front matter edits), `src/main.rs` (command, help, exit codes), `docs/commands.md` (section `refresh`): `hygiene-engineer` (it edits documents, as `mv`), `core-engineer` (CLI).

Tests: `tests/rollup_refresh.rs` (new, HYG): a stale summary with an unchanged body is refused (exit 1) and stays as it was; with `--holds` it gets the pins, and `check` gives SD645; after an edit of its body, it gets the pins with no flag; `--all --holds` exits 2; a removed requirement drops its pin; a pin through an alias gets the canonical id.

### D54. `finish`, `next` and `mv` with summaries

**Problem**: `finish` applies the delta, and its step 5 stops on each new error. The new SD641 that its own delta causes would stop `finish` in `standard` and `strict`. The text of a requirement changes only in step 4 of `finish`, so no pin of an area summary is stale during the build. The acceptor works before `finish`, so the acceptor cannot see an edit that comes after `finish`.

**Mechanism**, the flow of one change:

- In the build. `next` prints one note for the due roll-up documents: each summary, and each `system` or `product` document with `rests-on`, whose frontier holds a target of a `CHANGE`, `REMOVE` or `ADD` line. In a flat project, `system` itself can be due: ``note: the delta makes summaries/valves due at finish; edit the text of a summary whose meaning changes, and name each other one in `spec-dna finish <slug> --holds <id>` ``. A note has no done state and asks for no edit. The note does not change the stage.
- In the build, the agent edits the text of each due summary whose meaning changes. The pins of that summary still match, because the requirement text has not changed yet. The level above pins the body of the summary, so `check` gives SD641 for `system` at once. The agent edits `system` and runs `spec-dna refresh system`, or runs `spec-dna refresh system --holds`, in the same commit. The acceptor reads all these edits in the diff.
- At `finish`: `spec-dna finish <slug> [--holds <id>...]`. One function `finish::rollup()` in step 5, after the evidence (part 5.4) and before the archive (5.5) and `no_new_errors` (5.6). It has no step number, because it never stops (P3):
  1. It computes the roll-up findings of the rebuilt tree.
  2. It re-pins each due roll-up document whose text the change edited, from the deepest level up. The change edited a text when its `frozen_hash` differs from its hash in the tree before the commit that added the plan of the change (the lookup of P5). With no such commit, the compare uses the base. A re-pin changes only the front matter, so one pass is enough.
  3. It re-pins each due roll-up document that `--holds` names. `--holds <id>` takes one id, and it can repeat: `finish <slug> --holds summaries/valves --holds system`. Thus each id of a claim is named, in `refresh` as a positional id with the flag `--holds`, and in `finish` as the value of `--holds`. With `--holds`, the agent claims that the text still holds. The diff shows the claim, and `check` gives SD645. An id that names no due roll-up document is a usage error (exit code 2, row 2 of the table in `docs/commands.md`), and `finish` changes nothing. `finish` reports it after steps 0 to 5.4, with nothing written (S8b).
  4. It prints each due roll-up document that stays stale. Step 5 does not count SD641 and SD642 of these documents. `finish` exits 0.
  5. With `--dry-run`, the part prints `would re-pin` and `would hold`. The part runs also when a rule turns the group `rollup` or one of its codes off, because a re-pin is no finding (S8b).
- `next` prints the note of the due roll-up documents in each stage except `closed`. `status` prints no note. The note of `next` has at most 13 lines (S8b).
- Several pull requests. A change can merge its plan, then its code in 1 or more pull requests, then `finish`. An edit of a summary can merge in any of them. Step 2 compares with the tree before the plan, not with the base of the last pull request. Thus an edit of an earlier pull request counts, and the agent needs no `--holds` for it. SD645 uses the same compare (D52).
- After `finish`, `check` reports SD641 for each roll-up document that stays stale (an error in `standard` and `strict`, off in `lite`). The finding stays until an agent edits the summary and runs `refresh`, or runs `refresh --holds`. The fix is one more commit after `finish`.
- The approval modes. `base`: the merge covers the edits, the re-pins and the claims. `branch`: no approval commit for a summary; SD645 shows each claim. The acceptor does not see a claim of `finish --holds`. The tree of the record leaves Markdown out (D3), so a re-pin never makes the record stale.
- SD913 does not report a roll-up document (a summary, or a `system` or `product` document with `rests-on`), as it does not report a path of `shared-paths`. Thus `execute` does not stop and ask for a summary that is due, and a plan does not list `system` and `product` in advance.
- `mv` and a split: the preservation check does not count SD641 and SD642. `mv` prints the summaries whose frontier the move changed. A move of a whole document in one area changes no pin result, because the pin resolves through the alias and the hash stays. A move to another area makes the summary of each area stale. `mv` moves documents, not folders, and it writes no pin (S8b). A person moves an area folder with `git mv`, and the summaries with it. Then `check` names each stale pin (SD641) and each summary whose area folder is gone (SD644), and `refresh` writes the new pins. A move of a document that empties an area folder lists the summary of that area, and `check` gives SD644 for it.

**Formats**: `finish` text: `roll-up: re-pinned summaries/valves (the change edited its text)`, `roll-up: held summaries/sensors (--holds)` and `roll-up: stale summaries/valves (requirements/valves/closing#close-on-timeout changed); edit it and run spec-dna refresh summaries/valves, or run spec-dna refresh summaries/valves --holds`. `finish --json`: `"rollup":{"repinned":[...],"held":[...],"stale":[{"id","pins"}]}`. The new option `--holds <id>...` of `finish` (Q50).

**Codes**: no new code. **Config**: none.

**Upgrade**: with no roll-up document in the tree, the part does nothing, and `next` prints no note.

**Cost**: see "Cost per change" below.

**Does not prove**: that the edit before `finish` matches the requirement text after it. `finish` re-pins an edited summary, also if the edit was wrong.

Files and agents: `src/finish.rs` (`rollup()`, `--holds` and the exception in `no_new_errors`): `hygiene-engineer`. `src/main.rs` (the option `--holds` of `finish`): `core-engineer`. `src/lifecycle.rs` (SD913): `diagnostics-engineer`. `src/stage.rs` (the note of `next`): `core-engineer`. `src/split.rs`, `src/mv.rs` (the exception and the move of a summary): `hygiene-engineer`. `src/harness_text.rs` (`write-plan`, `execute`, `finish`): `init-engineer`. `docs/commands.md` (`finish`, `next`, `mv`), `docs/guides/change.md`.

Tests: `tests/finish.rs`: a delta that changes a requirement pinned by `summaries/valves`, with the summary and `system` edited in the branch: `finish` exits 0, the summary has the new pin, and `check` gives no SD641. The same with no edit and `--holds summaries/valves`: `finish` exits 0, the summary has the new pin, and `check` gives SD645 and no SD641. The same with no edit and no option: `finish` exits 0 and prints the summary as stale (before: step 5 stops with SD641), and `check` then gives SD641. `--holds` with an id that is not due exits 2. A flat project whose `system` pins the requirements: `finish --holds system` exits 0. A summary edited in a pull request that merged before the pull request of `finish`: `finish` re-pins it with no `--holds`, and `check` gives no SD645. `tests/lifecycle_commands.rs`: `next` prints the note with `summaries/valves`, and its items do not change. `tests/lifecycle_checks.rs`: a branch that edits `summaries/valves` outside `Files` gives no SD913. `tests/cli.rs` (`mv`): a move to another area exits 0 and names 2 summaries, and writes no pin. A move that empties an area folder lists its summary, and `check` gives SD644. `mv` of a folder exits 5, as in 0.7.1.

### D55. The budget of an area: SD705 to SD707

**Problem**: an area is a weak concept today: the first folder under the layer `requirements`, read only by `--group`. An area can grow with no limit, so its summary must condense more and more text.

**Mechanism**:

- An area is a folder of any depth under the folder of the layer `requirements`, and the folder itself is the root area. Its size is the sum of the body characters (the count of SD701) of the documents under it that are not inactive. For each sub-area that has a summary, the sum counts the summary in place of the documents of the sub-area. Thus a summary condenses a sub-area for each level above it.
- The rule against the base mirrors SD702 to SD704. SD706 is for a new excess, an area that was under the hard budget in the base, or growth above `[budgets] growth`. An excess of the base with growth up to that allowance gives SD707. The soft budget gives SD705.
- The fix: split the area into sub-areas with `spec-dna mv` and give each one a summary (`spec-dna new summary`), or condense its documents. A split area then counts its sub-summaries, so the levels grow with the corpus.
- The diagnostic is on the summary of the area, or on the folder when the area has no summary.

**Formats**:

```toml
[budgets.area]
soft = 60000    # SD705
hard = 120000   # SD706 (new or grown excess), SD707 (excess of the base)
```

**Codes** (the new rule group `area-budget`, so a rule for the group `budgets` of 0.7.1 does not change them):

| Code | Finding | lite | standard | strict |
| --- | --- | --- | --- | --- |
| SD705 | An area over its soft budget | off | warning | error |
| SD706 | An area over its hard budget: new, under it in the base, or grown by more than `growth` | off | error | error |
| SD707 | An area over its hard budget in the base, with growth up to `growth` | off | warning | error |

**Config**: `[budgets.area]` with `soft` and `hard`, in characters (the unit of each budget; a token count depends on the model). With no table, no area budget: the behavior of 0.7.1 (P5). `init` writes the table for each new project of `standard` and `strict` (Q29): `standard` 60,000 and 120,000; `strict` 40,000 and 80,000. The area budget is a mechanism of its own, not a part of the roll-up: the table is its key, and with no table it checks nothing. In `lite` it is off: `init` writes no table, and SD705 to SD707 are off (section 11). Reasons: 120,000 characters are about 30,000 tokens, an area that an agent can still read in one request. A summary of at most 6,000 characters condenses an area 10 to 20 times.

**Upgrade**: `upgrade` writes no table. The in-memory check of `upgrade` uses the planned tree as its base (D65), so an excess of the tree is SD707 there, as in `check --all`.

**Cost**: an agent that grows an area over its hard budget must split or condense in the same change. With summaries, one more summary for each split.

**Does not prove**: that a split follows the domain, or that a condensed document keeps its meaning. Characters are a proxy for the cost of a read.

Files and agents: `src/check.rs` (a function beside `hard_budget`), `src/config.rs` (the table, the profile rows, the group `area-budget` in `GROUPS`), `src/init.rs` (the table for `standard` and `strict`), `docs/config.md` ("Areas and groups", "Budgets", and the group in the row of `rules`), `docs/profiles.md`, `docs/diagnostics.md`: `diagnostics-engineer`, `core-engineer`, `init-engineer`.

Tests: `tests/layers_checks.rs`: an area of 3 documents over `hard = 100` gives SD706 when it is new and SD707 when the base had it; a sub-area with a summary counts the summary only; with no table, no code. `tests/init_profiles.rs`: the tables of `standard` and `strict`, and no table in `lite`. `tests/upgrade_cli.rs` (slice S8b): the equality test of D65 with an area over `[budgets.area] hard = 300`.

### D56. `context`: the tier `summary`

**Problem**: `context <file>` serves the requirement sections of the file and a top file only for its `applies-to`. An agent never gets the short text of the area and of the system first.

**Mechanism**:

- A new tier `summary`, after `convention` and before `rule`. Its documents are the chain of the request: the summary of each area that the planned documents reach, its ancestor summaries, and each `system` and `product` document with `rests-on` above them.
- The order is top down: `product`, `system`, then the summaries from the shallow folder to the deep one. For each document, its title section first, then the other sections in heading order.
- The full text of the tier uses at most a quarter of the budget (2,000 of 8,000 characters by default). A section that does not fit is a stub (id, hash, size), as in the other tiers. The other tiers keep the rest of the budget.
- A document in this tier is in no other tier. A stale document (SD641 or SD642) gets the word `stale` after the tier in its header line and `"stale": true` in `--json`. Thus an agent does not trust the document. A stale stub ends with `[stale]`, and its unit of `--json` has `"stale": true` (S8b).
- The cap of the tier is a quarter of the budget, measured on the full cost of each section. A layer `summaries` with `context = "on-request"` counts in the chain, and `context` serves none of its documents (S8b).
- With no roll-up document, the tier is empty, and the output is the same as in 0.7.1.

**Formats**: the header of a section of the tier keeps the form of 0.7.1 (`<!-- <section id> h:<hash> <type> <tier> -->`), for example `<!-- summaries/valves h:5d0e7c2a91b3f4e8 summary summary stale -->`. The tier name `summary` is a new value of the field `tier` of `--json`.

**Codes**: none. **Config**: none (the share is a constant of the tier).

**Upgrade**: a tree with no roll-up document gives the output of 0.7.1. The golden files of `context` do not change.

**Cost**: at most 2,000 characters (about 500 tokens) of each `context` call goes to the summaries, and the other tiers lose the same amount.

**Does not prove**: that the summary is true. A stale marker shows only a known break.

Files and agents: `src/context.rs`, the `context` section of `docs/commands.md`, `bench/results/retrieval-*.json` (a new run with a synthetic corpus that has summaries): `context-engineer`.

Tests: `tests/context_layers.rs`: a corpus with `system` and `summaries/valves`: the first sections are `system`, then `summaries/valves`, then the rule tier; a stale summary has the word `stale` in its header; a corpus with no summary gives the old output byte for byte.

### 6.1 Cost per change and the cascade

A typical change edits 1 to 3 requirements of one area at depth 1.

| Step | Documents | Who, and when |
| --- | --- | --- |
| The area summary, if its meaning changes | 1 rewrite. `finish` re-pins it | Agent, in the build |
| The area summary, if its meaning holds | No rewrite: its id in `finish --holds` | Agent, at `finish` |
| The level above (`system`) | Stale as soon as the text of the summary changes: usually 1 `refresh --holds`, seldom 1 paragraph and `refresh` | Agent, in the build |
| `product` | Stale only if `system` changed its text: usually none | Agent, in the build |
| A due roll-up document that the agent forgot | SD641 after `finish`: 1 edit and `refresh`, or `refresh --holds`, in one more commit | Agent, after `finish` |

Thus a typical change has 1 rewrite of at most 6,000 characters and 1 or 2 commands, all before or at `finish`. The agent reads the summary, the changed requirements and the text of `system`: up to about 6,000 tokens. The number is an estimate, not a measurement. A change in an area at depth `d` can make up to `d + 2` documents due. 4 rules keep the cascade small:

1. A pin is in the front matter, so a refresh never changes the hash that the level above pins.
2. `--holds` stops the cascade at a level whose text did not change.
3. The hash of a document drops link destinations, so a move that rewrites links does not cascade.
4. The area budget keeps the tree of areas balanced, so the depth grows with the log of the corpus.

### 6.2 Limits

- The gate cannot check the meaning of a summary. A wrong summary with current pins passes. `--holds` can be false.
- A summary covers only the layer `requirements`. Rules, interfaces and decisions have no roll-up in 0.8.0. A pin to a decision or a research document gives SD643.
- This repository has no layer `requirements`: its documents are decisions and research pages. Thus it has no roll-up source, and it writes no summary in 0.8.0. The tests of D50 to D56 and their fixture corpus prove the mechanism.
- An area is a folder. A project that sorts its requirements in another way gets one root area.
- SD645 needs a base. A repository with no base gets no finding for a claim.
- The guard compares with the base. After one edit of a summary in a branch, each later refresh of that summary in that branch passes. The same holds after a new change of a requirement.
- A summary that `finish` re-pins can still be wrong: `finish` sees only that its text changed in the branch.

### D57. Harness arms in the runner

**Problem**: `eval run --ab` has only the arms `with` and `without` of a skill. The copy takes `CLAUDE.md`, `AGENTS.md`, `REVIEW.md` and `.claude/*` from the project that runs the command, so each past run had the team of the host. The result files do not record the team. The `claude` command has no `--model`.

**Mechanism**:

- A harness arm is a built-in name: `none`, `lean`, `lean-no-advisor`, `full`, and `project` (the files of the project that runs the command, as today). The runner writes a `[harness]` table into the `spec-dna.toml` of the copy and runs the generator of `init` on the copy. It copies no `.claude/*`, no generated line and no `REVIEW.md` from the project, except for `project`.
- Each built-in arm has `skills = []`, `review-md = false` and `protect-tests = "off"`. Thus the arms differ only in the level and the roles. `lean-no-advisor` is `lean` with `advisor = { claude-code = "none" }`: no `advisorModel`, no `fallback-advisor.md`, no advisor sentence in the line. That is the only difference from `lean`.
- All arms get the adapter line of the binary (as `--ab` does since 0.7.1), so the arms do not differ in the spec-dna line.
- The main model: the runner passes `--model` and `--effort` with the orchestrator values of `lean` (`opus`, `xhigh`) in each arm (Q20). Thus arm `none` has the same main model, and the comparison measures the team, not the main model.
- `eval run --arms <arm>,<arm>[,<arm>] [<id>...]`: 2 or 3 arms on the plain evals of `<dir>`. Waves: wave `r` runs each eval once in each arm. Inside one eval, the arm order rotates by `(eval index + r) mod arms`. A stop by the cap keeps complete waves, and the analysis drops a partial wave.
- `--harness <arm>` with a plain `eval run`: the copy gets that arm, as above. With `--ab`, the copy gets the team of the arm and the skills that `init` proposes for the profile `standard` at that level (the default skills of ADR 0023). Then the edit of `--ab` adds or removes the measured skill. Some skills have a role with an agent file at that level, for example the skill `accept` and the agent `acceptor` of D3. In the arm `without`, such a skill also loses the agent file and the sentence of the role in the line of `CLAUDE.md`. Thus a skill runs beside the other default skills, as for a user.
- The reruns of D66 use `--harness lean`, so a release batch records its team. A rerun row is a new condition, not the condition of the current row of `RELEASE` (the host files of 0.7.x are not known). The newest batch decides (ADR 0021), and the release notes name the change.
- `--arms` and `--harness` isolate by default (`--setting-sources project`), so the advisor of the user settings cannot reach an arm. `--no-isolate` with them is a usage error.
- The result file: `arms-<stamp>.json`, with one side per arm for each eval and run. `--resume` works as for `--ab`. The records have `skill` = `harness` (D58). The test of `RELEASE` skips that name, so a batch of `--arms` never enters the table of the skills.

**Formats**: `spec-dna eval run --arms none,lean-no-advisor,lean team-01 team-02 --runs 5 --max-total-usd 327`.

**Codes**: none. Exit codes keep the meanings of `eval run` in `docs/commands.md`: 2 for an unknown arm, 1 arm or more than 3 with `--arms`, `--arms` with `--ab`, and `--no-isolate` with `--arms` or `--harness`; 3 for the configuration, an invalid eval, and a stop by the cap; 4 for a git or file error of the copy. 1 keeps its meaning for a plain run with `--harness` (the pass rate is below `min-pass-rate`); a run of `--arms` gives no pass rate, so it never exits 1. No new meaning. Row 2 of the table in `docs/commands.md` gets the usage errors above, next to the unknown id of `eval run`.

**Config**: none. The arms are names, not keys.

**Upgrade**: `--ab` without `--harness` keeps the copy of 0.7.1.

**Cost**: no cost to a user per change. The slice adds no dependency.

**Does not prove**: that an arm used its roles. The models of each run show only which models answered (D61 checks the advisor).

Files and agents: `src/eval_run.rs`, `src/eval_ab.rs` (the `Arm` enum, the `edit` closure of `one_attempt`, the rotation), `src/harness.rs` (a function that writes a harness into a folder, shared with `init`), `src/main.rs`, `docs/evals.md`, `docs/commands.md` (`eval`): `core-engineer`, `init-engineer` (`harness.rs`).

Tests: `tests/eval_ab.rs` with a stub `claude` that lists the copy: arm `none` has no `.claude/`; `lean-no-advisor` has no `advisorModel` and no `fallback-advisor.md`; `lean` has both; no file of the host `.claude/` is in any arm; the argv has `--model opus --effort xhigh`; the order of 2 waves of 2 evals follows the rotation; a cap stop after 1.5 waves keeps wave 1 only in the analysis.

### D58. Time, turns and the team in each record

**Problem**: no run records its time. A plain `eval run` records no tokens and no models. A record has 9 keys and no team, so a release table cannot be repeated with the same team.

**Mechanism**:

- Each run gets `seconds` (the wall time of the agent process, measured by the runner, 1 decimal) and `turns` (`num_turns` of the result of `claude`, or `null`).
- A plain `eval run` result gets `tokens`, `models`, `turns` and `seconds` for each run. These are additive fields.
- A record gets 3 keys after the 9 keys, in this order: `harness`, `turns`, `seconds`. `harness` is the arm of the copy: `project` or a built-in name. For a batch of `--arms`, `skill` is `harness` and `arm` is the arm name. A record of 9 keys stays valid and reads as `project`, `null`, `null`.
- "No time" in ADR 0021 means no clock time and no date. A duration is allowed.

**Formats**: `{"skill":"harness","eval":"team-03","run":2,"arm":"lean","pass":true,"cost":2.104,"tokens":{...},"models":[...],"claude_code":"2.1.330","harness":"lean","turns":31,"seconds":412.6}`.

**Codes**: none. **Config**: none.

**Upgrade**: the committed records of 0.7.x keep 9 keys. The test of `RELEASE` reads both forms.

**Cost**: none to a user.

**Does not prove**: that a run was efficient. Time depends on the API load.

Files and agents: `src/eval_run.rs`, `src/eval_ab.rs`, `src/eval_records.rs`, `docs/evals.md`: `core-engineer`. Amendment of ADR 0021 by ADR 0030.

Tests: `tests/eval_run.rs`: a stub `claude` with `num_turns` 7 gives `"turns":7` and a `seconds` above 0 in a plain run. `tests/eval_records.rs`: a result of 0.8.0 gives 12 keys; a 9-key record of `tests/fixtures/eval-records/` still imports; a negative `seconds` stops the import.

### D59. The floor of a verdict, and `--compare`

**Problem**: `decide` has no minimum sample. One pair that passes with the skill and fails without it gives `on`. A lab simulation (below) gives `on` in 22% of trials for 1 pair with no true gain.

**Mechanism**:

- The floor: at least 5 evals and at least 15 complete pairs. Below it, the verdict is `inconclusive`, with `"below_floor": true` in the item and the text `below the floor (<n> pairs of <k> evals; the floor is 15 pairs of 5 evals)`.
- Each row of `RELEASE` has 15 pairs or more over 5 evals, so the table does not change (checked on 2026-11-19).
- `eval verdict --compare <treatment>,<control> <result file>` gives the verdict of 2 arms of a result of `--arms`, with the same bootstrap and rules. ADR 0029 adds its own rules for the model team.
- The simulation of the floor is a test with `#[ignore]` on the real bootstrap of `src/verdict.rs`, as the simulation test of 0.7.0.

Lab estimates (numpy copy of the bootstrap, 600 trials each, pass rates drawn from 0.2 to 0.8 per eval, independent arms; the `#[ignore]` test repeats them):

| Evals x runs | Pairs | `on` with no true gain | `on` with a true gain of 0.20 |
| --- | --- | --- | --- |
| 1 x 1 | 1 | 0.22 | 0.32 |
| 1 x 3 | 3 | 0.09 | 0.22 |
| 3 x 3 | 9 | 0.04 | 0.14 |
| 5 x 3 | 15 | 0.03 | 0.21 |
| 10 x 3 | 30 | 0.03 | 0.42 |

The row of 1 pair is exact for the stated model: the control rate b is uniform from 0.2 to 0.8, and one pair is `on` only when the arm with the skill passes and the other fails, so the share is E[b(1 - b)] = 0.22 with no gain and E[(b + 0.2)(1 - b)] = 0.32 with a gain of 0.20. The first lab table had 0.29 and 0.44, which this model cannot give.

**Formats**: `"below_floor"` in each item of a result of `--ab` and `--compare`, and in `eval verdict --json`. Exit codes of `--compare`, as `eval verdict` and `eval records`: 0 done; 2 usage (not 2 arms, or an arm that the file does not have); 3 a file that is not a result of `--arms`, or a bad configuration. Rows 2 and 3 of the table in `docs/commands.md` get these cases of `eval verdict`.

**Codes**: SD507 reads the verdict, so a project result below the floor no longer turns a skill on. No new code.

**Config**: none. The floor is a constant of the release (Q39).

**Upgrade**: a project result file of 0.7.1 below the floor reads as `inconclusive`. The CHANGELOG names it.

**Cost**: none.

**Does not prove**: that a verdict above the floor is right. The floor removes only the smallest samples.

Files and agents: `src/verdict.rs`, `src/main.rs` (`--compare`), `docs/evals.md` ("The verdict"): `core-engineer`. Amendment of ADR 0016 by ADR 0030.

Tests: unit tests of `decide`: 9 pairs of 3 evals, all with a gain, give `inconclusive` and `below_floor`; 15 pairs of 5 evals with the data of the `tdd` row give `on`. The test that compares `RELEASE` with the records passes with no edit.

### D61. The protocol of the model-team measurement (ADR 0029)

**Problem**: the owner has 400 USD to decide an advisor gate for 0.8.1. The owner asks whether the generated team helps (no harness against `lean`) and whether the advisor helps (`lean` with and without it). Past runs cannot answer: nearly all of them list the advisor model (755 of 770 records), and the host team is not recorded.

**Mechanism**, written before any run:

- Arms: A = `none`, B = `lean-no-advisor`, C = `lean` (the default of `init`). Same main model and effort in each arm (D57). Two comparisons get a verdict by one rule. C against B tests the advisor and decides the gate. C against A is the first question of the owner: `lean` as `init` writes it, against no harness. B against A only splits the effect of C against A between the team and the advisor: a description, with no verdict.
- Tasks: 12 candidates, 10 in the batch. Each task is a small synthetic project in Python with `unittest` (no consumer code). It has a task text, visible tests, a hidden oracle, a reference solution and a wrong solution. Each candidate has one place where a first idea fails:

| Id | Kind | The trap |
| --- | --- | --- |
| `team-01` | Rule in the docs | A retry of a payment call must send the same key (a rule of `docs/rules/`). A plain retry charges 2 times |
| `team-02` | Wrong first idea | The trace points at a formatter; the cause is a cache that keeps an old value |
| `team-03` | Spec conflict | The request says "round half up". The rule says "round half to even" for money. The rule wins, and the conflict goes into `QUESTIONS.md` |
| `team-04` | Trap | The orders of a day in a time zone, across a change of the clock |
| `team-05` | Trap | A slug must be unique for 2 forms of the same accented name (NFC and NFD) |
| `team-06` | Trap | Cursor pages repeat or lose the last item of a page |
| `team-07` | Trap (security) | A file server accepts `..`, an absolute path and a link out of its folder |
| `team-08` | Wrong first idea | A new column is not null, and old rows have no value. The migration must fill them first |
| `team-09` | Regression | A module split must keep 3 edge results that no visible test covers |
| `team-10` | Spec conflict | The docs give the order flag, then variable, then file; the first idea reads the variable first |
| `team-11` | Trap | CSV fields with quotes and line breaks |
| `team-12` | Wrong first idea | A cache key leaves out one parameter, so a second call gets an old result |

- Selection rules: each task has a wrong solution that passes the visible tests and fails the oracle. The task text never states the trap. A second opinion can matter (a trap, a wrong first idea or a spec conflict). The batch has at least 3 kinds. No task is one that a past pack eval already measures.
- The oracle: deterministic checks only, no grep of the prose of the agent. The checks of an eval are `tests_unchanged` (the visible tests stay), the visible tests, and `hidden <id>`. The hidden tests sit in `<dir>/oracle/<id>/` of the project that runs the batch, outside the fixture. The runner never copies them into the copy. After `claude` exits, the check function copies them into the copy and runs them.
- The agent gets no path of the project: `SPEC_DNA_CHECK_SH` is only in the environment of a check. The batch uses a binary that is outside the project folder, so `PATH` names no folder of the project.
- The source files are in `bench/team/` of this repository. They are public, so a later model can know them: a limit.
- Metrics, for each arm: the pass rate with its 90% interval, the cost and the cost per correct outcome, the tokens, the turns, the median seconds, and the share of runs whose `models` list the advisor model.
- Pilot, which does not count in the verdict:
  1. Free: the oracle self-test of the 12 candidates, and the runner tests with a stub `claude`.
  2. Manipulation, about 18 USD: 3 candidates x 1 run x arms A, B and C. Pass: each run of the 3 arms lists the main model of `lean` (so `--model` took effect in arm A). No run of A or B lists the advisor model. At least 2 of 3 runs of C list that model. If a condition fails, stop, fix the arms, and run this step again. `claude --help` of Claude Code 2.1.328 lists `--model` and `--effort` (checked on 2026-11-19); no run has tested them in the copy yet.
  3. Headroom, about 45 USD: the 12 candidates x 2 runs in arm B (`eval run --harness lean-no-advisor`). Keep 10: first the tasks with 1 of 2 passes, then 0 of 2, then 2 of 2, each group in the order of the ids. A task with a `claude` error in both runs is a broken fixture: drop it. If fewer than 10 candidates remain, stop and ask the owner before the main batch. The options are a fix of the broken fixtures (and step 3 again for them only), or a batch of fewer tasks under a new floor that the owner states. No task drops in silence below the floor of 10 tasks.
- Fallback rules, from the projected cost of all 3 arms: `M` = 400 USD minus the spend of the pilot minus 10 USD. The cost of one wave is `W` = 10 x (`a` + `b` + `c`). Here `b` is the mean cost of a B run in step 3. The values `a` and `c` are `b` times the ratios of A to B and of C to B in step 2.
- If 5 x `W` <= `M`: 5 runs. If not, stop and ask the owner, who asked for 5 runs. The options are 4 runs (120 runs; the floor needs 3), or more money. The pilot costs about 63 USD (18 + 45), with a cap of 65 USD.
- Main batch: `eval run --arms none,lean-no-advisor,lean <10 ids> --runs 5`, 150 runs, `max-budget-usd` 4.0 for each run (a tight cap scores cost, not work), `--max-total-usd` = 400 minus the spend of the pilot minus 10 (327 USD at the estimate of the pilot). API refusals follow the back-off of `--ab` and do not count.
- The floor of this protocol: 10 tasks and 3 complete waves (30 pairs for each comparison). Below it: no verdict.
- The verdict of a comparison X against Y (X is the treatment): the bootstrap of D33 by task, seed 24, 2,000 resamples, 90% interval, complete waves only.
  - `better`: rule 1 or rule 2 of D33.
  - `worse`: the high end of the interval of the difference is below 0.
  - `no-gain-at-cost`: not `better`, not `worse`, the high end of the difference is below 0.20, and the low end of the ratio of the costs per correct outcome is above 1.00.
  - `inconclusive`: else. An undefined ratio (an arm with no pass in a resample) gives `inconclusive` in place of `no-gain-at-cost`.
- `eval verdict --compare` prints the D33 verdict and both intervals. A person reads the 4 results of this protocol from these numbers. The binary holds no rule of this protocol.
- The decision table for 0.8.1 (C against B):

| Result | 0.8.1 |
| --- | --- |
| `better` | Gate in: 0.8.1 designs an advisor gate |
| `no-gain-at-cost` | Gate out: no gate. The owner decides if `lean` keeps the advisor (Q21) |
| `worse` | Gate out. The owner decides if `lean` drops the advisor (Q21) |
| `inconclusive` | Stay: no gate, the advisor stays a default role as in 0.7.1 |
| Below the floor | No result: stay. The owner decides if more money goes to the waves that did not run |

- C against A: `better` goes into `docs/evidence.md` as evidence for the default `lean`. `worse` or `no-gain-at-cost` is a question for the owner. `inconclusive` changes nothing.
- The outcome rule: the main batch decides alone. No top-up of waves after the result, because a look at the data and more runs make a false `better` more likely. A later run is a new batch with its own pre-registration. The records go to `bench/results/evals/<stamp>-harness.jsonl`.
- The power, as lab estimates (numpy copy of the bootstrap, 400 trials, 10 tasks x 5 runs, pass rates of B from 0.2 to 0.8, independent arms): a true gain of 0.20 gives `better` in about 0.48 of trials. A true gain of 0.30 gives `better` in about 0.85. No gain gives a false `better` in at most 0.03. With no gain and a cost 1.25 times higher, `no-gain-at-cost` occurs in about 0.14 of trials. Thus a small effect most likely gives `inconclusive`, and the table then says "stay". The `#[ignore]` test of D59 repeats these numbers on the real code.

**Formats**: an eval of the batch is a plain eval: `{"id":"team-03","task":"...","fixture":"evals/fixtures/team-03","max-turns":40,"max-budget-usd":4,"checks":[{"name":"tests-unchanged","run":"tests_unchanged"},{"name":"visible","run":"python3 -m unittest -q"},{"name":"hidden","run":"hidden team-03"}]}`. `hidden` is a function of `check.sh` of the batch project.

**Codes**: none. **Config**: `--max-total-usd` on the command, as above.

**Upgrade**: none.

**Cost**: 400 USD at most for the owner, none for a user.

**Does not prove**: that the advisor helps on other tasks, another model or a long session. 10 synthetic tasks of one size show only a large effect. A result is valid for the model and the Claude Code version of the records. The advisor sees one session of at most 40 turns; its value in a long session is not measured.

### D63. The release check

**Problem**: on the day of 0.7.1, `gh attestation verify` printed nothing, and the check said "ok". Cause (proved): gh 2.101.0 prints nothing on success when stdout is not a terminal. The command ended with `; echo ok`, which dropped the exit code. No script or workflow step verifies the assets.

**Mechanism**:

- A script `scripts/verify-release.sh <tag> <dir>`, or `--download <tag>` to fetch the assets of the release into a temporary folder first. `set -euo pipefail`. Steps:
  1. The folder holds exactly the assets of the version: the binary of each target of `scripts/cross-build.sh --list --all` (7 today), `SHA256SUMS` and `spec-dna-pin.toml`. A file too many or too few: fail before `gh` runs.
  2. `SHA256SUMS` verifies each binary.
  3. For each asset: `gh attestation verify "$f" --repo "$repo" --signer-workflow "$repo/.github/workflows/release.yml" --source-ref "refs/tags/$tag" --deny-self-hosted-runners --format json --jq length`. The script keeps the exit code and stdout apart, never chains with `;` and never ends with `|| true`. It needs exit code 0 and an integer of at least 1. If a check fails, the script names the asset and the reason, checks the next asset, and fails at the end.
  4. It prints `verified <asset>: <n> attestation(s)` for each asset and `verify-release: 9 of 9 assets verified for <tag>`.
- `release.yml`: the step "Create the release" becomes 3 steps: create the draft; "Verify the attestations" (`scripts/verify-release.sh "$GITHUB_REF_NAME" dist`, with `GH_TOKEN` and `GH_REPO`); publish (`gh release edit --draft=false`). A failure keeps the draft, so nothing is published, and the owner deletes or fixes the draft. The job keeps its permissions (`attestations: write` includes the read).
- The checklist of `release-engineer` gets step 6: after the owner publishes, run `scripts/verify-release.sh --download v<version>` and give the whole output. If the output has no line `9 of 9`, or the exit code is not 0, the release failed.
- `docs/quickstart.md` and `docs/guides/upgrade-0.6.md` add one sentence: the command prints nothing when its output goes to a file or a pipe, so check its exit code (0 means verified).

**Formats**: exit codes 0 (each asset verified), 1 (a failure), 2 (usage). The script is not a command of the binary, so the table of `docs/commands.md` does not list it. Its codes keep the same meanings: 1 a refusal, 2 usage.

**Codes**: none (a script, not a diagnostic).

**Config**: none.

**Upgrade**: none for a user.

**Cost**: about 10 seconds in the release job, 9 calls to the API.

**Does not prove**: that the source of the tag is safe, or that the runner of the build was not changed. It proves that each asset has a provenance attestation of the release workflow of this repository for this tag, on a GitHub-hosted runner.

### From the review of the design

**Q40. What does a new `standard` or `strict` project get for `[evidence] reports`?** (a) `[]`, so item 1 is opt-in: a tag alone proves a requirement, as in 0.7.1, until the project sets a path. `init` writes the path when it detects a runner that writes JUnit XML. (b) In `strict`, an empty list is itself a finding (SD613). A `strict` project of 0.7.1 then fails after `upgrade` alone, so the rule must also use the pin of the plan (P5). Recommendation: (a). State that "covered means the test ran and passed" holds only where the key is set. **Decided** by the owner on 2026-11-19: (a). The design drops the detection of a runner, because `init` has no input to detect one: `init` writes `[]` with a comment in `standard` and `strict`.

**Q41. How does the mode `base` acknowledge the deviations of a change?** (a) The merge of the pull request: `finish` prints them and checks nothing more. (b) `finish` stops unless the command has `--ack-deviations <hash of the printed list>`. That forces a second run after a read, but an agent can type the hash. Recommendation: (a). The mode `base` already trusts the merge for each approval. Use `branch` where the acknowledgement must name a person. **Decided** by the owner on 2026-11-19: (a). The review part moved to 0.8.1 (answer 2).

**Q42. How does a `covers:` tag bind to a test case?** (a) By the rule of D1 item 6: `case:` when given, else the first word of the first code block after the tag that names a case. The block ends at the indent of its first line, or at a line with less indent than the tag. A case with a pytest-style `classname` binds only a tag of its file. It costs nothing for the tags of 0.7.1 above a test. A wrong bind is possible in 4 cases. First, an unrelated case that passes shares a word of the block. Second, a test is in a comment after the tag, so the block starts at the next test. Third, one case name is in 2 files, in a report with no `file` and no `classname` that names a file. Fourth, a test is on one line, with no deeper line. (b) Only `case:`: exact, but each old tag needs an edit before it proves anything. Recommendation: (a). Use the reports of 5 runners as the first fixtures of slice S2. Put the case name in each message of SD616 and SD617, so a reviewer can see the bind. **Decided** by the owner on 2026-11-19: (a).

**Q43. Does a plan that the branch adds always need an acceptance record?** (a) Yes. A branch cannot set the pin back for one commit to skip the record, and a rebase and a merge give the same result. The cost: a change that started on 0.7.1 and merges after the upgrade needs one acceptance run (1 to 2 USD). (b) No: the pin of the adding commit counts also inside the branch. An open change then costs nothing after the upgrade, but a commit that sets the pin back and restores it skips the record. Recommendation: (a). **Decided** by the owner on 2026-11-19: (a).

**Q44. What does the record bind when a change edits code outside the scope of its plan?** (a) Nothing: the record binds only the paths that `scope` matches, and SD913 already warns about code outside `Files`. The result does not depend on the number of open changes. (b) The whole diff: the bind is wider, but the result changes when another change finishes on the base. Recommendation: (a). **Decided** by the owner on 2026-11-19: (a).

**Q45. May a spec declare as an invariant a rule that the same change adds or removes?** (a) No: SD936 reports it on the spec before the approval, because such a rule cannot stay true across the change. A rule that the change edits with a `CHANGE` line is allowed, and SD937 compares the item with the hash of that line. (b) Yes, with a skip of the check for that item: the acceptor then answers for a rule that has no fixed text. Recommendation: (a). **Decided** by the owner on 2026-11-19: (a).

### D70 to D79. The acceptance in one pass

**Problem**:

The acceptance of part A is one more agent run for each change with a plan, after the review. Each code edit makes the record stale, and nothing limits the number of rejected records. Example: slice S4 of this repository had 8 runs, and each run said `rejected` (F24). A defect that the record lists as a `nit` cannot be fixed without a new run of 25 minutes (F25). The review and the acceptance are 2 passes of the same kind, and the independent check found defects that the acceptors did not find (F26).

**Mechanism**:

**D70. When a record is needed.**

1. A change that has a plan and is not closed needs a record when 3 conditions hold. The acceptance is on (SD927 is not off). The plan is new (D3 item 1 and P5, not changed). One of these is true:
    - `[change] acceptance-for` is `all`.
    - `[change] acceptance-for` is `higher-risk`, and the class of the change for the acceptance (item 2) is `higher-risk`.
    - A role of `[owners]` matches a role path of the change (item 7, D77). The key `[owners]` is the act of the project for that path. Thus a matched role needs a record also for a `routine` change, and also with `acceptance-for = "none"`.
2. The class of the change for the acceptance is `higher-risk` when one of these is true. Else it is `routine`.
    - The intent of the head has `class: higher-risk`, or its `class` is absent, empty or not valid (`class_unset`). This is the stricter result, as for a plan with no adding commit.
    - The intent in the tree of the lifecycle base has `class: higher-risk`.
    - A commit of the branch has the intent with `class: higher-risk`. The commits are the commits of D3 item 8: `git rev-list --first-parent <base>..<tip>`.
    - The minimum class of SD917 is `higher-risk`: a path of the diff or of `Files` matches `[change] high-risk-paths`, or the delta names a requirement of a layer of `high-risk-layers`.

    Thus a branch cannot lower or remove the class to skip the record. This is the shape of Q43: only a commit that is an ancestor of the base can lower the class, and a person merged it. When a shallow clone cuts the branch, the class is `higher-risk`, and SD927 names `fetch-depth: 0`.
3. One function, `acceptance::record_class`, gives this class. The need of item 1, the count of SD933 (`higher-risk-acceptors`), `next`, `finish` 5.2 and SD620 (`reliable-for`) call it. SD910 and SD917 keep the class of the head, as in 0.7.1.
4. Where the diff deletes the folder, the head has no intent. Then the newest intent of the change takes the place of the intent of the head in the first point of item 2: the intent at the last commit of the branch that has the folder, else the intent in the base tree. Thus an absent or invalid class there is `higher-risk` too, and `check` after `finish` reads the class that `finish` read. The function also reads the other 3 points of item 2: the base tree, the commits of the branch and SD917.
5. The rule of the plan (P5) does not change. ADR 0025 named it `base..HEAD`, but the code of part A reads the tree of the lifecycle base (F34). ADR 0032 corrects the ADR. A plan is new in 3 cases. The tree of the lifecycle base does not have the plan: a commit of the branch added it, or no commit did. The base has the plan, and no ancestor of the base added it (a shallow clone). The newest ancestor of the base that added the plan pinned 0.8.0 or later, or it has no pin.
6. The configuration of the need. A branch can edit `spec-dna.toml`, so the configuration of the head alone does not decide. Each value that the need reads is the stricter of the configuration of the head and the configuration in the tree of the lifecycle base. This is the shape of Q43 again:
    - The acceptance is on when SD927 is not off in the head or in the base (the key `profile` and `[rules]`).
    - `acceptance-for`: the stricter value (`all`, then `higher-risk`, then `none`), each with the default of its own profile.
    - `[owners]`, `high-risk-paths` and `high-risk-layers`: the union of the 2 configurations. `higher-risk-acceptors`: the larger value.

    A base tree with no `spec-dna.toml` (a pull request that adopts spec-dna) has nothing to lower, so the head decides. A base configuration that does not parse gives the strictest values: the acceptance on and `acceptance-for = "all"`. The commits between the base and the head add nothing, because they cannot lower the base. SD503 already refuses an edit of `spec-dna.toml` beside other files, so a lower value comes in a configuration change of its own. A lower value that a pull request merged into the base is the act of a person, and it counts: that stays a claim of the project, as each key is. One function, `acceptance::need_config`, gives these values to the need, `record_class`, SD933, `next` and `finish`.
7. The role paths of a change. A role of `[owners]` reads these code paths for the need, for SD933 and for the roles of the brief:
    - each code path of the diff that the `scope` of the change matches;
    - each code path of the diff that no `scope` of a change of the diff matches. A path that `Files` leaves out (SD913, a warning) thus still needs its role, for each change of the diff. This is the stricter result;
    - when the diff has no code path in `scope` (a pull request with only `finish`), the code paths in `scope` that changed since the commit that added the plan, the rule of D3 item 4.

    The record binds only `paths` (D3 item 4). A role path outside `scope` needs the role, but the record does not bind its content, so a later edit of that path makes no record stale. A path outside `scope` that an earlier pull request of the change edited needs no role in the pull request of `finish`. SD913 warned in that earlier pull request.

A note never gives `rejected`. An acceptor entry says `rejected` only when it has a blocker or the record has one of the other reasons.
    - The ids of the `[[deviation]]` entries are unique. The ids of the `[[invariant]]` entries are unique (D78).
    - Each `[[follow-up]]` follows the rules of D73.
    - In one life of the record, `rejected` never becomes `accepted` (D74 item 2).

**D73. The follow-up of a note.**

1. A fix of a note after the record needs no full run. It needs a follow-up: a short check of the fix by an agent that did not write the fix. The agent reads the diff of the fix against the requirements of the change, and it runs `Proof`. The follow-up binds the new tree.
2. `spec-dna accept <slug> --follow-up --brief` prints the follow-up brief. `spec-dna accept <slug> --follow-up [--session <id>]` adds a `[[follow-up]]` entry to the record, with `tree` computed, `closes` with each open note, and `pending` in each other field. The agent keeps in `closes` each note that the diff fixes, at least one, and removes the others. Both forms refuse (exit code 1) in these cases, and the message names a full run:
    - The record does not read, it has no open note, or it says `rejected`.
    - The diff of the fix (item 4) is empty, or it changes no `path` of an open note.
    - The diff of the chain has more than 16,384 bytes. It is the text of the diff over `paths` from the commit of the record to the head (item 8). The budget is for the whole chain, not for each link, so more notes do not buy more diff.
    - A path of the diff of the fix is a binary file (`git diff --numstat` prints `-`), because the budget measures text.
    - The diff of the change has a code path in `scope` that `paths` does not list, for example a new file. A follow-up binds the same `paths` as the record.
    - The edits that D3 item 5 refuses: the folder, `spec-dna.toml`, or a code path in `scope`, with an edit that `HEAD` does not have.
3. The chain. Its links are the record, then each follow-up in the order of the file. The tree of a link is the `tree` of the record or of the follow-up. The commit of a link is the adding commit of its entry, by the rule of D3 item 8. The identity of a follow-up is the pair of its `session` and `brief`. The commit of the record is the oldest adding commit of its `[[acceptor]]` entries. A link that the record of the base already has takes the commit of the lifecycle base, because its pull request compared it.
4. The diff of the fix of follow-up N is the set of paths of `paths` whose entry (mode and object id) differs between the tree of the commit of link N-1 and the tree of the commit of follow-up N. A follow-up that no commit has takes the index with `--staged`, else the working tree, as in D3 item 8.
5. What the tool compares, in SD928 where the diff adds or changes the record, and in `finish` 5.2:
    - `closes` names 1 or more findings of the severity `note`, no note 2 times in the chain, and the diff of the fix changes the `path` of 1 or more of them.
    - The tree of the commit of link N-1, over `paths`, has the hash `tree` of link N-1. Thus link N-1 bound the code of its own commit.
    - The tree of the commit of follow-up N, over `paths`, has the hash `tree` of follow-up N.
    - The diff of the chain up to follow-up N has at most 16,384 bytes, and no path of a diff of a fix is a binary file.
    - The `brief` of follow-up N is the follow-up brief that the tree of its commit gives.

    The tool does not limit the diff to the paths of the notes. A real fix of a note often changes another file and a test: the note of S5 on `src/acceptance.rs` has its fix in `src/record.rs` (D78 item 1). The agent reads the whole diff in the brief, and it sets `rejected` when the diff does more than fix the notes of `closes`. A fix of a Markdown file changes no tree, so it needs no follow-up, and its note stays open in the record.
6. What the tool compares in SD929: the record is fresh when the hash of `paths` now equals the `tree` of the last link. The other reasons of SD929 do not change.
7. SD932 (with `branch`, built in slice S6): a commit that adds a follow-up changes only the record, as each record commit. A follow-up commit that keeps an entry of `acknowledged-by` gives SD932, so the approver acknowledges the deviations again. The fix and the follow-up are 2 commits.
8. The follow-up brief. Its first line is `spec-dna-follow-up 2 <slug>`. Then comes a fixed text of about 800 bytes: read the whole diff against the requirements below, run each command of `Proof`, keep in `closes` each note that the diff fixes, set `result` to `rejected` when the diff changes other behavior or a command of `Proof` fails, write the commands and their results in `text`, and commit the record alone. Then come the delta lines of the spec, the items of `Invariants` and `Deviations`, the section `Proof` of the plan, the open notes (number, path, line and text), the 2 trees, the part `=== fix ===`, and the part `=== diff ===`. The last line is `brief <hash>`.
    - The part `=== fix ===` has one line `<path> <old mode> <old id> <new mode> <new id>` for each path of the diff of the fix: the input of the diff.
    - The part `=== diff ===` is the output of `git diff` with fixed options: `--no-ext-diff --no-textconv --no-color --no-renames --diff-algorithm=myers --indent-heuristic --inter-hunk-context=0 --src-prefix=a/ --dst-prefix=b/ -U3`, an empty order file (`-O`), and `-c core.quotePath=true -c diff.noprefix=false -c diff.mnemonicPrefix=false -c diff.relative=false`. `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` name an empty file. Thus the configuration of a user does not change the text.
    - The hash covers each line before the last line except the part `=== diff ===`. The part `=== fix ===` binds the same content, so another version of git, which can print another diff, gives no false SD928.
9. A follow-up with `result = "rejected"` makes the top `result` `rejected`. The record then counts for the stop rule (D74), and a full run follows.
10. `next` names the follow-up only when `accept --follow-up` does not refuse. Else it names a full run.

**D74. The stop rule.**

1. The count. The life of a record is an unbroken run of commits of the branch (the commits of D3 item 8) that hold `<folder>/acceptance.toml`. A commit with no such file ends the life, and the next record starts a new life. A life counts as one rejected record when the record says `rejected` at one or more of its commits. Thus the 2 entries of one round in `strict` count once, and an edit inside a life starts nothing new. A record that the tree of the base holds starts a life that counts once, also when the branch keeps it. The count reads the record at each commit of the branch in one batch, as the compare of the brief of D3 item 8 does, and the 2 share the read when both run.
2. No edit clears a rejection. In one life, a record that said `rejected` at an earlier commit cannot say `accepted` later. That record gives SD928, where the diff adds or changes the record and in `finish` 5.2: ``the record said `rejected` at <commit>; a later edit cannot accept it: fix the code, delete the record, commit, and accept again``. Thus a commit of the record alone that lowers a blocker to a note, or sets `accepted`, does not clear the rejection. D3 item 8 keeps the adding commit of an entry after an edit of its findings, and this rule closes that path.
3. The count survives the deletion of a record, because the commits keep it. CI reads it with `fetch-depth: 0`. When a shallow clone cuts the branch, SD941 names `fetch-depth: 0`, the stricter result.
4. The word of the owner is a new approval of the plan after the adding commit of the second rejected record. With `branch`, it is an approval commit of `plan.md` by an approver in the branch (ADR 0012). The flow of a change of an approved plan applies (step 8 of the skill `write-plan`): `status: draft` in one commit, then `spec-dna approve <slug> plan`. The walk of ADR 0012 gives that approval commit and its place also when the base tree has the plan `approved`. No code commit comes between the 2 commits, because SD910 needs an approved plan for code. After the approval commit, the count starts again at 0. The walk needs an author of `approvers`. With the hook `protect-approvals` (`[harness] protect-approvals = true`), rules A and B also deny an approval commit of an agent. Without the hook, the e-mail is the only condition, and an agent that commits with the e-mail of an approver meets it (ADR 0012, ADR 0018). Then the host (a protected branch, signed commits) is the control.
5. `next`. The count after the last approval of the plan can be 2 or more while the record of the head is not valid, fresh and accepted. Then the item `review` is an item of a person: ``wait for the owner: 2 acceptance records of <slug> say `rejected` (<commit>, <commit>); a third run needs the word of the owner``. With `branch`, the line adds ``: set `status: draft` in plan.md, then the approver runs `spec-dna approve <slug> plan` ``. The agent starts no third run.
6. The gate, SD941 (new, group `acceptance`). With `branch`, the record of the head comes after 2 rejected records, and no approval commit of the plan comes after the second. The code runs where the diff adds or changes a record, so the hook `check --staged` stops the commit of a third record. It also runs where the diff deletes the folder, and in `finish` 5.2.
7. With `base`, and so in `strict` (F11), no file of a branch holds a word of the owner that an agent cannot write. Then SD941 is not used, as SD932 and SD934. `next` stops the agent as in item 5. In each mode, `finish` prints `Acceptance runs: <n>, <r> rejected` when `n` is 2 or more. The skill `finish` puts the line into the commit message, as the line `Hours:`. The merge acknowledges the runs, as it acknowledges a deviation (Q41). Q52 asks the owner about this limit.
8. The limit is 2 rejected records, with no key. A later release can add a key when a project asks.

**D75. The friction of part A.**

1. The folder of the subagent. A subagent starts in the folder of the main session (F27). The brief cannot name the folder: the brief is a function of the repository, and a path differs on each machine. Thus `next` prints the prompt of the acceptor with the absolute root of the repository where `next` runs, as one shell word in single quotes (a `'` in the root becomes `'\''`): `cd '<root>' && spec-dna accept <slug> --brief`. The brief and the agent file tell the acceptor to start each shell call with that `cd '<root>' &&` and to stop when the `cd` fails. A call in another checkout reads that checkout. Another worktree of the repository often has the folder of the change, so `accept` can run there with no error. Its record then goes into that checkout, not into the folder of the builder. `next` of the builder keeps the item `review` open, and the builder sees that no record came. `isolation: worktree` is no fix, because its copy starts from the default branch (F27).
2. The agent type. The product writes `acceptor.md` with the skill `review` (D71 item 4), so the builder starts an agent of that name. This repository has its own agent team, and the main session used `general-purpose` in part A. `architect` adds the duty of the record to the team of this repository (an agent file in `.claude/agents/`), and the owner accepts it. That is no change of the product.
3. The brief with no paste. The prompt of the acceptor is the line of item 1, about 80 bytes. The acceptor runs the command and reads the brief as the output of its own call. The builder writes no word of the brief, and it pays no output tokens for it: part A pasted 7 to 9 KB (F29). The hash binds the input, as in D3. A `SubagentStart` hook was the other option. It is a feature of one agent host, it does not know the slug, and it puts a brief of more than 10,000 characters into a file (F29).
4. The commit of the record. The fixed text of the brief and the agent file `acceptor.md` say: "Commit `acceptance.toml` alone. This commit is part of your task. It is no approval commit: it changes no `status` line, and it needs no go-ahead of the owner." The skill `review` does not repeat it: each acceptor works from the brief, also at the harness level `none`, and the body of `review` is at its limit of 2,500 bytes. `APPROVAL_RULE` keeps its words. The hook `protect-approvals` allows the commit: it changes no `status` line (rule B), and a call with no word `accepted` before `git commit` passes rule C. This repository has its own approval rule in `AGENTS.md` (F32). `architect` adds the same sentence there, and the owner accepts it.
5. The writes of the acceptor. What enforces the limits, and where:
    - The hook `protect-approvals` exists only with `[harness] protect-approvals = true`, and `init` writes that key only in `strict` ([harness.md](../harness.md)). Without the key, no hook runs, and the text of the brief is the only rule.
    - With the hook, the new rule D runs for a `Bash` call whose input has `agent_type = "acceptor"` (F28): a subagent of that name, or a session that starts with `claude --agent acceptor`. The skill `review` tells the builder to start the second acceptor of `strict` in that way. A session that starts without `--agent` has no `agent_type`, and rule D does not run for it.
    - Rule D reads the text of the call before the call runs, and the index at that time. It reads a call that has the word `commit`, or the word `git` and a dynamic part outside single quotes (`$`, a backtick, `*`, `?`, `[` or `{`). The scan ignores case. It removes a backslash before a line feed, then each `'`, `"` and `\`. A word is a run of letters and digits, so a word counts also in quotes, in `bash -c`, in `eval` and in a here-document. Rule D does not read `git log`, `git diff -- src/a.py` or `git status`.
    - Such a call must match one form, else rule D denies it with a reason that names the form: `[cd <absolute path> &&] [git [-C <path>] add <record> &&] git [-C <path>] commit <options> [<record>]`. `<record>` is the literal path of one `acceptance.toml` of a change folder (the `--intent` folders), at most one time. The options of `commit` are `-m`, `--message`, `-s`, `--signoff`, `-n`, `--no-verify` and `--`. Only `&&` joins 2 parts.
    - Rule D denies outside quotes each of `;`, `|`, `&`, `(`, `)`, `{`, `}`, `<`, `>`, `$`, a backtick, `#`, `\`, `~`, `*`, `?`, `[`, `]` and a line feed, in each word, and in double quotes `$`, a backtick and `\`. It also denies a glob in the folder of `cd` or `-C`, also in quotes. Text in single quotes is plain text. The sequence `'\''` between 2 parts in single quotes is allowed, for a root with a `'`. Each other use of a backslash is denied. It denies each other command (for example `bash`, `eval`, `pushd`, `env`, `xargs`), each option of `git` other than `-C`, each verb other than `add` and `commit`, and more than one `add` or `commit`.
    - With no `<record>` after `commit`, rule D denies the call when the index already holds a path other than the record.
    - The scope. Rule D reads the repository of the `cwd` of the event or of `CLAUDE_PROJECT_DIR`, linked worktrees included. It denies a `cd` target that does not exist or is in no repository. A target in another repository that exists (for example a scratch repository of the acceptor) is allowed with the same form.
    - The change of behavior: a call that rule D reads and that does not have the form is denied, also a call that commits nothing. Examples for an acceptor: `git diff "$(git merge-base HEAD origin/HEAD)"`, `echo commit` and `grep commit docs`. The reason tells the acceptor to split the command, or to write the value in full.
    - What stays open: a command that the call builds only from variables or escapes, with neither the literal word `git` nor `commit`, is not read. Also open: a commit in a script file or through an alias, a hook of git, `git update-index` or another plumbing command in a call that rule D does not read, a commit of another tool, a commit in another repository, and each write of a file. Nothing in spec-dna limits the folder that a shell call or the tool `Write` writes to. A script can write into another checkout, as in run 6 of S4 (F30). The text of item 1, and the rule that each test repository goes under the scratch folder of the agent, lower the risk. They do not enforce the limit.
    - In CI, SD932 checks each record commit with `branch`, also with no hook. With `base`, nothing in CI checks that a record commit is alone.
    - A separate clone or a sandbox of the host can enforce the folder. 0.8.0 sets up neither: a clone costs one setup for each run, and the sandbox of the host binds the whole session. The [0.8.1 note](0.8.1-note.md) keeps the item.
6. An open task of the acceptance. Where the acceptance is on (SD927 is not off), a task whose text names `spec-dna accept <slug>` with the slug of its change closes with `finish`, as a task that names `spec-dna finish <slug>` (B1 of 0.7.1). In `lite`, the acceptance is off, so such a task stays an open task, and step 0 of `finish` stops on it, as in 0.7.1. `next` counts it as "for `finish`", so the stage does not stay at `build`. Step 0 of `finish` and `finish --dry-run` do not stop on it, and part 5.2 checks the record in its place. `finish` writes no tick, because it deletes the folder with the plan. "Where the acceptance is on" reads the floor of D70 item 6 (`need_config`), the value that the need reads. The skill `write-plan` of `standard` and `strict` says: "Write no task for the review or the acceptance: `next` names them." `lite` keeps the text of 0.7.1 (D76).
