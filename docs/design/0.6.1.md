# Design of spec-dna 0.6.1

Status: accepted, 2026-11-16. The owner's brief (the list of 16 items) is the acceptance. This page is a design only: it answers the feedback of the first 0.6.0 upgrade of a consumer repository, item by item, and gives the order of the work. The main session decided the owner questions, and the last section "Owner questions: answers" lists the answers.

The design adds no code. Each decision has a number (D1 to D64). A question that only the owner could answer has the mark OWNER QUESTION and a recommendation.

The repros ran the debug binary of the branch (0.6.0) on small repositories in a scratch folder. Q1 also used a copy of the source with the version 0.6.1. The repositories are:

- S: `init --non-interactive` in an empty repository with no remote. It has the small graph and `high-risk-layers = ["rules"]`.
- R: S with a bare remote and `origin/HEAD`, so the change commands have a base.
- F: a 0.5 project with `types = ["spec", "change", "decision", "note"]`, 2 changes in `docs/changes/` (one named `roadmap`), `docs/product-overview.md` and `docs/open-questions.md` (both `note`).
- H: `init` with the harness `full`, all skills, `REVIEW.md`, the evals and CI, then `new` for each type of the small graph.

## 1. `mv` to the path of its own alias

**Problem.** `mv` stops when the new id is an alias of the moved document itself. The person must delete the alias by hand first.

**Repro.** In S, `old/pumps` has `aliases: [requirements/pumps]`. `spec-dna mv old/pumps requirements/pumps` exits with code 2: `` `docs/requirements/pumps.md` (id `requirements/pumps`) already exists ``.

**Decision.**

- D1. `move_document` resolves the new id in the corpus. The move continues when the new id resolves to the moved document through its front matter `aliases`, and no file is at the new path. A file at the path, an id of another document and an ambiguous alias keep the stop and its text.
- D2. The move removes that entry from `aliases` (canonical comparison, as the lookup does). It removes the key when the list is empty. The old id becomes an alias, as before. The text output adds `(alias dropped: <alias>)`, and `--json` adds `"alias_dropped"`: the alias, or `null`.

**Files.** `src/mv.rs` and the `mv` output in `src/main.rs` (HYG); the `mv` section of `docs/commands.md`. Change sets: "Move, split or generated index" and "`--json` shape".

**Test.** `tests/cli.rs`, `mv_to_the_path_of_its_own_alias_drops_the_alias`: the move exits with code 0, `aliases` holds only the old id, and `check --all` exits with code 0. Before the fix, it exits with code 2.

## 2. `mv` into a top file or a layer folder

**Problem.** `mv` keeps the `type` and `status` lines. At a place that gives the type, `type` is redundant, or it contradicts the place. A status can be invalid for the type of the place. `new` writes neither line there.

**Repro.** In S, `mv old/glossary docs/terms.md` keeps `type: terms` and `status: active` (the type `terms` has no status). `mv old/pumps docs/requirements/pumps.md` keeps `type: requirements`. A move of `intent/roadmap-big/intent.md` to `docs/roadmap.md` keeps `status: draft` and `class: routine`. The front matter type still wins over the place. In R, `mv requirements/x notes/x` (no `type` line, a folder with no type) gives SD303 at the new place.

**Decision.**

- D3. After a move of a whole document in a mixed root, `mv` reads the type T that the new place gives (`Graph::place_type`, rules 2 to 4 of [Place gives the type](../types.md#place-gives-the-type)). If T exists, `mv` removes the `type` line. In a root of one type, nothing changes.
- D4. If T differs from the old type, the output names it: `type: intent -> roadmap (the place gives the type)`. OWNER QUESTION (decided, see the last section): may a move change the type of a document? Recommendation: yes, because the person chose the place.
- D5. If the document has requirements and T has none (`has_requirements` is false), `mv` stops with exit code 2 and changes nothing: `` `<path>` gives the type `<T>`, which holds no requirements; move the <n> requirements first with `spec-dna mv <id>#<key>... <to>` ``.
- D6. If T has no status, `mv` removes `status`. If the current status is a status of T (after `status-map`), it stays. Otherwise `mv` writes the first status of T (`templates::first_status`) and names it: `status: accepted -> draft`. The other fields stay.
- D7. This decision is an addition to the item. If the new place gives no type and the old type came from the old place, `mv` writes `type: <old type>`. It does not write the line when `default-type` of the new root is that type. Thus a move never changes a type with no line in the output.

**Files.** `src/mv.rs` (HYG). It reads `src/layer.rs` and `src/templates.rs` and changes neither. The `mv` section of `docs/commands.md`; one sentence in "Place gives the type" of `docs/types.md`. Change set: "Move, split or generated index".

**Test.** `tests/cli.rs`, `mv_into_a_place_fits_the_type_and_the_status`. The cases are:

- `terms` to `docs/terms.md` has no `type` and no `status`.
- `requirements` into `requirements/` keeps `status: active` and has no `type`.
- An accepted intent to `roadmap.md` has neither line, and the output has `type: intent -> roadmap`.
- A requirements document to `roadmap.md` exits with code 2.
- `requirements/x.md` with no `type` line to a folder with no type gets `type: requirements`.

Before the fix, the first case keeps both lines.

## 3. `log` and a move out of the intent layer

**Problem.** A commit that moves `intent.md` out of the intent folder reads as a deletion, so `log` lists a closed change that did not close.

**Repro.** In S, `spec-dna mv docs/intent/roadmap-big/intent.md docs/roadmap.md`, then a commit. `log` prints `2026-11-16 closed roadmap-big routine add 0 change 0 remove 0 373a5af7416d Roadmap big`. The walk of `git log -M --diff-filter=D -- <intent glob>` cannot pair the 2 paths, because the new path is outside the pathspec.

**Decision.**

- D8. This decision replaces part of D30 of [design 0.6.0](0.6.0.md). A commit can move `<intent dir>/<slug>/intent.md` out of every intent folder and keep its id as an alias. Such a commit does not end a change, because the id still resolves. `log` gives no entry for it. `stats --sdlc` drops that life: it is not finished, closed or open.
- D9. The new `Git::moved_out(entries)` runs `git diff-tree -r -M --name-status -z <parent> <commit>` for each entry that the walk found, with no pathspec. For a merge commit of the first-parent walk, it uses the first parent. An entry is a move out only if both conditions are true:
    1. The deleted `intent.md` is the source of an `R` record.
    2. The front matter `aliases` of the destination, in the tree of the commit, holds the old id of the intent. `spec-dna mv` and `upgrade` write it. `finish` never does.
- D10. Condition 2 is necessary. In a scratch repository, git paired a deletion by `finish` with a research note of the same commit that copied the text of the intent (`R078`). A plain `git mv` writes no alias, so it still ends the change, as today. `log` (`walk_deleted`) and `stats` (`lives`) filter with `moved_out`. The help of `log` and its section in `docs/commands.md` say: "A move of `intent.md` out of the intent folder that keeps its id as an alias (`spec-dna mv`) does not end a change."

**Files.** `src/git.rs`, `src/sdlc.rs`, the help in `src/main.rs` (COR); the `log` and `stats` sections of `docs/commands.md`. Change sets: "Git access" and "Command, option, help text or exit code".

**Test.** `tests/lifecycle_log.rs`, new `a_move_out_by_spec_dna_mv_does_not_end_a_change`: after `spec-dna mv <dir>/<slug>/intent.md docs/roadmap.md` and a commit, `log --json` has 0 entries, and `stats --sdlc` has 0 finished and 0 closed. Before the fix, it has 1 closed entry. The current `a_move_out_of_the_intent_folder_reads_as_a_deletion` (a plain `git mv`) stays green. `tests/git_lifecycle.rs`, `moved_out_needs_a_rename_and_the_old_id_as_an_alias`, covers both conditions and the near copy of D10.

## 4. `layer add --types` and the `types` list

**Problem.** `layer add` writes the layer, but not its types into the top-level `types` list. The new type is then not a type of the project.

**Repro.** In S with a `types` list that lacks `research`, `layer add research --types research --moves-to decisions --linked-from decisions` exits with code 0. Then `new research r2` exits with code 2: ``type `research` is not a type of this project``, and `check` gives SD303 for a document in `docs/research/`.

**Decision.**

- D11. If the file has a top-level `types` key, `layer add` appends each type of `--types` that the list lacks (`config_text::set_value`, so each comment stays). The file gets one write. Without the key, nothing changes, because then all types are valid.
- D12. The output adds `` added the types `research` to `types` `` and then at most 3 lines that start with `next:`, one action each:
    1. `next: commit spec-dna.toml as a change of its own (SD503)`. This replaces the current last line.
    2. If `adapters::project_types` changes and `.claude/skills/spec-dna/SKILL.md` is in the tree: `next: run spec-dna init to update the agent skill, which lists the types of the project`.
    3. `next: run spec-dna new <first type> <id> to write the first document of the layer`.
- D13. `--json` adds `"types_added"` (a list) and `"next"` (the lines without the prefix `next:`).

**Files.** `layer_add` in `src/main.rs` (COR); the `layer add` section of `docs/commands.md`. Change sets: "Command, option, help text or exit code" and "`--json` shape".

**Test.** `tests/layer_cmd.rs`, `layer_add_appends_its_types_to_the_types_list_and_prints_the_next_steps`: the list holds `research`, the comments stay, `new research r` exits with code 0, and the output has `next: run spec-dna init`. Before the fix, `new` exits with code 2.

## 5. The types of a change policy

**Problem.** The intent layer holds `intent`, `spec` and `plan`. A `types` list with only `intent` blocks `new spec` and `new plan` when a policy starts.

**Repro.** In F, `upgrade --layout` writes `types = ["requirements", "intent", "decision", "research"]`. Then `init --reconfigure` with `change-policy = "three-class"` writes the policy with no warning, and `new spec x` exits with code 2: ``type `spec` is not a type of this project``.

**Decision.**

- D14. A `types` list that `upgrade` writes holds the 3 types of the intent layer together, or none of them. For a 0.5 source, `edit_types` maps `change` to `intent`, `spec` and `plan`.
- D15. For a 0.6 source, `upgrade` adds the absent types when `[change] policy` is not `none` and the `types` list lacks one of the 3. The report says so. With the policy `none`, no command writes a spec or a plan, so the list stays as the person wrote it. D15 and D34 are the only edits of a 0.6 file other than the pin. They change only `spec-dna.toml`, so the pull request of the pin can hold them (SD503).
- D16. `init --reconfigure`: if the answer to question 4 is not `none` and the kept `types` list lacks one of the 3, `init` prints `warning: the policy <p> needs the types intent, spec and plan; add <list> to types in spec-dna.toml`. It does not edit `types`, because no question asks for the key ([docs/init.md](../init.md#reconfigure)).

**Files.** `src/upgrade_config.rs` (COR), the 0.6 branch of `plan` in `src/upgrade.rs` (INI), `src/init.rs` (INI); the `upgrade` section of `docs/commands.md`, "Reconfigure" in `docs/init.md`, `docs/guides/upgrade-0.5.md`. Change set: "Upgrade plan".

**Test.** The unit test `the_key_types_gets_the_new_names_with_no_duplicate` in `src/upgrade_config.rs` changes. Before: `types = ["spec", "guide", "runbook", "change"]`. After: `types = ["requirements", "procedure", "intent", "spec", "plan"]`, with 5 types. The test needs no fixture. Add `upgrade_of_a_06_file_with_a_policy_adds_spec_and_plan_to_types` to `tests/upgrade_cli.rs`. Add `reconfigure_warns_when_types_lacks_a_type_of_the_policy` to `tests/init_change.rs`. Each test fails before the fix.

## 6. `init --reconfigure` and `high-risk-layers`

**Problem.** The reconfiguration keeps the value of the old graph. [docs/config.md](../config.md#keys) gives the default `["interfaces", "rules"]`, without the layers that the graph lacks.

**Repro.** In S (`high-risk-layers = ["rules"]`), `init --reconfigure` with `graph = "default"` keeps `["rules"]`. `init.rs` copies `cfg.high_risk_layers`, which is the effective value of the old graph.

**Decision.**

- D17. The reconfiguration keeps the current value only if it differs from the default of the current graph (`default_high_risk_layers(&cfg.layers)`). Otherwise it writes `DEFAULT_HIGH_RISK_LAYERS` without the names that the new graph does not have. A value that the file states and that equals the default of the old graph counts as the default.

**Files.** `src/init.rs` (INI); `default_high_risk_layers` becomes `pub(crate)` in `src/config.rs` (COR). One bullet in "Reconfigure" of `docs/init.md`. Change set: none (a fix of `init` behavior).

**Test.** `tests/init_change.rs`, `a_small_graph_reconfigured_to_the_default_graph_gets_both_high_risk_layers`: the result is `["interfaces", "rules"]`. A second case starts from `high-risk-layers = []` and keeps `[]`. Before the fix, the first case gives `["rules"]`.

## 7. Markdown lint of the generated files

**Problem.** Some generated files break the rules of `.markdownlint-cli2.yaml`. No golden file covers them, so the pre-commit hook of this repository never lints them.

**Repro.** In H, a small line checker in the scratch folder found these problems:

- `.claude/agents/Explore.md:18` and `.claude/agents/fallback-advisor.md:16` break MD032: a line `Answer:` and a list have no blank line between them.
- In `.claude/skills/spec-dna/SKILL.md`, the begin marker is directly above `# spec-dna` (MD022), and the end marker is directly below the list (MD032).

The real linter did not run on the skill, so the golden file of D20 must confirm those 2 problems. The other files of H, the templates of `new` and the `--stub` stub gave no problem.

**Decision.**

- D18. Add a blank line between `Answer:` (or `Answer in 200 words or fewer:`) and its list in `AGENT_DEFS` of `src/harness.rs`. Add a blank line after the begin marker and before the end marker of the skill block in `src/adapters.rs`.
- D19. Add a test helper `md_lint(text) -> Vec<(u32, &str)>` in `tests/common/` (TST). It skips the front matter and fenced code, and it reads an HTML comment line as text. It checks MD009, MD010, MD012, MD022, MD031, MD032, MD040, MD047 and MD058. The comment of the helper maps each rule to the configuration: `default: true` enables them, and the file disables only MD013 and MD041, so the helper does not check those 2. It does not check the rules that need a full parser (MD004, MD007, MD029, MD033, MD034). It adds no dependency.
- D20. Add the golden files `Explore.md`, `fallback-advisor.md`, `implementer.md`, `model-team.md` and `skills/spec-dna.md` to `tests/golden/harness/`. The harness tests compare them. The pre-commit hook then runs the real `markdownlint-cli2` on them.

**Files.** `src/harness.rs` and `src/adapters.rs` (INI); `tests/common/` (TST); the new `tests/generated_lint.rs` and `tests/golden/harness/` (INI). Change sets: "Harness role or generated file" and "Adapter or skill text".

**Test.** `tests/generated_lint.rs`, `every_generated_markdown_file_passes_the_lint`. The test runs `init` with the harness `none`, `lean` and `full`, all skills, `REVIEW.md` and both adapters. It runs `new` for each type and each embedded template, writes a `--stub` stub and writes an `index` file. Each problem fails the test with `path:line rule`. Before the fix, it fails at `.claude/agents/Explore.md:18 MD032`.

## 8. The files that SD503 counts

**Problem.** The row of SD503 in `docs/diagnostics.md` says "the adapters, the harness files" and gives no paths. A person cannot tell if a lint configuration counts.

**Repro.** This is a documentation gap. `config_not_alone` in `src/main.rs` compares paths with fixed lists. A lint configuration, such as `.markdownlint-cli2.yaml`, counts.

**Decision.**

- D21. The row keeps one sentence and links a new section "Files that SD503 counts". The section keeps the current facts of the row: `check` does not examine a new `spec-dna.toml`, and SD503 does not apply when the base pins a version before 0.6.0. It has 2 lists:
    1. No count: `spec-dna.toml`; `AGENTS.md`, `CLAUDE.md`, `.claude/skills/spec-dna/SKILL.md`; `.claude/settings.json`, `.claude/agents/model-team.md`, `REVIEW.md`; `.claude/agents/` `fallback-advisor.md`, `verifier.md`, `Explore.md`, `implementer.md`, `code-simplifier.md`, and the 0.5 files `checker.md` and `spec-writer.md`; `.claude/skills/spec-dna-<intent|spec|plan|review>/SKILL.md`; `.pre-commit-config.yaml`, `.husky/pre-commit`; with `[evals]` in the head configuration, `<dir>/check.sh`, `<dir>/example.json`, `<dir>/fixtures/example/notes.txt` and `.github/workflows/agent-evals.yml`; each path whose file name starts with `spec-dna`, such as `.github/workflows/spec-dna.yml`.
    2. Count: each other path that differs from the base. Examples are documents, code, lint configurations, `CODEOWNERS`, other workflows, a deleted file, both paths of a move (the diff has no rename detection), and, without `--base`, an untracked file that git does not ignore.
- D22. The section says that the rule reads paths only. The lists do not depend on the harness level. An edit by hand of a file of list 1 does not count.

**Files.** `docs/diagnostics.md` (DIA). No code changes.

**Test.** A unit test in `src/main.rs` (DIA), `the_sd503_section_names_each_path_that_does_not_count`. It reads the doc with `include_str!`. It asserts each path of `adapters::PATHS`, the agent and skill paths of `harness`, `init::HOOK_FILES` and `evals::skeleton_paths`. Before the fix, the doc does not name `.claude/agents/model-team.md`.

## 9. A routine change with no files

**Problem.** `finish` and `log` work for such a change. `next` and `status` do not: they stay at the stage build and ask for paths that the work does not have.

**Repro.** In R, a routine intent is `accepted`, and its plan is `approved` with the text "None: this change is research." in `Files` and 1 done task. `finish` exits with code 0, and `log` prints `finished research-x routine add 0 change 0 remove 0`. But `next` shows `[ ] add the paths of the work to Files in docs/intent/research-x/plan.md: it lists none`. With the item `- none`, it shows `the items of Files ... are not paths (the first is "none")`. A `none` plan and an edit of `README.md` gave no SD913, because no change of the diff has a scope.

**Decision.**

- D23. A plan states "no files" in a `Files` section. The section has one item only, a list item or a paragraph. The item starts with the word `none` in any case, such as `- none: research only`. `Change::no_files` reads it, and `files_not_paths` does not report it.
- D24. For a routine change with an approved "no files" plan, `next` and `status` show `[x] the plan lists no files: the change edits no file` instead of the step of the files. The stage passes build when each task of `Order` is done, or when `Order` has no task. Then the steps of test, verify, review and finish follow, as today.
- D25. A higher-risk change keeps the current message, because its spec has a delta.
- D26. Add the rule to "Files and paths" of `docs/types.md`. Add "Work with no files" to "A routine change" in `docs/guides/change.md`. In "A small fix", say that trivial work that keeps each requirement needs no intent with the policy `three-class`.

**Files.** `src/change.rs` and `src/stage.rs` (COR); `docs/types.md`, `docs/guides/change.md` and the stage table of `docs/commands.md`. Change set: "Command, option, help text or exit code" (the output of `next` and `status`).

**Test.** `tests/lifecycle_commands.rs`, `a_routine_plan_with_files_none_reaches_the_finish_step`: the output of `next` has `[x] the plan lists no files` and `run spec-dna finish <slug>`. Before the fix, the stage is build.

## 10. A dead link in the locked text of a decision

**Problem.** `check` gives no SD101 or SD102 for a link in locked text, because the author cannot edit it. After `finish`, nothing says that the link is dead or how to record it.

**Repro.** In R, an accepted decision links `../intent/pump-y/intent.md` in its first section, and `check` gives SD611. `finish pump-y` exits with code 0, because its step 0 skips locked text. After the commit, `check --all` gives 0 errors and 0 warnings. The `mv` half does not reproduce: `mv` rewrote the locked link (also for a move of one requirement) and kept the aliases, with no SD405.

**Decision.**

- D27. `check` keeps the quiet rule, and it records each quiet reference as a locked link: the path, the line and the target.
- D28. `check --all` prints one line for each locked link, after the diagnostics: `` <path>:<line>: info: the locked text links `<target>`, which no longer exists; add an amendment that points to <pointer> ``. If the target is in an intent folder, the pointer is ``the change `<slug>` (`spec-dna log` names its commit)``. Otherwise it is `the new place of the text, or the reason for its removal`. Without `--all`, `check` prints no such line.
- D29. OWNER QUESTION (decided, see the last section): a line that is not a diagnostic, or a new warning code? Recommendation: not a diagnostic. It has no code, no severity, no `[rules]` key and no effect on the exit code, because the author cannot fix the locked text. `check --json` always has the field `locked_links`: a list of `{path, line, target, pointer}`.
- D30. SD611 stays the warning before `finish`, and `finish` keeps its step 0. An absent anchor in locked text stays SD602, as today.

**Files.** `src/check.rs` and the output of `check` in `src/main.rs` (DIA); the `check` section of `docs/commands.md`; the SD611 text of `docs/diagnostics.md`; `tests/golden/check-all.json`. Change sets: "`--json` shape" and "Command, option, help text or exit code".

**Test.** `tests/lifecycle_finished.rs`, `check_all_names_a_dead_link_in_locked_text_after_finish`: `check --all` exits with code 0, its output has `` info: the locked text links `../intent/pump-y/intent.md` ``, and `--json` has the target in `locked_links`. Before the fix, the output has no such line.

## 11. Empty folders after `mv` and `upgrade`

**Problem.** `mv` and `upgrade` leave the folders that they empty. `finish` removes them already.

**Repro.** In S, after the moves of items 1 and 2, `docs/old/` stays empty, and after the move of item 3, `docs/intent/roadmap-big/` stays. In F, `docs/changes/` stays after `upgrade --layout`.

**Decision.**

- D31. After it moves a file, `mv` removes each empty parent folder of the old path with `std::fs::remove_dir`. It goes from the deepest folder to the highest folder. A folder with any file, including an ignored file, stays. It stops at the root folder of the document. With `--stub`, the stub keeps the folder.
- D32. `upgrade` does the same after its moves. `--dry-run` writes and removes nothing. The output does not list the folders, because git does not track them.

**Files.** `src/mv.rs` (HYG) and the write step of `src/upgrade.rs` (INI); the `mv` and `upgrade` sections of `docs/commands.md`. Change sets: "Move, split or generated index" and "Upgrade plan".

**Test.** `tests/cli.rs`, `mv_removes_the_folder_that_it_leaves_empty`: `docs/old` does not exist after the move, and the root folder stays. `tests/upgrade_cli.rs`, `upgrade_removes_the_folder_of_the_moved_changes`. Both fail before the fix.

## 12. Links to the `pending` layer

**Problem.** A requirement that names an open question, or a decision that names the roadmap, gets SD901.

**Repro.** In R (small graph), a requirement links `../questions.md` and a decision links `../roadmap.md`. `check --all` gives 2 SD901 warnings.

**Decision.**

- D33. In the default and the small graph, `pending` gets `linked-from = ["intent", "requirements", "decisions"]`. ADR 0005 names no edge, so it needs no amendment. [docs/config.md](../config.md#default-graph) changes its 2 tables.
- D34. A file with `[layers.pending]` keeps its value. For a 0.6 source, `upgrade` adds `requirements` and `decisions` (the layers that the graph has) only when `linked-from` of `pending` is exactly `["intent"]`, the value of `init` 0.6.0. The report says so. OWNER QUESTION (decided, see the last section): may `upgrade` edit a layer table? Recommendation: yes, with this exact match only.

**Files.** `PENDING` in `src/layer.rs` (COR); `docs/config.md`; `tests/golden/layer-list-*.{txt,json}`; the 0.6 repair in `src/upgrade_config.rs` (COR). Change set: "Config key" (a default value).

**Test.** `tests/layers_checks.rs` (DIA), `requirements_and_decisions_can_link_the_pending_layer`: no SD901 in the default graph and in the small graph. The golden files of `layer list` change. Before the fix, the test finds 2 SD901.

## 13. A repository with no remote

**Problem.** The change commands need `origin/HEAD` or `--base`. A local repository has neither, so `status` and `next` have no base, and `check` skips the checks of the diff.

**Repro.** In S, `status` prints `base none` and the note `no base for the change checks; pass --base <rev>, or run git remote set-head origin <branch>`. A local symbolic ref is a workaround with no code: after `git symbolic-ref refs/remotes/origin/HEAD refs/heads/main`, `status` shows the base. The ref is in one clone only.

**Decision.**

- D35. New key `[change] base`: the name of a local branch, such as `"main"`. The name is not empty. It has no space, no `..`, and none of `~ ^ : ? * [ \`. It does not start with `-` or `/`, and it does not end with `/` or `.lock`. A bad name gives exit code 3 with the key path.
- D36. The base order is `--base`, then `refs/remotes/origin/HEAD`, then `refs/heads/<base>`. This amends D32 of design 0.6.0: spec-dna never guesses a branch, and it reads only the branch that the file names.
- D37. If the branch does not exist, the base is unknown, and the note says ``no base for the change checks: no origin/HEAD, and the branch `<b>` of [change] base does not exist; pass --base <rev>``. It is not an error, because a CI clone often has no local branch. `NO_BASE_NOTE` adds `or set [change] base`.
- D38. `status`, `next`, `finish` and the change checks of `check` read the key. `finish` reads it for each policy. The help text says `(default: origin/HEAD, then [change] base)`. The review skill (`src/harness_text.rs`, line 77) adds: "or use the branch of `[change] base` in spec-dna.toml". `init` does not propose the key.
- D39. The new section "A repository with no remote" in `docs/guides/upgrade-0.5.md` gives these steps:
    1. Run `upgrade` on a branch and commit.
    2. Run `spec-dna check --base main`.
    3. Merge into `main`.
    4. Set `[change] base = "main"` in a commit of its own (SD503).

    The section also gives the symbolic ref for a binary of 0.6.0.

**Files.** `src/config.rs` and `schema/spec-dna.schema.json` (COR), `src/git.rs` (COR), `merge_base_of` in `src/lifecycle.rs` (DIA), help in `src/main.rs` (COR), `src/harness_text.rs` (INI); `docs/config.md`, `docs/commands.md`, `docs/guides/upgrade-0.5.md`, `tests/golden/harness/skills/spec-dna-review.md`. Change sets: "Config key", "Git access", "Command, option, help text or exit code" and "Harness role or generated file".

**Test.** `tests/lifecycle_base.rs` (DIA), `the_base_is_the_branch_of_the_config_when_there_is_no_origin_head`: no remote, `base = "main"`, a change on a feature branch, and `status` prints the short SHA of `main`. A second case with `base = "nope"` asserts the note. A third case shows that `origin/HEAD` wins. `tests/change_config.rs` (COR), `base_must_be_a_branch_name`. ## 14. `upgrade --layout` and the top files

**Problem.** A 0.5 roadmap, overview, glossary or question list stays a `research` document, or becomes an intent. The 0.6 layout has a top file for each of them.

**Repro.** In F, `upgrade --layout` moves `docs/changes/roadmap.md` (`type: change`) to `docs/intent/roadmap/intent.md`. It keeps `docs/product-overview.md` and `docs/open-questions.md` in place as `research`. On a 0.6.0 source, `upgrade --layout --dry-run` of the 0.6.1 copy plans no move of a document.

**Decision.**

- D40. With `--layout`, a document of a root that was mixed in 0.5 moves to the top file of the root. This happens when its file stem is in this list. The file stem is lowercase, and `_` is read as `-`. The list: `roadmap` to `roadmap.md`; `product-overview` or `overview` to `product.md`; `open-questions` or `questions` to `questions.md`; `glossary` or `terms` to `terms.md`; `architecture` or `system` to `system.md`.
- D41. A document qualifies only if all these conditions are true:
    1. Its 0.5 type is `note`, `reference` or a `change` that is not `done`.
    2. It has no requirement.
    3. It is directly in the root, or directly in `notes/`, `reference/` or the folder of the changes.

    A `change` named `roadmap` goes to `roadmap.md`, not to the intent folder.
- D42. If 2 files map to one top file of a root, or the top file exists, nothing moves, and the report gets one `kept` line with the paths. The upgrade does not stop.
- D43. `classify` gives `Facts.top_types`, so pass 2 adds the type to `types` (if the key exists) and the layer `foundation` or `pending` to the graph. The moved file gets no `type`, no `status` and no `was-type` (D3, D6). Item 3 of the proof expects the type of the top file for such a document (`Class.top`), and the old id stays an alias.
- D44. A 0.6 source gets no move to a top file: SD503 forbids a move of a document in the pull request of the pin. `docs/guides/upgrade-0.5.md` gives `spec-dna mv <id> <root>/roadmap.md` for a later pull request. Items 1, 2 and 11 make that move clean.

**Files.** `src/upgrade_docs.rs` and `src/upgrade_proof.rs` (HYG), `src/upgrade_config.rs` (COR), `src/upgrade.rs` (INI); a new overlay `tests/fixtures/upgrade/top-files/` of `v05/` (TST), written by hand: it has documents only, so `make.sh` records nothing for it; `docs/commands.md`, `docs/guides/upgrade-0.5.md`. Change set: "Upgrade plan".

**Test.** `tests/upgrade_cli.rs`, `layout_moves_a_roadmap_change_and_overview_notes_to_top_files`, with `Repo::from_fixture("v05", &["top-files"])`: `docs/roadmap.md` has the type `roadmap` and no `type` line, `docs/product.md` and `docs/questions.md` exist, each old id resolves, the proof is ok, and `check --all` gives no new error. Before the fix, the roadmap is at `docs/intent/roadmap/intent.md`.

## 15. `upgrade --layout --areas <file>`

**Problem.** A 0.5 project keeps its requirements in a flat folder. The 0.6 layout puts them in `requirements/<area>/`.

**Repro.** No repro is possible, because the option does not exist. `upgrade --help` lists `--dry-run`, `--layout` and `--pin-file`. In F, `docs/specs/pumps.md` stays in `docs/specs/`, and the plan writes no `areas`.

**Decision.**

- D45. `--areas <file>` needs `--layout`. Otherwise the exit code is 2. The file is outside the repository, as `--pin-file` is, because an untracked file makes the tree not clean. It is TOML with one table `[areas]`: each key is a document id of the 0.5 tree, and each value is an area, such as `"specs/pumps" = "pumps"`.
- D46. Each mapped document moves to `<root>/<dir of the requirements layer>/<area>/<slug>.md` in its own root, with its old id as an alias. The command stops and writes nothing in these cases: an unknown id; a document that is not `requirements` in 0.6; an area that is not one folder name (letters, digits, `-`, `_`); the current stops of `plan_moves`.
- D47. The plan adds each area to `areas`, sorted, and writes the key if it is absent.
- D48. A 0.6 source with `--areas` gives exit code 2 and this text: `` `--areas` moves documents of a 0.5 project; in a 0.6 project, run `spec-dna mv` in a pull request of its own ``. The guide gives a shell loop over a file of id and area pairs.

**Files.** The option and the help in `src/main.rs` (COR), `src/upgrade.rs` (INI), `src/upgrade_docs.rs` (HYG), `src/upgrade_config.rs` (COR); `docs/commands.md`, `docs/guides/upgrade-0.5.md`. Change sets: "Command, option, help text or exit code" and "Upgrade plan".

**Test.** `tests/upgrade_cli.rs`, `areas_moves_each_mapped_requirements_document_into_its_area`: the file is at `docs/requirements/pumps/pumps.md`, the alias `specs/pumps` resolves, and `areas = ["pumps"]`. Before the fix, the option gives exit code 2.

## 16. The benchmark in GitHub Actions

**Problem.** The tool benchmark runs only on the host of a person, so its numbers depend on that host and its load.

**Repro.** No workflow exists. In the scratch folder, a release build of 0.6.1, `gen.py --model spec-dna --size small` and `run.py --runs 3` ran in 2.4 s. It worked only after a change of the pin: `gen.py` writes `spec-dna = "0.1.0"`, and on that pin `check` exits with code 3, so `run.py` raises. With the pin of the binary, the result had 72 documents, `modes_agree: true` and `incremental_agrees_with_full: true`.

**Decision.**

- D49. Add the new file `.github/workflows/bench.yml`, with the name `Benchmark` and the trigger `workflow_dispatch` only. The inputs are `ref` (string, default `master`: the branch, tag or SHA to measure), `size` (choice `small`, `medium`, `large`; default `medium`) and `runs` (number, default 15). With `ref`, the copy of the file on `master` measures a branch that does not have the file.
- D50. Set `permissions: {}` at the workflow level. The job `bench` has `contents: read` only. It has `runs-on: ubuntu-24.04`, `timeout-minutes: 30`, `defaults.run.shell: bash`, and `concurrency` by workflow and `ref`, with no cancel.
- D51. The steps are:
    1. Check out with `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`, `ref: ${{ inputs.ref }}` and `persist-credentials: false`.
    2. Install Rust `1.99.1` and build with `cargo build --locked --release`, as `build.yml` does.
    3. Write the corpus with `python3 bench/gen/gen.py --model spec-dna --size "$SIZE" --out "$RUNNER_TEMP/corpus"`.
    4. Copy `spec-dna.toml` of the corpus to `$RUNNER_TEMP/spec-dna.toml` with the pin of `target/release/spec-dna --version`.
    5. Run `bench/tool/run.py` with `--context` set to the first entry of `tasks.json`, `--runs "$RUNS"`, `--work "$RUNNER_TEMP/work"` and `--out "$RUNNER_TEMP/tool-synthetic-$SIZE.json"`. Keep its output.
    6. Fail if `modes_agree` or `incremental_agrees_with_full` is false.
    7. Write to `$GITHUB_STEP_SUMMARY`: the ref, the commit, the binary version, the runner and its CPU count, and the output of `run.py` in a `text` block.
    8. Upload the JSON and the output with `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2`, name `bench-tool-<size>`, `if-no-files-found: error` and `retention-days: 30`.
- D52. Each input goes to a step through `env:` (`SIZE`, `RUNS`), never as `${{ }}` in `run:`, so `zizmor` finds no template injection. `actionlint` and `zizmor` of the pre-commit hook check the file. The comments of the file are in STE.
- D53. The workflow commits nothing. A result of a shared runner is not a result of `bench/tool/README.md`, which names its host. The README gets one paragraph on the workflow. OWNER QUESTION (decided, see the last section): the default size. Recommendation: `medium` (1,194 documents).

**Files.** `.github/workflows/bench.yml` (REL; change set "CI or hooks", A ARC); `bench/tool/README.md` (TST). No change of `run.py` or `gen.py`.

**Test.** The CI lint job checks the file (pre-commit with `actionlint` and `zizmor`). After the merge, one run with `ref` set to the branch of 0.6.1 proves the job and gives the first artifact.
