## 3. Approval through the code host (item 4 of 0.8.0)

### D4. Approval through a review of the host

**Problem**:

An e-mail is no proof (ADR 0012), and an agent often commits with the e-mail of its owner (ADR 0018). The code host knows who approved a pull request, and spec-dna does not read it. Example: the agent runs `spec-dna approve` on its own initiative with the e-mail of the owner. `check` counts the approval.

**Mechanism**:

1. `[change] approval = "review"` is a third value. The approval of an artifact is a review by an approver that approves the pull request on the head commit. `base` and `branch` stay for a repository with no code host.
2. `approvers` items have 2 forms (Q15): an e-mail matches the author of a commit (`branch`), and `@<login>` matches an account of the host (`review`). A hidden address `<id>+<login>@users.noreply.github.com` also gives the login. With `review`, the list needs one login, or the exit code is 3.
3. The status lines stay. A person runs `spec-dna approve`, or the agent sets the status on the word of the owner in the chat, as today. The status says what was approved. The review says who approved it.
4. `check` with `review` has no network. SD910 reads the statuses as follows: an artifact may follow an earlier artifact whose approval status the same diff sets. Code under `Files` needs a plan that the base tree approves (reason 1), as with `base` (Q14). Thus the floor stays 2 pull requests: the design, then the code with the record and `finish`.
5. `spec-dna reviews [--pr <n>] [--json]` is the command that reads the reviews. It runs `gh` as a child process, so it adds no Rust dependency:
    - `gh api repos/{owner}/{repo}/pulls/<n>` gives the head and the base commits and the author.
    - `gh api --paginate --slurp repos/{owner}/{repo}/pulls/<n>/reviews` gives the reviews.
    - With no `--pr`, it reads the number from `GITHUB_EVENT_PATH` (`pull_request.number`).
6. The items that need an approval, from the diff of the merge base and the head commit (git, local):
    - each artifact whose approval status the diff sets: an approver;
    - the record, when it needs an acknowledgement (D3): an approver;
    - each group of persons of `[owners]` that matches a touched path: one person of the group (D5).
7. The reviews that count: for each login, the last review with the state `APPROVED`, `CHANGES_REQUESTED` or `DISMISSED`. That review counts when its state is `APPROVED` and its `commit_id` is the head commit (Q13). A review of the author of the pull request never counts.
8. On `merge_group`, the command exits 0 with a note: the queue takes only a pull request whose required checks passed.
9. A squash merge keeps the net diff. After it, `check` on the default branch reads the statuses of the base tree, as with `base`, and the record of the archive. `check` cannot show that a review existed: the host keeps the reviews.
10. A repository with no remote: `reviews` exits 3. Use `branch` or `base`.

**Formats**:

Exit codes of `reviews`, in the table of `docs/commands.md`:

- 0: each approval is present.
- 1: an approval is absent (the output names the item and who can give it).
- 2: usage, also no `--pr` and no `GITHUB_EVENT_PATH`.
- 3: configuration (`approval` is not `review`, the pin, no `@<login>` item in `approvers`, no remote, or no `gh`, as `eval run` treats an absent `claude`).
- 4: the call of the host failed. The causes are: `gh` exit 4 (`gh` has no signed-in account), `gh` exit 1 (an API or network error or an unknown pull request), or a head commit that is not in the clone.

Code 4 gets this new meaning in the table, beside a git or file error.

`reviews --json`:

```json
{"pr":12,"head":"4b825dc642cb6eb9a060e54bf8d69288fbee4904","ok":false,"items":[{"kind":"artifact","path":"docs/intent/sensor-timeout/plan.md","who":["@owner"],"by":null},{"kind":"owner","path":"src/auth/login.rs","who":["@lead"],"by":"@lead"}]}
```

The workflow that `init` writes with `review`, `.github/workflows/spec-dna-reviews.yml`:

```yaml
name: spec-dna reviews
on:
  pull_request:
    types: [opened, synchronize, reopened]
  pull_request_review:
    types: [submitted, edited, dismissed]
  merge_group:
permissions: {}
jobs:
  reviews:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false
      # The step "Install the pinned spec-dna" of spec-dna.yml (src/init.rs)
      - run: spec-dna reviews
        env:
          GH_TOKEN: ${{ github.token }}
```

The person makes the job `reviews` a required check of the default branch on the host.

**Codes**:

No new code. `reviews` reports by its exit code. SD910 keeps its code, its severity and its 9 reasons.

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[change] approval` | `"base"`, `"branch"` or `"review"` | `"base"` | `review` only on a question of `init`: a GitHub remote, and the answer yes |
| `[change] approvers` | e-mails and `@<login>` items | none | the logins of the answer with `review` |

With no answer to Q1, `review` with `strict` is exit code 3, as `branch` with `strict`. Q1 asks the owner to allow `review` with `strict`.

**Upgrade**:

An upgraded project keeps its value. `review` is new, so no project has it.

**Cost**:

- The host needs 2 accounts: the account that opens the pull request (the agent) and the account that approves (a person). The host does not let an author approve a pull request of that author (F19). A person whose agent opens pull requests with the account of that person cannot use `review`.
- A push after the review needs a new review. The same holds for the commit of `finish`. Run `finish` before the review.
- CI: one job for each push and each review. The estimate is 10 seconds per job, not a measurement.

**Does not prove**:

- What the gate proves: at the time of the job, an account of the list approved the head commit for each item that needs it.
- What rests on the branch protection of the host. The check is required. The merge waits for it on the last head. No administrator skips it. The host knows who the account is.
- That the person read the diff.

**Files and agents.** `src/reviews.rs` (new: the command, the `gh` calls, the items), `src/lifecycle.rs` (SD910 with `review`), `src/approval.rs` (the items of a diff, shared with `branch`), `src/config.rs` (the value, the login form), `schema/spec-dna.schema.json`, `src/main.rs`, `src/init.rs` (the question, the workflow), `docs/config.md`, `docs/commands.md`, `docs/guides/change.md`, `docs/init.md`. Agents: `diagnostics-engineer` (the change set "Approval in the branch", `reviews`), `core-engineer` (config, CLI), `init-engineer` (workflow).

**Tests**:

- `tests/reviews_cmd.rs`, a stub `gh` on `PATH` with canned JSON: a review by `@owner` that approves the head, for a plan that the diff approves: exit 0. The same review on an older commit: exit 1, and the output names the plan.
- A last review `CHANGES_REQUESTED` after an `APPROVED`: exit 1. A review by the author of the pull request: it does not count.
- A stub `gh` that exits 4: exit 4. A stub that prints nothing and exits 0: exit 4 (no head commit), never 0.
- No `GITHUB_EVENT_PATH` and no `--pr`: exit 2. No `gh` on `PATH`: exit 3.
- `tests/branch_approval.rs`: `review`, a diff with an intent and a plan set to `approved` in one pull request: no SD910. Code under `Files` in the same diff: SD910 reason 1.
- `tests/change_config.rs`: `review` with only e-mails: exit 3. `@octocat` with `branch`: exit 3.
- `tests/init_change.rs`: the workflow text (golden), with `permissions: {}` and the SHA of the checkout of `src/init.rs`.

## 4. The persons of `[owners]` (item 5 of 0.8.0)

This is D5 as the design of 0.8.0 had it before 2026-11-19. 0.8.0 keeps the parts of the roles. These are items 2, 3, 4 and 7, the first test, and the test of 2 globs. 0.8.0 accepts only a role name as an entry.

### D5. Owners by path (roles and persons)

**Problem**:

A change can touch a sensitive path, and nothing asks for the review that the path needs. Example: an agent edits `src/auth/session.rs` in a `routine` change. No security review happens, and `check` passes.

**Mechanism**:

1. `[owners]` maps a glob from the root to a list of entries. An entry is a role (`[a-z][a-z0-9-]*`, at most 40 characters) or a person (`@<login>`, or an e-mail). The glob form is the form of `high-risk-paths`, with the match of `src/glob.rs`. The form of a person must fit the mode, as for `approvers` (D4). `branch` needs an e-mail. `review` needs a login or a hidden address that gives one. Another form can never match, so it is exit code 3. With `base`, each form is valid.
2. Each glob that matches a touched path applies. No order and no last match exist, so the result is the union.
3. The touched paths of a change are the paths of its diff against the lifecycle base. When the diff holds more than one change, a path counts for a change when its `Files` covers it (the scope rule of `finish` step 5). The folder of the change and the archive do not count.
4. A role is satisfied by an `[[acceptor]]` entry with that role in the record (D3). Each role of each matched glob is needed. The role has no file of its own: the acceptor runs the skill `accept` with `--role <name>`, and reads the paths as a reviewer of that role.
5. The persons of one glob form a group. One person of the group must approve (Q16):
    - `branch`: an entry in `acknowledged-by` by `spec-dna approve <slug> acceptance` of that person (SD934). `approve` accepts such an author, also outside `approvers`.
    - `review`: a review by that login that approves the head (`reviews`).
    - `base`: no check. `check` prints one note: ``note: `[owners]` names persons, and `approval = "base"` cannot check them; use the code owners of the host`` (Q17).
6. `approvers` approve the artifacts and acknowledge the deviations. Persons of `[owners]` approve paths. One person in both lists satisfies both with one act. The 2 lists do not conflict.
7. `[owners]` has no R, A, C or I letters and no list of personas. A role name is a word that the record repeats.

**Formats**:

```toml
[owners]
"src/auth/**" = ["security-reviewer", "@lead", "@second-lead"]
"migrations/**" = ["db-reviewer"]
```

The first line needs an acceptor with the role `security-reviewer`, and the approval of `@lead` or `@second-lead`.

**Codes**:

SD933 (a role) and SD934 (a person with `branch`) of D3. A bad glob or entry is exit code 3.

**Config**:

| Key | Type | Default | `init` writes |
| --- | --- | --- | --- |
| `[owners]` | table: glob to a list of entries | `{}` | nothing |

**Upgrade**:

No table, no effect.

**Cost**:

- One more acceptance run for each role that matches. A `higher-risk` change counts a role entry as its second acceptor.
- One approval act for each group of persons.

**Does not prove**:

- That the role acceptor has the skill of the role. The role is a name.
- That any person rule holds with `base`.

**Files and agents.** `src/config.rs` (the table), `schema/spec-dna.schema.json`, `src/owners.rs` (new: the match, the items), `src/record.rs`, `src/approval.rs`, `src/approve.rs`, `src/reviews.rs`, `docs/config.md`, `docs/guides/change.md`. Agents: `core-engineer` (config, `approve`), `diagnostics-engineer` (codes, walk, `reviews`).

**Tests**:

- `tests/owners.rs`: `"src/auth/**" = ["security-reviewer"]`, a diff that edits `src/auth/a.rs`, a record with only `acceptor`: SD933 (before: exit 3, unknown table). With an entry `security-reviewer`: no SD933.
- `branch`, `"src/auth/**" = ["lead@example.test"]`: no acknowledgement gives SD934. `approve demo acceptance` by that author clears it.
- 2 globs that match one path: both lists apply.
- `base` with a person: the note, and no diagnostic.
- An entry `Security Reviewer` or `@`: exit 3.
- `@lead` with `branch`, or `lead@example.test` with `review`: exit 3 (before the rule: SD934 or `reviews` exit 1 that nothing can clear).

## 5. The acknowledgement by a person and by a review

Item 10 of D3, as the design of 0.8.0 had it. 0.8.0 keeps the `base` and `branch` parts for a deviation, with no person of `[owners]`.

- The acknowledgement of the record. It is needed when the record has a deviation (D7), or a person of `[owners]` matches a touched path (D5). The way depends on `[change] approval` (P4):
  - `base`: the merge of the pull request of `finish`. spec-dna checks nothing more.
  - `branch`: `spec-dna approve <slug> acceptance` adds the e-mail of its author to `acknowledged-by` and commits that file alone. The walk counts an entry only when 4 conditions hold: the commit added the entry, its author has that e-mail, the commit changes nothing else, and no later commit changes the record. Another such commit and the commit of `finish` are the exceptions. The commit of `finish` moves the same bytes to the archive. A record commit of the acceptor writes `acknowledged-by = []`. Any other commit that changes the record and keeps an entry gives SD932, so no entry outlives the text that it acknowledged. An approval commit of a second person keeps the first entry, and the commit of `finish` moves entries. Each clause of SD932 has these 2 exceptions. The person then runs `approve` again. Thus an approver never acknowledges a text that changed after the approval. The rule extends condition 3 of the approval commit (ADR 0012). An approver acknowledges the deviations. A person of `[owners]` acknowledges the paths.
  - `review`: a review that approves the head commit (D4). `spec-dna reviews` checks it, not `finish`.

The rows of SD932 and SD934, as the design of 0.8.0 had them. 0.8.0 keeps both codes for the acknowledgement of a deviation by an approver with `branch`.

| Code | Name | lite | standard | strict | Meaning |
| --- | --- | --- | --- | --- | --- |
| SD932 | record-commit-invalid | warning | error | error | With `branch`: a commit changes the record and another path, adds an entry of `acknowledged-by` that is not its author, or changes the record and keeps an entry. 2 commits are exceptions to each clause: an approval commit (`approve <slug> acceptance`), and the commit of `finish`, which moves the same bytes to the archive |
| SD934 | ack-missing | warning | error | error | With `branch`: a needed acknowledgement is absent. The message names who can give it |

| The deviations | As the record | As the record | As the record |

From D53:

The acknowledgement (P4): a summary is not an artifact of a change, so it needs no status and no approval commit of its own. An edit of its text, and a claim with `--holds`, are in the diff of the pull request. The acceptance record does not carry the claim in 0.8.0 (Q28).

| Refresh | `base` | `branch` | `review` |
| --- | --- | --- | --- |
| With a text edit | The merge of the pull request | Nothing more (the diff) | The approving review of the head |
| With `--holds` | The merge of the pull request | Nothing more: SD645 shows it | The approving review of the head |

From D54:

- After `finish`, `check` reports SD641 for each roll-up document that stays stale (an error in `standard` and `strict`, a warning in `lite`). The finding stays until an agent edits the summary and runs `refresh`, or runs `refresh --holds`. The fix is one more commit after `finish`. In `review` mode, the new head needs a new review that approves it.
- The approval modes. `base`: the merge covers the edits, the re-pins and the claims. `branch`: no approval commit for a summary; SD645 shows each claim. `review`: the review that approves the head covers the commit of `finish`, with its re-pins and claims. A forgotten summary costs one more commit and one more review. The acceptor does not see a claim of `finish --holds`. The tree of the record leaves Markdown out (D3), so a re-pin never makes the record stale.

## 6. The questions

Q1 and Q13 to Q17 moved with the mode. Q12 and Q41 stay in 0.8.0 with a change; their text of 0.8.0 is here for the person and the review parts.

**Q1. May the profile `strict` use `approval = "review"`?** (a) Yes. The host authenticates the reviewer, which is stronger than an e-mail. `strict` reads the statuses of the base for the code. (b) No: `strict` keeps `base` only. Recommendation: (a).

**Q12. When does the record need an acknowledgement?** (a) With a deviation or a person of `[owners]`. (b) Also for each `higher-risk` change. Recommendation: (a). The owner already approves the spec and the plan of a `higher-risk` change.

**Q13. Which review counts?** (a) Only a review of the head commit. (b) Also an older review, when the commits after it change only Markdown and the record. Recommendation: (a). Run `finish` before the review.

**Q14. With `review`, can code be in the pull request of its plan?** (a) No: the plan merges first, so the work waits for the approval (2 pull requests). (b) Yes: one review approves the plan and the code at once, with no order. Recommendation: (a).

**Q15. Where are the host logins?** (a) In `approvers`, as `@<login>` items. (b) In a new key `reviewers`. Recommendation: (a): one list of persons.

**Q16. How do the entries of one glob of `[owners]` combine?** (a) Each role is needed, and one person of the persons. (b) Each entry is needed. Recommendation: (a), as the code owners of a host.

**Q17. What do persons of `[owners]` do with `approval = "base"`?** (a) A note: `base` cannot check them. (b) Exit code 3. Recommendation: (a).

**Q41. How does the mode `base` acknowledge the deviations of a change?** (a) The merge of the pull request: `finish` prints them and checks nothing more. (b) `finish` stops unless the command has `--ack-deviations <hash of the printed list>`. That forces a second run after a read, but an agent can type the hash. Recommendation: (a). The mode `base` already trusts the merge for each approval. Use `branch` or `review` where the acknowledgement must name a person.
